## 问题概述

我们系统的底层数据源支持多维模型，业务在多维模型基础上体系性的定义了维度、度量、指标，单次查询可以指定维度、度量、指标、时间粒度的灵活组合，通过这些组合可实现对底层OLAP表进行过滤优选，直到最终选择出来一个满足组合条件的最优表，然后查询信息基于优选表组装成SQL查询，然后返回查询对应的结果。

现在我们设计了本体的对象、属性以及属性与多维模型（维度、度量、指标）的绑定，这里面存在一个很重要的问题：
业务对象上通常会定义丰富的属性，在属性定义时分为如下情况：
1. 多维建模的维度、指标是分为研发和现场定制，这就会出现一个情况：
    - 研发定义了一个小区维度，名称为CGI，基于该维度定义了上行流量、下行流量、用户数几个指标
    - 一线出于自己的考虑，又定义了一个新的小区维度，名称为 CUSTOM_CGI，基于该维度定义了总流量、上行时延、上行速率
2. 属性绑定维度时就需要支持属性绑定多维度（业务含义相同的维度），此时会出现小区对象的小区ID属性绑定了CGI维度、CUSTOM_CGI维度
3. 其他属性（例如指标属性），会定义为两个属性的合集，如上行流量、下行流量、用户数、总流量、上行时延、上行速率

这样就会在LLM针对本体对象的属性分析时出现要求查询小区ID属性的上行流量、下行流量、用户数、总流量、上行时延、上行速率的情况。这种在OQL如果直接按维度、指标组合下发到多维模型服务进行查询时，是无法查询成功的：因为按照组合选表时，没有任何一个表满足这些过滤条件。

针对以上，初步考虑采用如下方式：
1. 维度属性和指标属性如果是绑定多维模型，在绑定时建立“属性组”的概念，在一个属性可用组内是有可用的多维模型对应的表
2. 有该属性可用组的概念后，OAC在OQL到多维查询中间增加分析逻辑，可以将一个OQL查询按属性可用组拆为多个物理的多维查询执行计划
3. 每个组返回结果后，再根据维度属性在内存中做数据的拼接

请对以上问题进行描述逻辑和处理的整理，之后总结输出如下章节内容，并对该功能给出一个功能名，能见名知义同时体现技术深度：
1. 章节1：业务问题场景
2. 章节2：业务问题实例化举例，含业务问题期望的处理过程与结果，在此处针对物理表也可能存在该情况，一并进行举例（物理表方式是否可以通过物理表等同为属性可用组，不用额外定义属性可用组了）
3. 章节3：针对业务问题做系统性的归类整理，给出该类问题的系统性处理思路。
4. 章节4: 以"OQL查询语句"->"物理执行计划拆分"->"并行执行"-> "结果合并"为流程，给出设计思路参考




你这个问题本质上已经不是“一个属性绑定多个维度”这么简单，而是一个典型的**语义查询与物理数据可组合性不一致**的问题：

> **本体层允许Agent按业务语义自由组合对象属性，但底层多维模型/物理模型的数据能力存在天然边界，并非任意属性组合都能由单一物理查询满足。因此OAC需要把一个语义完整的OQL，编译成多个物理可执行子计划，再通过公共维度进行结果融合。**

这个能力实际上已经接近数据库领域的 **Logical Query → Physical Plan → Federated Execution** 思想，只不过你这里多了一层“本体语义→多维模型能力”的映射。

功能名称我优先推荐：

> ## **语义查询分解与融合执行**
>
> **Semantic Query Decomposition & Fusion Execution**

如果希望更突出OAC的技术深度，可以叫：

> **语义驱动物理执行计划编排**
> **Semantic-driven Physical Execution Planning**

前者更“见名知义”，后者更偏底层引擎技术。下面按第一个名称展开。

# 1. 业务问题场景

## 1.1 问题背景

本体面向业务提供统一的对象语义。

例如定义：

```text
Cell
├── CGI
├── ULTraffic
├── DLTraffic
├── UserCount
├── TotalTraffic
├── ULLatency
└── ULThroughput
```

对于Agent而言，这些都是：

> **Cell对象下可以访问的业务属性。**

因此Agent完全合理地生成：

```text
查询某小区的：
CGI
上行流量
下行流量
用户数
总流量
上行时延
上行速率
```

对应OQL逻辑上也完全成立。

问题出现在物理执行阶段。

---

## 1.2 多维模型存在“属性组合可用边界”

研发定义：

```text
维度：CGI

指标：
├── UL_TRAFFIC
├── DL_TRAFFIC
└── USER_COUNT
```

底层可优选到：

```text
Table_A
CGI + UL_TRAFFIC + DL_TRAFFIC + USER_COUNT
```

现场又定义：

```text
维度：CUSTOM_CGI

指标：
├── TOTAL_TRAFFIC
├── UL_LATENCY
└── UL_THROUGHPUT
```

可优选到：

```text
Table_B
CUSTOM_CGI + TOTAL_TRAFFIC
           + UL_LATENCY
           + UL_THROUGHPUT
```

业务上：

```text
CGI ≡ CUSTOM_CGI
```

都表示：

> Cell.CellID

所以本体绑定可以是：

```text
Cell.CellID
   ├── CGI
   └── CUSTOM_CGI
```

但这并不意味着：

```text
CGI
CUSTOM_CGI
UL_TRAFFIC
DL_TRAFFIC
USER_COUNT
TOTAL_TRAFFIC
UL_LATENCY
UL_THROUGHPUT
```

可以任意组合成一次多维查询。

---

## 1.3 当前直接查询为什么失败

Agent生成：

```text
SELECT
    Cell.CellID,
    Cell.ULTraffic,
    Cell.DLTraffic,
    Cell.UserCount,
    Cell.TotalTraffic,
    Cell.ULLatency,
    Cell.ULThroughput
```

如果直接转换成多维模型查询：

```text
Dimension:
    CGI / CUSTOM_CGI

Metrics:
    UL_TRAFFIC
    DL_TRAFFIC
    USER_COUNT
    TOTAL_TRAFFIC
    UL_LATENCY
    UL_THROUGHPUT
```

多维模型服务会尝试：

> 找到一张同时满足这些维度、指标组合的最优表。

但实际上：

```text
Table_A：前三个指标
Table_B：后三个指标
```

不存在：

```text
Table_X：
CGI
+ 6个指标
```

因此选表失败。

---

# 1.4 问题本质

这里必须明确区分两个概念：

### 本体属性可组合性

从业务语义看：

```text
Cell.ULTraffic
Cell.ULLatency
Cell.UserCount
```

都是Cell属性，可以组合查询。

### 物理属性可组合性

从数据执行看：

```text
ULTraffic + UserCount
```

可以由Table_A一次查询。

但：

```text
ULTraffic + ULLatency
```

无法由同一物理数据集满足。

所以存在：

> **Semantic Composability ≠ Physical Composability**

这是该能力真正要解决的问题。

# 2. 业务问题实例化

## 2.1 多维模型场景

假设本体：

```text
Cell
├── CellID
├── ULTraffic
├── DLTraffic
├── UserCount
├── TotalTraffic
├── ULLatency
└── ULThroughput
```

绑定关系：

| 本体属性         | 多维元素          | 可用数据集合  |
| ------------ | ------------- | ------- |
| CellID       | CGI           | Group A |
| ULTraffic    | UL_TRAFFIC    | Group A |
| DLTraffic    | DL_TRAFFIC    | Group A |
| UserCount    | USER_COUNT    | Group A |
| CellID       | CUSTOM_CGI    | Group B |
| TotalTraffic | TOTAL_TRAFFIC | Group B |
| ULLatency    | UL_LATENCY    | Group B |
| ULThroughput | UL_THROUGHPUT | Group B |

用户问：

> 查询Cell001昨天的上行流量、下行流量、用户数、总流量、上行时延和上行速率。

Agent只需要理解业务语义。

生成一个OQL：

```text
SELECT
    Cell.CellID,
    Cell.ULTraffic,
    Cell.DLTraffic,
    Cell.UserCount,
    Cell.TotalTraffic,
    Cell.ULLatency,
    Cell.ULThroughput

WHERE
    Cell.CellID = 'Cell001'
    AND Cell.Time = Yesterday
```

**不要要求Agent自己拆成两个OQL。**

这是OAC应该解决的问题。

---

## 2.2 OAC执行计划拆分

OAC分析Binding后发现：

```text
                 Logical OQL
                     │
          ┌──────────┴──────────┐
          ↓                     ↓
       Group A                Group B
          │                     │
      CellID/CGI          CellID/CUSTOM_CGI
      ULTraffic           TotalTraffic
      DLTraffic           ULLatency
      UserCount           ULThroughput
```

于是生成：

### Physical Plan A

```text
Dimension:
CGI

Metrics:
UL_TRAFFIC
DL_TRAFFIC
USER_COUNT
```

### Physical Plan B

```text
Dimension:
CUSTOM_CGI

Metrics:
TOTAL_TRAFFIC
UL_LATENCY
UL_THROUGHPUT
```

两个计划分别交给多维模型服务执行。

---

## 2.3 返回结果

Plan A：

| CGI     | UL Traffic | DL Traffic | User Count |
| ------- | ---------: | ---------: | ---------: |
| Cell001 |        100 |        200 |         50 |

Plan B：

| CUSTOM_CGI | Total Traffic | UL Latency | UL Throughput |
| ---------- | ------------: | ---------: | ------------: |
| Cell001    |           300 |         10 |            50 |

OAC知道：

```text
CGI
   ↓
Cell.CellID
   ↑
CUSTOM_CGI
```

因此使用本体统一语义：

```text
Cell.CellID
```

作为结果融合Key。

最终：

| CellID  | UL Traffic | DL Traffic | User Count | Total Traffic | UL Latency | UL Throughput |
| ------- | ---------: | ---------: | ---------: | ------------: | ---------: | ------------: |
| Cell001 |        100 |        200 |         50 |           300 |         10 |            50 |

对于Agent而言，整个过程仍然只是：

> **查询Cell对象的6个属性。**

底层执行了几次查询、用了CGI还是CUSTOM_CGI、用了哪几张表，都被OAC屏蔽。

这正是本体语义访问应该提供的价值。

---

# 2.4 物理表场景

物理表同样存在这个问题。

例如：

### CELL_TRAFFIC

```text
CGI
TIME
UL_TRAFFIC
DL_TRAFFIC
USER_COUNT
```

### CELL_QUALITY

```text
CELL_ID
TIME
UL_LATENCY
UL_THROUGHPUT
```

本体：

```text
Cell.CellID
    ├── CELL_TRAFFIC.CGI
    └── CELL_QUALITY.CELL_ID
```

其他属性分别绑定：

```text
Cell.ULTraffic
    → CELL_TRAFFIC.UL_TRAFFIC

Cell.ULLatency
    → CELL_QUALITY.UL_LATENCY
```

用户仍然可以：

```text
SELECT
    Cell.CellID,
    Cell.ULTraffic,
    Cell.ULLatency
```

OAC需要拆：

```text
Plan A
CELL_TRAFFIC
CGI + UL_TRAFFIC

Plan B
CELL_QUALITY
CELL_ID + UL_LATENCY
```

然后：

```text
CGI ↔ Cell.CellID ↔ CELL_ID
```

进行结果融合。

# 2.5 物理表是否可以直接等同于“属性可用组”？

**可以，而且我建议优先这么设计，不要为了统一概念而强制给物理表再配置一个属性可用组。**

原因是物理表天然已经定义了：

> **哪些字段可以在一次物理查询中共同获得。**

例如：

```text
CELL_TRAFFIC
├── CGI
├── TIME
├── UL_TRAFFIC
├── DL_TRAFFIC
└── USER_COUNT
```

它本身就是一个天然的：

> **Physical Capability Set**

没有必要重复配置：

```text
Group A =
CGI + TIME + UL_TRAFFIC + DL_TRAFFIC + USER_COUNT
```

否则会出现两份信息：

```text
Table Schema
+
Property Available Group
```

容易产生一致性问题。

---

## 但多维模型有所不同

多维模型：

```text
Dimension
Measure
Metric
```

到物理表并不是简单的一对一关系。

同一个：

```text
CGI + UL_TRAFFIC
```

可能通过多维模型选表规则最终选择不同物理表。

所以对于多维模型，你真正需要表达的并不一定是“属性组”，而应该是：

# **查询能力域 / Query Capability Set**

定义：

> **哪些维度、度量、指标可以在一次多维查询中合法组合，并由底层选表机制找到可执行数据集。**

因此我建议把你当前的：

> “属性可用组”

稍微升级一下命名。

推荐：

### **查询能力组**

**Query Capability Group**

或者更技术化：

### **物理可执行域**

**Physical Executability Domain**

我更推荐前者，容易理解。

# 3. 系统性处理思路

整个问题建议抽象成：

> **一个逻辑语义查询，可能需要映射到多个物理查询能力域，由OAC自动完成查询分解、计划优化、并行执行和语义结果融合。**

## 3.1 第一层：保持OQL语义完整

这一点非常重要。

不要让Agent知道：

```text
ULTraffic来自Group A
ULLatency来自Group B
```

Agent仍然：

```text
Cell
├── ULTraffic
├── ULLatency
└── UserCount
```

生成：

```text
SELECT
 Cell.ULTraffic,
 Cell.ULLatency,
 Cell.UserCount
```

也就是说：

> **OQL表达用户“想查什么”，而不是底层“怎么查”。**

---

# 3.2 第二层：建立物理查询能力描述

不同数据源可以采用不同方式产生Capability。

### 多维模型

显式定义或从多维元数据自动推导：

```text
Capability A
├── CGI
├── UL_TRAFFIC
├── DL_TRAFFIC
└── USER_COUNT

Capability B
├── CUSTOM_CGI
├── TOTAL_TRAFFIC
├── UL_LATENCY
└── UL_THROUGHPUT
```

### 物理模型

直接从：

```text
Table Schema
```

推导：

```text
Table = Capability
```

### API

实际上未来也可以使用相同模型：

```text
API A
├── input: CGI
└── output:
    ├── ULTraffic
    └── DLTraffic
```

API本身也是一个Capability。

所以继续抽象以后，你会发现：

> **Query Capability并不应该是多维模型特有概念，而可以成为OAC统一描述“一个数据能力一次能提供哪些本体属性”的模型。**

这个方向很有价值。

---

# 3.3 第三层：OAC进行Capability Matching

输入：

```text
Required Properties:

CellID
ULTraffic
DLTraffic
UserCount
TotalTraffic
ULLatency
ULThroughput
```

候选能力：

```text
Capability A
→ CellID + ULTraffic + DLTraffic + UserCount

Capability B
→ CellID + TotalTraffic + ULLatency + ULThroughput
```

OAC求解：

> **使用尽可能少且代价尽可能低的Capability覆盖全部Required Properties。**

抽象上实际上变成：

### **Capability Cover Problem**

即：

```text
Required Attribute Set
        ↓
Candidate Capability Sets
        ↓
Minimum / Optimal Cover
        ↓
Physical Execution Plans
```

这比简单“按属性组拆查询”更系统。

---

# 3.4 第四层：不是所有能拆的查询都一定能合

这里必须增加一个约束，否则后面容易出现数据正确性问题。

两个Plan可以融合，至少需要存在：

> **Compatible Join Key + Compatible Grain**

例如：

Plan A：

```text
CGI + 15分钟
```

Plan B：

```text
CUSTOM_CGI + 15分钟
```

可以通过：

```text
CellID + TimeBucket
```

融合。

但如果：

Plan A：

```text
Cell + 15分钟
```

Plan B：

```text
Region + 1天
```

就不能简单Join。

所以Capability还需要描述：

```text
Dimensions
Grain
Temporal Grain
Join Key
Cardinality
```

OAC执行计划阶段进行：

### **Grain Compatibility Check**

即：

> 查询能力覆盖只是第一步，粒度兼容才允许结果融合。

---

# 3.5 第五层：统一语义Join Key

你这里还有一个非常重要的问题：

```text
CGI
```

和：

```text
CUSTOM_CGI
```

物理字段虽然不同，但本体都绑定：

```text
Cell.CellID
```

因此真正的Join不是：

```text
CGI = CUSTOM_CGI
```

而是：

```text
CGI
  ↓
Cell.CellID
  ↑
CUSTOM_CGI
```

OAC应基于本体Canonical Property确定：

```text
Semantic Join Key = Cell.CellID
```

如果值编码也不同，则进一步通过你前面讨论的：

> **多标识语义解析与转换**

完成：

```text
CGI Value
     ↓
Canonical Cell ID
     ↑
CUSTOM_CGI Value
```

再Join。

这样前面设计的能力正好可以复用。

---

# 3.6 第六层：结果融合不能只考虑Join

建议至少支持：

```text
JOIN
UNION
MERGE
AGGREGATE
RECOMPUTE
```

例如：

### 横向属性拼接

```text
A:
Cell + Traffic

B:
Cell + Latency

→ JOIN
```

### 相同属性不同时间分表

```text
Table_202607
Table_202608

→ UNION
```

### 不同粒度数据

可能：

```text
ROLLUP / AGGREGATE
```

之后才能Join。

所以建议底层模块不要直接叫：

> Result Joiner

而叫：

### **Semantic Result Fusion**

这样扩展性更好。

---

# 4. OQL → 物理执行计划 → 并行执行 → 结果融合

完整流程建议设计成下面四个阶段。

## 阶段一：OQL逻辑查询

Agent生成：

```text
SELECT
 Cell.CellID,
 Cell.ULTraffic,
 Cell.DLTraffic,
 Cell.UserCount,
 Cell.TotalTraffic,
 Cell.ULLatency,
 Cell.ULThroughput

WHERE ...
```

此时只描述：

> **业务需要什么。**

---

## 阶段二：物理执行计划拆分

OAC进行：

```text
OQL
 ↓
Schema Resolution
 ↓
Property Binding Resolution
 ↓
Required Attribute Set
 ↓
Query Capability Discovery
 ↓
Capability Matching
 ↓
Grain Compatibility Check
 ↓
Plan Optimization
```

最终生成：

```text
Logical Plan
     │
     ├──── Physical Plan A
     │
     │     CGI
     │     UL_TRAFFIC
     │     DL_TRAFFIC
     │     USER_COUNT
     │
     └──── Physical Plan B
           CUSTOM_CGI
           TOTAL_TRAFFIC
           UL_LATENCY
           UL_THROUGHPUT
```

---

## 阶段三：并行执行

如果两个Plan不存在依赖关系：

```text
            Execution DAG
                 │
         ┌───────┴───────┐
         ↓               ↓
      Plan A           Plan B
         │               │
     多维查询          多维查询
         │               │
         └───────┬───────┘
                 ↓
```

OAC可以并行执行。

这对于Agent场景尤其重要，因为原来：

```text
Agent查询A
↓
等待
↓
Agent发现还缺B
↓
再次查询
```

变成：

```text
Agent一个OQL
      ↓
OAC自动拆分
      ↓
A || B并行
```

既减少Agent React轮次，也降低总体时延。

---

# 阶段四：语义结果融合

OAC根据Execution Plan中预先确定的：

```text
Semantic Join Key
Grain
Temporal Grain
Merge Strategy
```

进行融合：

```text
Plan A Result
      │
      ├── Cell.CellID ──┐
      │                 │
                        ├─ Semantic Result Fusion
      │                 │
      ├── Cell.CellID ──┘
Plan B Result
```

最终重新恢复为OQL要求的统一本体结果：

```text
Cell
├── CellID
├── ULTraffic
├── DLTraffic
├── UserCount
├── TotalTraffic
├── ULLatency
└── ULThroughput
```

Agent完全不需要知道底层实际执行了几个Query。

---

# 5. 建议的整体架构

可以最终抽象为：

```text
                         Agent
                           │
                           ↓
                    Semantic OQL
                           │
                           ↓
              ┌───────────────────────┐
```

# 6. 对“属性可用组”的最终建议

你的初步方案**方向是正确的**，但我建议从“属性组”进一步抽象。

不要定义成：

> **属性可用组 = 一堆属性放在一起。**

而定义成：

> **查询能力组（Query Capability Group）：描述一个物理数据能力在一次查询中能够共同提供的本体属性集合，以及其可用维度、粒度、时间粒度和关联键。**

例如：

```text
QueryCapabilityGroup A

sourceType:
  MULTIDIMENSIONAL

availableProperties:
  Cell.CellID
  Cell.ULTraffic
  Cell.DLTraffic
  Cell.UserCount

dimensions:
  Cell.CellID

grain:
  CELL

temporalGrain:
  15MIN

physicalCapability:
  CGI
  UL_TRAFFIC
  DL_TRAFFIC
  USER_COUNT
```

物理表则**无需人工再定义一份Group**：

```text
Physical Table
       ↓ 自动推导
Query Capability
```

多维模型：

```text
Cube Metadata
       ↓ 分析/配置
Query Capability
```

API：

```text
API Schema
       ↓ 自动推导
Query Capability
```

这样未来整个OAC可以形成统一的：

> **Semantic Property → Query Capability → Physical Execution Plan**

而不是为多维模型单独设计一套特殊逻辑。

# 7. 功能名称建议

综合你的业务问题和未来架构，我最推荐两个层次的命名：

### 对外功能名称

# **语义查询分解与融合执行**

**Semantic Query Decomposition & Fusion Execution**

一句话定义：

> **基于本体属性与底层查询能力映射，将单一语义OQL自动分解为多个可执行物理查询计划，并通过并行执行和语义结果融合，实现跨数据能力的统一对象查询。**

### 底层核心技术名称

# **语义驱动物理执行计划编排**

**Semantic-driven Physical Execution Planning**

其内部包括：

> **Capability Discovery → Capability Matching → Query Decomposition → Plan Optimization → Parallel Execution → Semantic Result Fusion**

如果要放到OAC竞争力材料里，我会把它最终浓缩成：

> **语义查询智能分解与融合：突破底层单表/单模型的属性组合限制，基于查询能力自动将OQL拆解为最优物理执行计划并行执行，按本体统一维度进行结果融合，实现Agent面向对象的任意属性组合查询。**

这个表述既体现了**用户看到的功能价值——任意属性组合查询**，又体现了背后的技术深度——**从语义查询到物理执行计划的自动编译、优化与融合**。
