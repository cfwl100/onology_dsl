## 问题概述

根据用户query进行数据访问时，会涉及到访问意图理解，如访问明细数据、汇总数据，访问数据期望是按照5分钟粒度汇总还是1小时汇总。另外当前属性不感知底层的数据的原始计算粒度，这样就会出现：
1. 访问意图中的数据汇总、明细以及汇总粒度无法理解
2. 实际数据为5分钟，访问时如果没有指定汇总粒度，可能会出现细粒度的多条记录，此时LLM处理复杂，同时也会造成数据膨胀，超过token上下文大小

请对以上问题进行描述逻辑和处理的整理，之后总结输出如下章节内容，并对该功能给出一个功能名，能见名知义同时体现技术深度：
1. 章节1：业务问题场景
2. 章节2：业务问题实例化举例，含业务问题期望的处理过程与结果，在此处针对物理表也可能存在该情况，一并进行举例（物理表方式是否可以通过物理表等同为属性可用组，不用额外定义属性可用组了）
3. 章节3：针对业务问题做系统性的归类整理，给出该类问题的系统性处理思路。
4. 章节4: 以属性自身存在用途差异以及局点个性化诉求为输入，给出设计思路参考


这个问题本质上不是简单的“5分钟还是1小时”，而是：

> **自然语言中的查询粒度意图，如何与本体属性对应数据的原始数据粒度、可聚合能力以及LLM可消费的数据规模进行统一协调。**

建议把该能力定义为：

# **语义粒度解析与自适应聚合**

**Semantic Granularity Resolution & Adaptive Aggregation**

这个名字同时体现两层能力：

* **Semantic Granularity Resolution**：理解用户究竟要明细、汇总、趋势，以及5分钟/小时/天等分析粒度；
* **Adaptive Aggregation**：结合底层数据原始粒度、指标聚合规则、时间范围和结果规模，自动选择合理的数据聚合方式。

如果偏OAC底层技术名称，也可以叫：

> **查询粒度语义编译（Query Granularity Semantic Compilation）**

下面按四章整理。

# 1. 业务问题场景

## 1.1 问题背景

网络指标类查询通常同时存在三个不同的“粒度”概念：

### ① 用户期望的分析粒度

例如：

> 查询昨天每小时PRB利用率趋势。

这里明确要求：

```text
分析粒度 = 1小时
```

---

### ② 底层数据原始粒度

实际数据可能每：

```text
5分钟
```

产生一条记录：

```text
10:00
10:05
10:10
...
```

这属于：

> **Physical/Data Native Granularity**

---

### ③ 返回给Agent/LLM的结果粒度

即使底层是5分钟数据，也未必应该直接给LLM全部明细。

例如：

```text
7天 × 24小时 × 12条/小时
= 2016条/小区
```

如果再查询100个小区：

```text
20万+记录
```

不仅SQL扫描量增加，更重要的是：

> 返回数据会快速膨胀，导致LLM上下文变长、分析效率下降甚至超过Token限制。

所以需要解决：

> **业务查询粒度、底层原始粒度、最终消费粒度三者之间如何协调。**

---

## 1.2 当前缺失的两个核心能力

### 第一：无法准确理解查询意图

用户可能表达：

* 查原始明细；
* 看趋势；
* 按小时汇总；
* 看每天情况；
* 比较最近一周；
* 看整体平均值。

这些并不只是时间过滤，而是在表达：

```text
DETAIL
AGGREGATE
TREND
TIME_SERIES
```

以及：

```text
5MIN
15MIN
1H
1DAY
```

如果不识别，就无法正确生成OQL。

---

### 第二：本体属性不知道数据天然粒度

例如：

```text
Cell.PRBUsage
```

只知道：

```text
属性 = PRB利用率
数据类型 = double
```

但不知道绑定的数据是：

```text
5分钟粒度
```

于是当用户说：

> 查询最近7天PRB情况

没有显式要求粒度时，OAC可能直接返回2016条5分钟数据。

这在SQL上可能正确，但在Agent场景下并不是好的结果。

---

# 2. 业务问题实例化举例

## 2.1 示例一：用户明确指定1小时粒度

用户问题：

> 查询Cell001昨天每小时的PRB利用率变化。

### 意图理解

得到：

```text
对象：Cell
属性：PRBUsage

访问模式：TIME_SERIES
时间范围：Yesterday
期望粒度：1H
```

底层数据：

```text
Native Granularity = 5MIN
```

因此：

```text
5MIN
 ↓
聚合
 ↓
1H
```

假设PRB利用率聚合规则为：

```text
AVG
```

则生成类似：

```sql
SELECT
    hour_bucket,
    AVG(prb_usage)
FROM ...
WHERE ...
GROUP BY hour_bucket
```

最终返回：

```text
00:00  45%
01:00  48%
...
23:00  72%
```

而不是288条5分钟数据。

---

## 2.2 示例二：用户明确要求明细

用户：

> 查询10:00~10:30期间Cell001的原始PRB明细。

解析：

```text
Access Mode = DETAIL
Requested Granularity = NATIVE
```

底层：

```text
Native Granularity = 5MIN
```

所以直接返回：

```text
10:00
10:05
10:10
10:15
10:20
10:25
```

此时平台不应该强行汇总。

---

## 2.3 示例三：用户没有指定粒度

用户：

> 分析最近7天Cell001的PRB变化趋势。

没有说：

```text
5分钟
1小时
每天
```

但语义上明确是：

> 趋势分析，而不是查原始明细。

如果底层数据：

```text
5MIN
```

直接返回2016条并不合理。

平台可以结合：

```text
时间范围 = 7天
任务类型 = TREND
原始粒度 = 5MIN
结果规模
```

自动选择：

```text
1H
```

或者：

```text
1DAY
```

作为默认分析粒度。

例如：

```text
7天趋势
→ 默认1H

30天趋势
→ 默认1DAY
```

这种机制就是：

> **Adaptive Granularity**

---

## 2.4 示例四：只需要一个汇总值

用户：

> 昨天Cell001的平均PRB利用率是多少？

解析：

```text
Access Mode = AGGREGATE
Temporal Granularity = WHOLE_RANGE
Aggregation = AVG
```

底层即使有：

```text
288条5分钟数据
```

最终只返回：

```text
Cell001
Yesterday AVG PRB = 67.3%
```

这种场景不存在“每小时”或者“5分钟”粒度问题，因为：

> 整个时间范围就是一个Aggregation Window。

---

## 2.5 示例五：多对象数据膨胀

用户：

> 分析100个小区最近7天PRB利用率变化。

5分钟原始数据：

```text
100 × 7 × 24 × 12
= 201,600条
```

如果直接交给LLM，基本不可接受。

如果调整为：

```text
1小时
```

则：

```text
100 × 7 × 24
= 16,800条
```

仍可能较大。

进一步根据任务目的，例如用户要的是：

> 找出高负荷小区

OAC/ODI可以进一步执行：

```text
每小时聚合
+
阈值过滤
+
TopN
```

最终只返回：

```text
Top 20异常小区
+
异常时段
+
最大/平均PRB
```

说明这里不能只处理“时间粒度”，还应考虑：

> **Agent消费规模。**

# 2.6 物理表场景

这个问题在物理表中同样存在。

例如：

```text
CELL_KPI_5MIN

CGI
COLLECT_TIME
PRB_USAGE
DL_THROUGHPUT
```

表名本身可能已经明确：

```text
5MIN
```

此时物理模型可以直接定义：

```text
nativeGranularity = 5MIN
```

如果还有：

```text
CELL_KPI_HOUR
```

则：

```text
nativeGranularity = 1H
```

OAC甚至可以根据用户要求：

```text
Requested = 1H
```

优先选择：

```text
CELL_KPI_HOUR
```

而不是从5分钟表重新聚合。

这和你前面提到的“多维模型优选表”可以结合起来：

> **粒度也应成为物理数据能力选择的重要约束条件。**

---

## 2.7 物理表是否需要额外定义“属性可用组”？

针对本问题，通常**不需要因为粒度额外建立属性可用组**。

物理表本身就可以描述：

```text
这个表有哪些字段
+
这些字段对应什么原始粒度
```

例如：

```text
CELL_KPI_5MIN
├── available properties
└── nativeGranularity = 5MIN
```

即可作为：

> Query Capability

的一部分。

所以更推荐：

```text
Physical Table
    ↓
Query Capability
├── Properties
├── Dimensions
├── Native Granularity
└── Aggregation Capability
```

而不是再复制维护一个单独“粒度属性组”。

# 3. 系统性归类与处理思路

这个问题建议系统化拆成四个概念。

## 3.1 Access Mode——访问模式

首先理解用户究竟想：

```text
DETAIL
AGGREGATE
TIME_SERIES
DISTRIBUTION
TOP_N
COMPARISON
```

例如：

| 用户表达       | Access Mode  |
| ---------- | ------------ |
| 查询原始记录     | DETAIL       |
| 昨天平均PRB    | AGGREGATE    |
| 最近7天变化     | TIME_SERIES  |
| 各地市分布      | DISTRIBUTION |
| Top10高负荷小区 | TOP_N        |

这是意图层信息。

---

# 3.2 Requested Granularity——期望粒度

用户可能明确指定：

```text
RAW
5MIN
15MIN
1H
1DAY
1W
1MONTH
```

也可能：

```text
AUTO
```

即用户没有指定。

建议TaskIR显式表达：

```json
{
  "accessMode": "TIME_SERIES",
  "granularity": {
    "type": "AUTO"
  }
}
```

而不是把粒度隐含在自然语言里。

---

# 3.3 Native Granularity——原始数据粒度

这是物理数据能力的一部分。

例如：

```text
Cell.PRBUsage

binding:
  source = CELL_KPI_5MIN

nativeGranularity = 5MIN
```

或者多维模型：

```text
Cube:
CellPerformance

supportedGranularity:
5MIN
15MIN
1H
1DAY
```

这里不要把原始粒度简单写成属性本身的业务语义。

更准确地说：

> **粒度属于属性Binding对应的数据能力。**

因为同一个：

```text
Cell.PRBUsage
```

可能同时绑定：

```text
5分钟事实表
小时汇总表
日汇总表
```

属性自己没有唯一原始粒度。

---

# 3.4 Aggregation Semantics——聚合语义

从5分钟转1小时，必须知道怎么聚。

例如：

```text
Traffic
→ SUM

PRBUsage
→ AVG/MAX

PeakThroughput
→ MAX

SuccessRate
→ RECOMPUTE

UserCount
→ 可能DISTINCT_COUNT
```

因此：

```text
Native Granularity
+
Requested Granularity
```

只决定：

> 要不要聚合。

而：

```text
Aggregation Semantics
```

决定：

> 怎么聚合。

---

# 3.5 Adaptive Granularity Policy——自适应粒度策略

如果用户没有指定粒度，可以根据：

```text
任务类型
时间范围
对象数量
底层原始粒度
预计返回行数
LLM Token Budget
```

自动选择。

例如：

```text
ExpectedRows
=
ObjectCount
× TimeRange / Granularity
× DimensionCardinality
```

如果：

```text
ExpectedRows > ResultBudget
```

则：

```text
5MIN → 15MIN → 1H → 1DAY
```

逐级提升粒度。

但不能无限聚合，要受到：

> 任务分析需要

约束。

例如异常定位：

```text
不能从5分钟直接聚成1天
```

否则会丢失异常峰值。

所以策略应该：

> **在满足分析目标的前提下，选择能够控制结果规模的最粗合理粒度。**

---

# 3.6 建议最终形成三个粒度

这是架构上非常值得明确的。

```text
Native Granularity
底层原始粒度

Requested Granularity
用户期望粒度

Effective Granularity
最终执行粒度
```

例如：

```text
Native = 5MIN

Requested = AUTO

Task = 7 Days Trend

Effective = 1H
```

这样非常清楚。

# 4. 整体设计思路

你章节4的描述我建议稍作调整，当前问题更适合以：

> **“访问意图差异 + 底层数据粒度差异 + Agent消费规模约束”**

作为输入。

完整链路可以设计为：

```text
用户Query
   ↓
访问意图理解
   ↓
Access Mode识别
   │
   ├── DETAIL
   ├── AGGREGATE
   └── TIME_SERIES
   ↓
期望粒度识别
   │
   ├── 用户明确指定
   └── AUTO
   ↓
OAG获取本体属性
   ↓
Binding Capability分析
   │
   ├── Native Granularity
   ├── Supported Granularity
   └── Aggregation Semantics
   ↓
Granularity Planner
   │
   ├── Time Range
   ├── Object Count
   ├── Expected Rows
   ├── Token Budget
   └── Analysis Requirement
   ↓
确定Effective Granularity
   ↓
OQL / Physical Plan
   ↓
OAC选择已有汇总数据
或执行Rollup聚合
   ↓
Result Size Check
   ↓
返回Agent可消费结果
```

---

用户：

生成：

```json

  "accessMode": "TIME_SERIES",
  "timeRange": "LAST_7_DAYS",
  "requestedGranularity": "AUTO"
}
```

用户：

> 查询10点到10点半5分钟明细。

生成：

```json
{
  "accessMode": "DETAIL",
  "requestedGranularity": "5MIN"
}
```

## 4.2 本体/Binding层

本体告诉Agent/OAC：

```text
Cell.PRBUsage
```

代表什么。

Binding告诉OAC：

```text
Source A：
CELL_KPI_5MIN
nativeGranularity = 5MIN

Source B：
CELL_KPI_HOUR
nativeGranularity = 1H
```

这样语义层和物理粒度层保持解耦。

---

## 4.3 Granularity Planner

这是建议增加的核心能力。

输入：

```text
Access Mode
Requested Granularity
Time Range
Object Count
Native Granularity
Aggregation Semantics
Result Budget
```

输出：

```text
Effective Granularity
```

例如：

```text
最近7天趋势
+
100个小区
+
5MIN源数据
+
未指定粒度
+
Token Budget有限

↓


Effective Granularity = 1H
```

---

## 4.4 OAC执行

优先级建议：

### 方案1：已有符合粒度的数据

```text
Requested = 1H
已有1H汇总表
```

直接查询：

```text
CELL_KPI_HOUR
```

### 方案2：没有目标粒度

```text
只有5MIN
Requested = 1H
```

则：

```text
5MIN → Rollup → 1H
```

### 方案3：用户要求原始明细

```text
Requested = NATIVE
```

直接查询5分钟数据。

---

## 4.5 结果保护机制

即使规划了粒度，也建议在返回Agent前做：

```text
Result Budget Guard
```

例如：

```text
maxRows
maxChars
maxTokens
```

超过以后可以：

* 再聚合；
* 分页；
* TopN；
* 摘要；
* 交给ODI先分析。

但必须保留：

> **不能改变用户明确要求的查询语义。**

例如用户明确：

> 要全部明细

就不能静默聚合，只能分页或提示规模过大。

# 5. 建议的元模型

建议不要简单在本体属性加：

```text
granularity = 5min
```

因为同一个属性可能有多个Binding。

更合理：

```text
Property
Cell.PRBUsage
    │
    ├── aggregationSemantics = AVG
    │
    └── Binding
          │
          ├── Source A
          │    nativeGranularity = 5MIN
          │
          └── Source B
               nativeGranularity = 1H
```

即：

### 本体概念语义层

定义：

```text
Aggregation Semantics
```

### Binding / Physical Capability层

定义：

```text
Native Granularity
Supported Granularity
```

### Query Runtime

定义：

```text
Requested Granularity
Effective Granularity
```

这个分层最清晰。

# 6. 与Agent结合后的价值

这个功能实际上不是为了SQL好看，而是直接服务Agent。

没有粒度控制：

```text
5分钟数据
→ 上万行
→ LLM长上下文
→ Token膨胀
→ 注意力下降
→ 分析变慢/变错
```

有粒度规划：

```text
用户任务
↓
识别分析目标
↓
选择合适粒度
↓
OAC前置聚合
↓
高信息密度结果
↓
Agent推理
```

这符合一个很重要的原则：

> **不要把数据库能够返回的所有数据都交给LLM，而应该给LLM完成当前任务所需的最小充分事实。**
