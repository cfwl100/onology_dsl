## 1. 软件 CBS 场景本体数据流和新的分工边界

### 1.1 业务背景与目标

CBS 涉及面向运营商人员的问账、集团客户问账，以及面向经营、销售、运营、运维人员的问计、问因与辅助决策。例如：查询预付费账户数量、汇总可用优惠余额、分析套餐月活 TOP3 及原因、回答账单风险和运营建议等。问计智能体侧重 CXO 客户体验、CMO 套餐市场表现、CFO 应收账款风险等决策分析场景，业务IRB成效目标准确率90%，端到端时长5min。

**CBS 软件场景本体模型**：对象类型：144，属性总数：2896，关系总数：370，内部划分11个域，当前业务侧还在优化本体模型。

### 1.3 基线与新方案的数据流对比

[原始方案和优化方案对比](https://clouddragon.huawei.com/cloudmodeling/myspace/diagram?diagramId=3d573f06653f407ca3c3e0b022f601a0)
![原始方案和优化方案对比](https://cloudmodelingapi.tools.huawei.com/cloudmodelingdrawiosvr/d/a9ab04097ac74d6680bdab1ed2a0e70a?t=1792393267209)

**原有通用链路（OAG V1 自然语言模式，概括）**：

    用户自然语言 Query
      → OAG：实体提取与问题理解
      → ObjectType / Property / Value 召回、融合及原有精排
      → 种子投影、图关系连接
      → 返回候选本体子图
      → 下游 Agent / OAC：按业务语义裁剪并生成查询

**软件 CBS 新链路（OAG V2 entities 模式）**：

    CBS 用户原问
      → CBS Agent / Skill：意图识别、业务规则补全、问题改写、领域定位
      → OMS：查询分组及组内本体对象/属性定义
      → CBS Agent：结合组内定义做实体提取、规范化切词与对象/属性对齐
      → OAG v2：entities（extractedEntities + propertyValues）
      → OAG：仅检索 t_oag_instance_{ontology_id} 中的实例值
      → OAG：实例值证据裁剪、显式种子保护、对象/属性补全
      → OMS：提供 EnumType/values[] 权威枚举定义（不走枚举检索索引）
      → OAG：全量枚举及命中实例值填入 Property 节点
      → OAG：无向低冗余最小连通子图构建
      → OAG：nodes（Property 含 propertyEnumValues/propertyInstanceValues）/ edges / functions / actions
      → V2 响应不再包含 semanticExtensions
      → CBS Agent：结合业务规则构造、校验并执行 Cypher
      → 数据库 / 业务查询工具 → 聚合、分析、图表或答复

**关键变化**：在 CBS 软件场景，业务意图/领域判断、切词和对象/属性对齐前移到 CBS；OMS 提供权威定义，OAG V2 **entities 模式**对已对齐对象/属性不重复链接，只负责值链接、证据裁剪、属性补全及子图连接。**V2 query 模式仍继承原有自然语言提取与链接能力**，不可因软件专项配置误关闭内部 Skill 的通用功能。OMS 对本体定义及分组负责，OAG 对语义索引、值检索与子图契约负责。


### 1.4 新的分工界面

[本体子图检索流程和分工](https://clouddragon.huawei.com/cloudmodeling/myspace/diagram?diagramId=1a0bdac4d88b4a1a868b56c09ab6d9d9)

| 环节 | CBS / GDE Agent 责任 | OMS 责任 | OAG 责任 | 交付接口 / 结果 |
|---|---|---|---|---|
| 意图与分域 | 理解用户问题、业务隐含规则、选领域及 Skill，处理多轮上下文 | 提供可见分组元数据 | 不承担软件专项的业务意图推断 | 改写问题、分组条件 |
| 模型准备 | 基于领域获取定义、规范化切词；保证对象与属性对应真实本体 | 管理对象分组、分组成员、元数据版本和查询 | 维护既有本体语义索引 | group、ObjectType、Property 定义 |

| 子图精筛 | 不依赖 OAG 猜测业务隐含条件；必要时调整模型和切词 | 保证引用与权限边界 | 保护显式锚点，去除无有效证据的值候选，补全属性并连接关系 | 低冗余、可用本体子图 |
| 查询与反馈 | 生成/执行 Cypher，分析结果，回传错误用例和领域反馈 | 依据反馈修改模型、分组、定义 | 排查值检索、连接路径和结果契约问题 | 可执行查询及故障归因 |

准确性属于**共同交付**：CBS 对业务语义、意图改写和切词正确性负责；OMS 对可见本体定义与分组正确性负责；OAG 对值链接、候选过滤、关系保全和子图结构正确性负责；CBS 对 Cypher 生成与结果解释负责。不得把业务侧切词本身的错误归咎于 OAG 值检索，也不得把 OAG 关系断裂归咎于后置 Cypher 生成。

### 1.5 典型闭环与新增约束

以“查询截至当前所有预付费类型账户总数”为例：CBS 通过 OMS 获取 `Account.paymentType` 定义，并把 `Account.paymentType` 作为**显式锚点**传入；OAG **不再针对 `prepaid` 查询枚举索引**，而是在补全 `paymentType`（枚举类型）时从 OMS 获取完整的 `Prepaid / Postpaid / Hybrid` 枚举元数据，装入 Property 节点 `propertyEnumValues`；CBS 再自行依据业务问题选择 `Prepaid`，通过其 `defaultDataValue=0` 和真实物理绑定生成查询条件。**全部枚举返回不等于 OAG 已替业务选定枚举条件**，不应将所有返回枚举都转为 Cypher 条件；时间规则仍归 CBS。

另一类场景是切词包含大量“预付费”跨对象候选属性。显式锚点（例如 BonusBalanceBook.balanceAmount）不可因某个附加值未命中而删除；仅存在于 propertyValues 的冗余对象，如阈值过滤后无有效候选，才按软件专项规则剔除。

本期**平台子图验收**以“黄金对象/属性/关系标准答案 + 冗余扰动集 + V1 回归 + V2 新链路回归”闭环，覆盖中英文问法、同义词、显式锚点、冗余值、跨对象连接和无向路径；**CBS Cypher 的生成、执行和业务答案验证由 CBS 业务侧独立负责，不纳入平台准入**。时间语义独立处理：配套软件专项设计明确本期 OAG 切词/值链接不实现独立时间实体处理，不能因问句包含“截至当前”就声称平台已完成时间归一。

### 1.6 交付与验收边界

CBS 提供标准切词和黄金集并独立验收 Cypher/业务答案；OMS 验收分组、可见元数据与 revision；OAG 验收 V2 契约、实例映射、完整枚举、裁剪和子图连接。平台联合验收与具体用例见附录 A。**CBS Cypher 可执行率不计入 OAG 发布准入**。

业务 IRB 准确率目标与子图 Precision/Recall/F1 属不同指标；早期提出的“高召回、F1 90%”仅为方向，正式门槛需按黄金集确定。

## 2. OMS 本体定义和分组查询接口

### 2.1 目标、增量范围与职责

**目标**：业务 Agent 能以领域为单位加载本体定义，而非每轮把全部对象及其数千属性灌入 LLM；同时保持模型分组可管理、可交付、可追溯。解决业务Agent全量定义导致的上下文膨胀与注意力稀释问题，降低切词对不相关对象/属性的误选。

相对原有 OMS 本体管理，本期新增**分组建模与分组查询**两项核心能力，详细实现参见《ontology-group-end-to-end-design.md》。

1. **分组建模**：通过本体元数据配置与成员记录，定义 ObjectType 的领域归属，并在画布中支持分组管理及独立布局。
2. **分组查询**：OMS 开放分组列表和成员查询接口，供 CBS Agent 按业务域读取真实对象定义，再做精确切词。

这属于 OMS 权威元数据能力，不是由 OAG 临时生成“语义分组”，也不把业务用户实例值划归组。

### 2.2 分组模型概要

**OMS 分组方案首版**采用 `ontologyGroup`（组定义）和 `groupMember`（成员归属）两类记录，基于配置元数据/图库 Tag 承载，App 包按 `onto-groups/{groupName}.json` 组织；沿用现有对象、关系、权限、引用、版本与 App 生命周期。**此处首版仅指 OMS 分组方案，不等于 OAG V1 检索接口。**

| 设计项 | 约束 / 新增内容 |
|---|---|
| 分组层级 | V1 平级、单一分组体系，不设置组中组 |
| 成员类型 | 仅 ObjectType；Property、Function、Action 等通过其所属对象获取 |
| 成员归属 | 同一本体一个对象最多属于一个分组；可未分组 |
| 约束范围 | 所属当前本体的有效可见对象，不因配置成员扩大对象访问权限 |
| 身份与迁移 | group 和 groupMember 具有稳定 ID；移组更换成员记录 ID，不变更对象 ID |
| 组与画布 | 组成员归属属于元数据；组框/坐标属于画布布局，2D/3D 独立 |
| 资产生命周期 | 导入导出、App 安装/升级/回滚、并发修改、权限及审计按详细设计执行 |
| 兼容原则 | 分组仅为 OMS 建模元数据及 CBS 领域上下文；OAG V1/V2 均不增加 `groupFilter` 参数或按组召回逻辑；历史 layers 为展示兼容字段，不等价于结构分组 |

特别说明：分组只是**元数据过滤和展示边界**，不是新的业务关系边；不能把 ontologyGroup / groupMember 误作为业务 ObjectType 或用于最小连通路径。

### 2.3 分组查询契约概要

面向 CBS Agent 提供**分组列表和组成员查询两项核心只读接口**，另包含一项批量反查对象归属的支撑接口。以下 URL 沿用配套 OMS 分组首版**建议契约**，实际路径/分页须联调冻结，不能据此声称已上线：

| 能力 | 建议接口 | 业务用途 |
|---|---|---|
| 列出当前本体分组 | GET /api/v1/ontologies/{ontologyId}/groups | 获取领域编码、名称、描述、成员数与修订号，辅助选域 |
| 查询组成员 | POST /api/v1/ontologies/{ontologyId}/group/members | 按 groupId 或 groupName 获取对象定义/引用；支持分页、可见性与修订检查 |
| 批量查询归属（支撑能力） | POST /api/v1/ontologies/{ontologyId}/group-members:resolve | 已知对象 ID 时批量查询所属分组，避免逐对象 N+1 |

查询必须绑定 ontologyId、调用方权限与当前元数据 revision；禁止把不同修订版本的分组和成员拼合为一次 LLM 上下文。组内返回对象要进一步获取或包含足够的 ObjectType、Property、description 等权威定义，不能只有组名或对象 ID 就宣称可支撑切词。

**接口评审待收敛项**：配套分组详细设计第 10 章使用 data + cursor + revision 契约；第 11 章的成员接口示例又出现 RestResponse / Page / start-limit 两套分页形式。应在实现联调前统一 OMS 分组列表与成员接口的响应包装、分页方式、修订参数及错误码，不得由调用方猜测。

### 2.4 与 OAG 的分工边界（不按组检索）

**本软件场景中 OMS 分组查询的直接消费方是 CBS Agent/Skill 的领域识别与切词流程**：OMS 按权限、ontologyId 和 revision 返回指定分组的 ObjectType/Property 定义；CBS 利用这些定义生成规范化的 `entities.extractedEntities` 与 `entities.propertyValues`，然后调用 OAG V2。

**OAG 不具备也不新增按组召回/过滤功能**。V2 只根据 `entities` 所携带的对象、属性和值执行语义链接、候选裁剪和真实本体关系图的连接，不接收 `groupFilter`，不查询 OMS 分组成员，不采用 INTERNAL/EXPAND 等分组扩展模式。不同分组的实际本体关系可以构成连接路径，**不能以 CBS 切词时使用的分组边界截断 OAG 图遍历**；本体访问权限与模型有效性仍遵循既有安全和版本约束。

| 模块 | 职责 | 输出及限制 |
|---|---|---|
| OMS | 分组配置、成员归属、列表/成员查询、权限和 revision | 向 CBS 提供领域定义；分组不是 OAG 检索过滤条件 |
| CBS Agent | 使用 OMS 分组定义定位业务领域、选择真实 ObjectType/Property，生成切词结果 | 调用 V2 时只发送已有字段和结构化 `entities`，无需组 ID/名称 |
| OAG V2 | 根据传入切词进行值链接、候选裁剪、属性补全和无向子图构建 | 不依赖组归属；可以跨分组连接本体中的真实节点/关系 |
| OAG V1 | 继续原自然语言输入及历史执行逻辑 | 不受 OMS 新分组能力影响 |

**验收边界**：OMS 按组查询正确、CBS 获取组内定义正确即可满足分组专题；OAG 需验证同一 `entities` 输入在“原对象分组改变但本体关系不变”的情况下检索图结果不被错误裁剪。此前草案中的 OAG `groupFilter` / INTERNAL / EXPAND 不属于本方案接口设计或本期交付范围。

### 2.5 验收标准

| 编号 | 验收场景 | 通过条件 |
|---|---|---|
| OMS-01 | 新增、修改、删除分组及成员 | 本体归属唯一、组编码唯一、成员引用合法；移动对象不改变对象本身 ID |
| OMS-02 | App 导入导出、安装升级与回滚 | 分组配置可重放、跨 App 权属正确、旧包及未分组对象兼容 |
| OMS-03 | 查询按域定义 | CBS 可分页取得指定组全部**有权限**的 ObjectType 及所需 Property 定义；无遗漏和跨组误混 |
| OMS-04 | 权限、引用与修订一致性 | 不泄漏不可见对象，组与成员的 revision 一致；修订改变返回明确错误或重新获取 |
| OMS-05 | 大组与复杂页面 | 无 N+1 查询；游标、索引或批量加载生效；内存、分页、缓存具备上限 |
| OMS-06 | 切词收益 | 同一黄金集对比全量定义与按域定义的输入 Token、实体/属性对齐准确率、漏抽率及歧义错误；输出实测报告，不以未实测百分比替代验收 |
| OMS-07 | 分组与检索职责隔离 | OMS 分组只供 CBS 切词；在对象、属性、关系定义及 V2 `entities` 相同的前提下改变分组归属，不应导致 OAG 子图结果变化；OAG 不接收 `groupFilter` |

详细模型、DDL、元数据包、页面交互、权限、并发和接口字段，统一参见《ontology-group-end-to-end-design.md》。

## 3. OAG 本体子图检索能力增强

### 3.1 总体目标与新增能力分解

**版本决策**：10/30 软件增强参数**预置且默认开启**，内部本体子图 Skill Python 脚本与前端页面适配统一 V2；**10/30 后**增加 DCC 租户级配置并注册原预置参数，支持变更、回滚和 10/30 升级兼容。V1 虽主要供内部 Skill 使用，但当前不能断定所有消费者已清零；只有完成调用方盘点、V2 回归、灰度、监控及正式退役审批后，才可考虑下线。具体方案见 §3.7、§3.9（配置演进）、§3.10（调用迁移）。

**目标**：在 CBS 已完成对象/属性对齐的前提下，提高有效目标对象及关系召回率，减少冗余对象/属性，确保输出子图既结构连通又可供下游 Cypher 使用；同时减少不必要的 LLM 与索引调用。

本轮在原 OAG Schema/值索引和图构建能力基础上，新增以下三项演进：

1. **统一 V2 接口与前端双输入**：CBS 提供 entities.extractedEntities / propertyValues，内部 Skill 和前端仍可用 query；前端增加 Entities JSON 输入框及错误提示（§3.11）。
2. **实例值证据裁剪与 Property 双值结构**：在线值链接仅检索 t_oag_instance_{ontology_id}，属性补全从 OMS 全量取 EnumType/values[]，组装 propertyEnumValues/propertyInstanceValues；V2 删除 semanticExtensions（§3.4、§3.12）。
3. **无向低冗余最小连通子图**：图遍历不区分存储边方向，仅使用真实对象关系白名单，通过成对最短路径和 MST 式归并减少断裂与冗余。

此处“自适应裁剪”指**根据输入锚点和有效值检索证据确定性收敛**，不另设 LLM 消歧/精排阶段；“最小连通”是工程启发式/近似最小连接，并不保证任意图上的全局 Steiner 最优。

**V2 能力及兼容边界**：V2 保留 V1 query 的自然语言 ObjectType/Property 提取/链接、vector/keyword/hybrid、minimal/khop/component 和 Function/Action 功能，并支持 CBS entities，双输入时 entities 优先。**本轮明确取消 V2 Enum Value Linking，原本依赖枚举索引的召回可能变化**，须做黄金集对照；V1 直到正式退役仍保留原接口和 DTO。

| 接口 | 路径与本体 ID | 输入和能力 | 原文所列默认参数 |
|---|---|---|---|
| V1（内部 Skill 迁移前） | `/v1/onto-retrieval/{ontologyId}/subgraph/semantic-search`；ID 为 Path 参数 | query Body 必填（1～1024 字符），自然语言提取、三种召回模式和三种图策略，返回 ObjectType / Property / Relationship / Function / Action | seedRetrievalMode=vector、similarityThreshold=0.6、topk=1、graphExpansionStrategy=minimal、hopLimit=3、includeFunctions=0、includeActions=0 |
| **V2（统一入口）** | **POST `/v2/onto-retrieval/subgraph/semantic-search`；ontologyId 为 Body 必填**（1～256 字符） | query 或 entities，至少一个非空；两者都有时 entities 优先；完整继承 V1 能力，新增 RelationshipProperty、软件增强与租户级配置 | adaptiveRetrieval=1（ObjectType+Property ≤300 节点默认返回全图，否则按策略）、seedRetrievalMode=vector、similarityThreshold=0.6、topk=3、graphExpansionStrategy=minimal、hopLimit=3、includeFunctions=0、includeActions=0 |

**需联调的契约差异**：文档提供的 V1/V2 参数表均写 `topk`，但仓库现有 `ontology-platform-unified-skill/scripts/semantic_subgraph_search.py` 实际发送 `topK`，并使用 includeFunctions=1、seedRetrievalMode=hybrid 作为其默认值。迁移客户端时须明确转换 `topK → topk`、保留 Skill 所需的行为默认，不得假定 V2 后端已经接受两个拼写。正式 V2 参数表规定 `entities` 为 **JSON String（1～102400 字符）**，现有 CBS 示例却使用 JSON Object；最终线上 DTO 是否同时支持两者须实测确认，接入侧不能省略解析/序列化适配。

**来源和部署边界**：上述 V1/V2 路径、Body/Path 差异、默认值与输入优先级依据本文件此处原有的完整接口说明归纳。V1 给出了后台、网格外、DeepAgent 三种带服务前缀的访问方式；V2 提供的是逻辑 API 路径，具体环境网关前缀遵循实际部署。

### 3.2 V1/V2 能力对比及输入模式执行差异

| 维度 | V1 / 原内部 Skill | V2 query（内部 Skill 迁移） | V2 entities（CBS） |
|---|---|---|---|
| 输入 | query，ontologyId 位于 Path | query，ontologyId 位于 Body | entities，ontologyId 位于 Body；query 同传时 entities 优先 |
| 提取与链接 | 自然语言实体提取、对象/属性链接 | **必须保留原有自然语言提取与对象属性链接能力** | CBS 已对齐对象属性；可以由租户配置关闭重复提取/链接 |
| 值链接 | 原 Enum/Instance 值检索 | 仅 Instance 索引检索，query 模式仍保留 ObjectType/Property 自然语言链接 | CBS entities 用真实实例命中进行候选裁剪，枚举值只从 OMS 本体全量获取 |
| 自适应 | V1 原参数表未声明 adaptiveRetrieval | V2 默认 adaptiveRetrieval=1，可覆盖原 V1 能力 | CBS 可显式 adaptiveRetrieval=0 |
| 子图 | minimal/khop/component | 三策略均保留，最小连通图**无向默认开启** | 同左，可租户级回滚为旧图策略 |
| 返回 | 原图及扩展值结果 | 保留原图元素，Property 节点直接含 propertyEnumValues/propertyInstanceValues，移除 semanticExtensions | 同左，OMS 枚举全量返回，Instance 仅为本次检索命中 |
| 配置 | V1 保持迁移期原契约 | 10/30 query 模式服务端预置，10/30 后 DCC 租户覆盖 | 10/30 entities 增强默认开启，10/30 后注册预置参数到 DCC 并支持修改 |
| 组过滤 | 无 | 无 | OMS 只供 CBS 定义，不增加 OAG groupFilter |

**分阶段配置**：10/30 由 OAG 读取服务端预置参数，按 query/entities 输入模式隔离；不依赖 DCC。10/30 后从 DCC 根据已鉴权 tenantId + 输入模式读取覆盖项，未覆盖项继续采用 10/30 对应预置值。query 模式不能被 CBS entities 模式“关闭二次链接”的参数误伤；DCC 存储、热更新和版本功能待后续实现。

`enableObjectLinking`、`enablePropertyLinking`、`enablePropertyValueLinking`、`includeAllProperties`、`includeKeys`、`subgraph.undirected-filter` 为 **10/30 内置预置，后续按真实 Key 注册 DCC** 的参数，均不新增为请求 Body；Body 的 `adaptiveRetrieval` 等原有 V2 参数保留原语义。软件候选裁剪和 Property 类型输出如果不是独立配置 Key，不应凭空注册。

### 3.3 OAG V2 统一接口及软件场景 JSON Schema

#### 3.3.1 V2 接口路径、参数与输入模式

**统一 V2**：`POST /v2/onto-retrieval/subgraph/semantic-search`，`application/json`。**ontologyId 位于 Body 且必填**，不再采用 V1 Path 路由。**query 与 entities 至少一个非空；二者同时有值时优先 entities**，跳过 query 的实体提取。CBS 业务侧以 entities 为必备业务输入，但**不能将 entities 定为所有 V2 客户端的通用必填**。

| Body 参数 | 类型 | 必填 | 默认值 | 作用及约束 |
|---|---|---|---|---|
| ontologyId | string | **是** | 无 | 1～256 字符 |
| query | string | 条件必填 | 无 | 1～1024 字符，自然语言模式；与 entities 至少一个非空 |
| entities | **JSON String（正式表）** | 条件必填 | 无 | 1～102400 字符；CBS 业务结构见 3.3.2，和 query 至少一个非空 |
| adaptiveRetrieval | int（0/1） | 否 | **1** | 本体 ObjectType+Property ≤300 默认全量，超过按指定策略；CBS 可传 0 |
| seedRetrievalMode | string | 否 | vector | vector / keyword / hybrid |
| similarityThreshold | double | 否 | 0.6 | vector/hybrid 时生效 |
| topk | int | 否 | **3** | 文档中 V2 的正式拼写为 topk；Skill 现有 topK 需客户端适配 |
| graphExpansionStrategy | string | 否 | minimal | minimal / khop / component |
| hopLimit | int | 否 | 3 | 文档称 khop 时生效，最短路径内部限制另按算法核实 |
| includeFunctions | int（0/1） | 否 | 0 | Function 原能力保留 |
| includeActions | int（0/1） | 否 | 0 | Action 原能力保留 |

**传输格式评审点**：正式 V2 表把 entities 定义为 JSON String，CBS 现有 JSON 示例则是内嵌 Object。请求 Schema 将两种表示列为**待联调确认的候选形态**；静态 Schema 同时接受不等于后端已支持两者。建议客户端基于实际 DTO 明确序列化方式，服务端应在解析后对业务实体结构做相同校验。

**内部 Skill 的 V2 query 调用示例**：

```json
{
  "ontologyId": "<ontology-id>",
  "query": "查询设备故障及关联对象属性",
  "seedRetrievalMode": "hybrid",
  "topk": 3,
  "graphExpansionStrategy": "minimal",
  "includeFunctions": 1
}
```

#### 3.3.2 `entities` 分词结构与校验规则

| 字段 | 类型 | 必填 | 约束与职责 |
|---|---|---|---|
| `entities.extractedEntities[]` | array | 与 propertyValues 二选一有数据 | 显式已对齐的对象锚点，元素 `objectType` 必填；`properties[]` 可以省略，附件大量对象只传 objectType |
| `entities.extractedEntities[].properties[]` | array of string | 否 | 已归属 ObjectType 的本体属性，不能为空名称 |
| `entities.propertyValues[]` | array | 与 extractedEntities 二选一有数据 | 值候选分组，元素含必填 `objectType` 与 `propertyValues[]` |
| `entities.propertyValues[].propertyValues[]` | array of object | 是（分组存在时） | 每项必须有 `property` 和 `value`；`value` 非空 |
| **`property` 为空字符串** | string | 允许 | **附件实测 `"property":""`**，表达该值候选尚未确定所属属性；由值链接决定归属，不能把空串当作真实 Property ID/name |

**entities 模式校验**：解码后 `entities` 不能是空对象或两个数组均空；两输入集合的对象重复时根据归属合并并保护显式锚点。若采用正式 JSON String 传输，还须校验 1～102400 字符长度、JSON 语法及内部结构。**V2 query-only 模式不要求 entities，也不执行软件切词结构校验**。

#### 3.3.4 V2 输出结构：属性节点承载完整枚举与命中实例值

**目标接口变化**：保留 V2 的 `resultCode/resultMessage/result` 以及图的 `nodes/edges/functions/actions` 等既有容器；**移除 `result.semanticExtensions`（含 `valueMappings`）**。Property 节点的 `properties` 直接新增以下两个数组，避免再以顶层扩展结构向下游输出值信息：

| 路径 | 类型 | 来源 / 作用 |
|---|---|---|
| `result.nodes[]` | array | 保留 ObjectType、Property 等真实本体节点；仅 `label=property` 的 `properties` 装配下面两种值集合 |
| `nodes[label=property].properties.dataType` | string | 从 OMS 同一模型 revision 的 Property 定义读取，用于判定枚举类型和非枚举属性 |
| `nodes[label=property].properties.propertyEnumValues[]` | array | **全量枚举**。若 Property 对应 EnumType，从 OMS 的 EnumType/values[] 读取该属性**所有**枚举项，完整保留 `value/isDefault/defaultDataValue/description/synonyms`；不进行 Enum 索引检索、TopK 截断或相关性筛选 |
| `nodes[label=property].properties.propertyInstanceValues[]` | array | **实例命中值**。只基于 `t_oag_instance_{ontology_id}` 的检索结果，经 ObjectType + Property 归属/置信度检查，返回 `sourceValue/canonicalValue`；不从枚举字典伪造实例命中 |
| `result.propertyValuesLinks[]` | array（历史可选） | 如保留用于兼容/诊断，**仅包含实例索引链接证据**；不再包含枚举来源证据，也不能替代 Property 节点的两类值集合 |
| `result.seedNodes[]` | array（按模式） | 原显式锚点和经实例命中确认的种子信息；不根据枚举字典构造虚假的值检索命中 |
| `result.edges[]` | array | 使用原始 `sourceId/targetId/edgeType/propertyMap`，不因无向遍历改写关系方向 |
| `result.functions[]/actions[]` | array | 继承 V1 对应能力及结构 |
| **`result.semanticExtensions`** | **移除** | V2 新契约**不返回**；原来使用此结构的 CBS/Skill/前端消费者必须升级 |

**propertyEnumValues 详细定义**：

| 字段 | 类型 | 规则 |
|---|---|---|
| `value` | string | OMS 枚举规范值，例如 `Prepaid` |
| `isDefault` | string | **按本次给定样例使用 `"true"` / `"false"` 字符串**，不要在前后端静默换成 Boolean；实际 OMS 源值是 Boolean 时由 DTO 做明确序列化转换 |
| `defaultDataValue` | string | 枚举对应的默认业务数据值，如 `"0"`；不得由向量检索推断 |
| `description` | object（可选） | 中英文 `en/zh`；从 OMS 原始模型取值，缺失时不得由模型生成 |
| `synonyms` | object（可选） | 中英文同义词数组 `en[]/zh[]`，保留 OMS 定义；无同义词时可省略 |

**propertyInstanceValues 详细定义**：数组条目包含必填字符串 `sourceValue`（输入/待标准化原值）与 `canonicalValue`（实例索引匹配的规范值）。仅包含真实且满足归属与筛选条件的实例候选；返回多个候选时保留匹配关系，不在 OAG 中假定其全部为最终 Cypher 过滤条件。除非详细设计另行评审，不添加 `defaultDataValue` 或 `isDefault` 到实例值结构。

**装配规则**：枚举型 Property 即使用户查询未包含枚举关键字，也应在返回该属性节点时填充**完整** OMS 枚举表；非枚举属性 `propertyEnumValues` 为空数组。无有效实例命中的属性 `propertyInstanceValues` 为空数组；没有输入值也不扫描或全量枚举实例库。两种集合均挂在真实 Property ID 对应的节点上，同一 Property 节点按 ID 去重；枚举的源定义必须与本次查询本体 revision 一致。**当前目标 V2 响应 Schema 明确：每个 Property 节点都必须有两种数组，不适用时返回 `[]`；非 Property 节点不得携带。** Controller/DTO 应据此落地和联调。

#### 3.3.5 索引调整对输出契约的影响

原设计的 `semanticExtensions.valueMappings` 和枚举候选证据来自历史链路/回包；**本次需求明确用 Property 节点中的两类字段替换**。旧 V1 在退役前使用原有响应定义，不把新字段逆向强加给 V1。V2 属于**破坏性响应契约变更**：所有读取 `semanticExtensions.valueMappings` 的 CBS、内部 Skill、OAC 适配层、前端和批跑评测代码均需检查/升级；不能仅通过 JSON Schema 修改就声称消费者已兼容。

#### 3.3.6 JSON Schema 与协议回归边界

- **请求不变**：V2 `ontologyId` 位于 Body，`query` 与 `entities` 至少一个非空、同时传入时 `entities` 优先。前端对 `entities` 做 JSON 解析和业务结构校验，按最终联调 DTO 序列化。
- **V2 响应 Schema**：只在 Property 的 `properties` 下声明 `propertyEnumValues` / `propertyInstanceValues`；不再包含 `semanticExtensions` 定义，并明确禁止 V2 result 中继续出现旧扩展。非 Property 节点不应附带这两个集合。
- **数据准确性**：枚举以 OMS 本体定义完整性、Property/EnumType 真实绑定、`isDefault`/数据值/语言字段一致性验收；实例以检索真实命中、来源、归属、阈值与去重验收。
- **前端与客户端**：旧 `semanticExtensions` 消费逻辑必须迁移；新 JSON 数组使用统一响应解析，不允许枚举缺省直接报实例索引故障。V1 路由及其原 DTO 不受此 V2 调整影响。
- **接口待决议项**：`entities` String/Object、`topk` 字段大小写、实际 OMS EnumType 查询入口和 `isDefault` 源类型需在代码/接口评审中冻结。详细结构参见 [V2 响应 JSON Schema](./schemas/oag-software-subgraph-response.schema.json)。

### 3.4 自适应实体裁剪、种子生成、属性补全和属性类型填充

**重构后的值处理边界**：V2 接收已对齐的 `extractedEntities` 与 `propertyValues`，对 ObjectType/Property 保持原锚点逻辑；**在线值检索仅访问实例索引 `t_oag_instance_{ontology_id}`**，不执行 Enum 值召回。EnumType/values[] 是 OMS 的 Schema 元数据，进入 **Property 属性补全/响应组装** 阶段，而非检索证据融合阶段。

**候选处理规则（仅实例值可作为索引命中证据）**：

1. `extractedEntities` 中显式 ObjectType/Property 必须保留；某个值候选没有实例命中也不能删除这些显式锚点。
2. 对 `propertyValues` 的候选值按真实 ObjectType/Property 归属过滤，再从 `t_oag_instance_{ontology_id}` 执行检索。跨对象同名属性不可错挂。未知 `property:""` 也必须在真实属性归属确定后才能记作命中。
3. **枚举输入不再触发枚举值链接**：例如 `Account.paymentType=prepaid` 若只有 EnumType 中定义但实例索引没有命中，不能虚构 `ValueMapping` 或因“枚举检索失败”而推断此对象无效。业务需将必要的枚举 ObjectType/Property 放入 `extractedEntities` 作为显式锚点；纯 `propertyValues` 的枚举候选不会因 OMS 字典存在而自动变成值检索种子。
4. 仅存在于 `propertyValues` 的候选对象，若其各候选**已完成实例检索**且无有效命中，则按现有确定性裁剪策略处理；`NOT_SEARCHED`、索引超时、`ERROR/INDEX_NOT_READY` 不可当成 `NO_MATCH` 裁剪证据。
5. 对象同时在两组输入中出现时，保护显式锚点，与有效实例命中对象/属性按真实 ID 合并；最终 seedNodes = 显式锚点对象 ∪ 实例值有效链接对象，不再纳入“枚举索引命中种子”。
6. 按最终子图中保留的 ObjectType 补全真实 Property（包括主键与关系所需属性），填充来自 OMS 的 `dataType`。当 Property 关联 EnumType 时查询该枚举的完整 `values[]`，组装 `propertyEnumValues`；实例索引有效命中填入 `propertyInstanceValues`。
7. 无枚举时 `propertyEnumValues` 为空；无实例命中时 `propertyInstanceValues` 为空；响应**不输出** `semanticExtensions`。不可通过属性补全反向伪造实例召回，也不可把全部枚举理解为被用户选中的查询约束。

**Enum 属性补全要求**：OMS 查询应按 `ontologyId + revision + ObjectTypeId + PropertyId` 校验属性真实归属，结合 Property 的 EnumType 绑定获取其所有枚举值（`value/isDefault/defaultDataValue/description/synonyms`）。避免逐属性 N+1 查询，优先在一次/批量模型定义查询中带回关联 enum values；若当前 OMS API 不支持全量枚举批量获取，应在实现评审时明确接口扩展，不宣称已有。不得将枚举截断为 TopK、使用索引相似度筛选或由 LLM 猜测缺失值。

**一致性与异常**：本体修订变更时不能混用旧 Property 与新 EnumType/values[]；权限或加载故障不可悄悄替换为“无枚举”。对没有真实定义的 Property 应报告模型/绑定错误；只针对确认无枚举定义的非枚举属性返回空枚举数组。实例索引失败不能影响已成功从 OMS 获取的全量枚举定义，也不能被标为 `NO_MATCH`。

**返回体积**：全量枚举意味着返回量与所保留的 Enum Property 数及各枚举定义的基数成正比，而非与输入值个数或 TopK 成正比；须单独统计 EnumType 查询次数、枚举项总数、`nodes` 序列化大小、P95/P99 和前端渲染耗时。**不得为了性能在当前契约中静默裁剪枚举项**；若后续需要分页/大小限制，应作为新协议另行评审。

### 3.5 无向最小连通子图构建算法

名称：**OAG 无向最小连通子图构建算法**（Undirected Minimum Connecting Subgraph，UMCS）。

一句话定义：**基于本体图双向关系遍历与限定边类型，连接多个目标种子对象，通过最短路径探测及低冗余归并构建近似最小的连通子图，同时保留实际关系方向。**

与原有路径探测的新增变化：

| 项 | 历史逻辑 | 无向增强 |
|---|---|---|
| findShortestPath | 单向出边；任意边类型 | Nebula BIDIRECT / Gremlin bothE + otherV，仅 defines_relation / has_property |
| findAllPath | 单向出边；任意边类型 | 双向路径，边类型白名单，严格终点过滤作为质量回归项 |
| getSubgraph | 单向 OUT；仅 defines_relation | BOTH/both，defines_relation + has_property，TinkerPop 显式去重 |
| 归并 | 基于现有 MST 式路径收集 | 最短路径优先、无向端点匹配、并查集判断连通并提前终止 |
| 配置阶段 | V1 过渡期保持旧路径 | 10/30 V2 预置 `undirected-filter=true`；10/30 后 DCC 才可按租户 false 回退 |

**默认行为**：V2 `minimal` 最小连接默认采用无向白名单遍历，即 `subgraph.undirected-filter=true`。**10/30 版本由服务端预置实现默认开启；按租户显式设 false 的能力属于后续 DCC 版本**。V1 在过渡期保持旧图查询路径，不随 V2 默认配置改变。

**版本与配置实施状态**：当前说明书规定**10/30 服务端预置 true**；在该版本尚未具备 DCC 租户开关的前提下，不可把“按租户设置 false 回退”写为已可用。10/30 回退应通过发布/预置策略与原 V1 兼容链路评审，**后续 DCC** 才支持按租户改变 `undirected-filter` 并在线回滚。

算法流程：

    真实种子 ObjectType / Property
        → 种子对路径探测（Nebula / TinkerPop Repository）
        → 双向、边类型白名单
        → 路径按跳数排序
        → MST 式并查集归并 / 去除不必要连接
        → 补边、去重、保留原始 source / target 方向
        → 结构完整且低冗余的本体子图

**语义与实现限制**：

- “无向”仅用于**连通性判定与遍历**，不改变真实 Relationship 的方向、ID、属性及后续 Cypher 的 source/target 语义。
- 原附件给出的 MST 式贪心归并不是全局 Steiner 最优求解；规范描述为低冗余/近似最小。
- 路径必须真的抵达 dst；Gremlin repeat 通过 until 的 hopLimit 退出时，单用 emit(hasId(dst)) 仍可能把非目标终点带入结果。推荐在 repeat 后执行 hasId(dst).path()，两个分支均需回归。
- Gremlin shortest path 使用 limit(1) 不自动证明得到全局最短，需以最短路径语义一致性测试和实现策略保证。
- 双向搜索会扩大搜索空间；hopLimit、maxPaths、maxNodes、maxEdges、timeoutMs、图库请求量与回退机制必须纳入压测。
- 保留 GraphQueryResult / Path / DataFrame 原有列契约；V2 图算法配置仅在 V2 分流后生效。**即使 V2 `undirected-filter=true`，V1 也必须继续使用历史查询路径和默认配置行为**。

#### 3.5.1 分层调用与最小连接流程

| 模块 | 主要方法及职责 | 约束 |
|---|---|---|
| 编排层 `GraphSearchHelper` | `performGraphSearchOptimized → getPathInfos → computePairwiseShortestPaths` | `minimal` 选定种子对象并计算两两连接路径 |
| 图查询层 `InfinityGraphRepository` | `findShortestPath/findAllPath/getSubgraph`；Nebula、TinkerPop 双实现 | 先由调用版本分流：V1 只使用历史分支；**仅 V2** 根据 `undirectedFilter` 切换路径，DataFrame 列结构不变 |
| 算法层 `GraphSearchUtils` | `buildMstSubgraph/buildAllSubgraph`，并查集和去冗余归并 | 与具体图库解耦；属于近似最小连接，不承诺全局 Steiner 最优 |

实现概要：将种子对路径按跳数升序排序；并查集检测两端是否已连通，已连通跳过，未连通则收集 Path 中节点/边；全部种子进入同一连通分量后提前终止。最后补边、按无向端点规则匹配真实边并校验边 ID，**输出边仍保持实际 source/target 方向**。不同分量时须显式表示无法连通，不应补造关系。

| 图查询 | Nebula 新分支（示意） | TinkerPop 新分支（示意） |
|---|---|---|
| `findShortestPath` | `FIND SHORTEST PATH ... OVER defines_relation,has_property BIDIRECT YIELD path AS p` | `bothE(EDGE_DEFINES_RELATION, EDGE_HAS_PROPERTY).otherV().simplePath()` |
| `findAllPath` | `FIND ALL PATH ... OVER defines_relation,has_property BIDIRECT UPTO N STEPS YIELD path AS p` | `repeat(bothE(...).otherV().simplePath())`，受 `hopLimit` 约束 |
| `getSubgraph` | `GET SUBGRAPH N STEPS ... BOTH defines_relation,has_property` | `both(...)` 扩展，`bothE(...).dedup()` 收边 |

#### 3.5.2 图算法风险与测试

- V2 minimal **无向默认 true**；检查 Nebula BIDIRECT / Gremlin bothE、仅允许 defines_relation/has_property、原始边方向保留及低冗余连通性。
- **10/30** 验证预置 true 和两种输入模式；**后续 DCC 阶段**才验证不同租户 true/false、动态修改及回滚，不得用未来 DCC 能力卡住 10/30 交付。
- V2 Gremlin findAllPath 到达 hopLimit 却未抵达 dst 的路径必须过滤；Gremlin limit(1) 不保证最短，需代码核对和独立用例验证。
- 双向默认可能增大图库探测成本，按种子数/节点度/hopLimit 记录 Probe、P95/P99、CPU/内存并设超限保护。
- 本节为分阶段的方案约束，10/30 不代表已支持 DCC，代码实现和联调验收须分别证明。

### 3.11 前端子图检索页面：query / entities 双输入与错误提示（DC-07）

**设计目标**：现有子图检索页面保留自然语言 Query 输入框，并新增 **Entities JSON 多行输入框**。两个输入均通过统一的 V2 接口检索，不再使用 V1 Path 路由；支持单独 query、单独 entities、同时填写，两者都非空时 **entities 优先**，两个均空时不可提交。

| 页面区域 | 控件与数据 | 交互及校验要求 |
|---|---|---|
| 请求配置 | ontologyId、topk、seedRetrievalMode、graphExpansionStrategy 等原有控件 | V2 使用 Body ontologyId，保留原 query-only 的参数能力 |
| 自然语言 | Query 文本框 | 输入自然语言可以单独检索，不强制填写 entities |
| 结构化输入 | **Entities JSON 多行编辑框**，支持粘贴、清空、格式化/校验 | 编辑器输入内部 entities 结构；如果用户粘贴完整请求对象，应提示并提取其中 entities，不允许拼成 entities.entities |
| 双输入 | 页面提示“本次实际查询模式：Query / Entities” | 两者同时有效时按 entities 查询；若 entities JSON 错误，**不得静默退化到 query** |
| 提交 / 状态 | 查询、清空、加载中、取消/防重复点击 | 只有至少一个有效输入且没有本地错误才发送请求 |
| 结果 | 现有 nodes/edges 图及 Property 详情 | 枚举型 Property 展示完整 propertyEnumValues，实例值展示 propertyInstanceValues；**移除从 semanticExtensions 渲染值映射的旧逻辑** |

**输入转换规则**：前端先对编辑器内容 JSON.parse，再校验 extractedEntities / propertyValues 的结构和至少一项非空；property 允许空字符串表示待归属，value 必须非空。正式 V2 参数表将 entities 定为 JSON String，CBS 示例却是 Object：HTTP 发送时按联调确定的 Controller/DTO 做 JSON.stringify 或发送 Object，**不得从前端自行假定服务端两者皆支持**。ontologyId 必填，query 长度和其他参数遵守 V2 请求 Schema。

**前端错误提示与操作建议**：

| 场景 | 提示文本示例 | 校验与处理 |
|---|---|---|
| query 与 entities 同时为空 | “请输入自然语言问题或 Entities JSON。” | 本地阻止请求 |
| JSON 语法错误 | “Entities JSON 格式不正确，请检查引号、括号和逗号。” | 标示错误位置，不自动回落到 query |
| JSON 结构错误 | “Entities 至少包含一组有效对象或属性值。” | 识别 objectType、propertyValues 等字段，标示问题路径 |
| 输入超过限制 / 参数不合法 | “输入长度或检索参数不符合要求。” | 在输入框提示对应字段 |
| 鉴权失败 / 本体无权限 | “没有该本体的访问权限，请检查授权。” | 不泄露内部详情 |
| 模型不存在 / revision 已变化 | “本体定义不存在或已更新，请刷新后重试。” | 可重新加载模型 |
| 正常空结果 | “未找到匹配子图，可调整查询条件。” | 作为空结果，不伪装成服务器异常 |
| 索引异常 / OMS EnumType 读取失败 / 服务超时 | “检索服务暂时不可用，请稍后再试。” | 展示可用的 requestId/traceId；不输出后台堆栈 |
| V2 返回格式与页面不兼容 | “子图结果解析失败，请检查接口版本。” | 不回退到 semanticExtensions 猜测旧值 |

具体错误码、HTTP 状态和 resultCode/resultMessage 的对应关系以服务端接口契约为准，**本设计只给用户可理解的提示类别，不发明业务错误码**。区分校验失败、无结果、服务端故障、网络失败和超时；支持受控的诊断 ID，避免把敏感业务值、认证信息或完整堆栈显示给用户。

**页面验收**：query-only、entities-only、双输入优先级、JSON 解析/结构/长度错误、无结果和服务端超时、Enum Property 全量展开、Instance Property 值对展示，以及移除 semanticExtensions 后的前端兼容性。该节属于页面设计，不表示前端代码已修改。

### 3.12 索引构建与在线检索调整：只保留实例值索引（DC-08）

**对原 OAG 索引方案的覆盖范围**：原设计用 t_oag_{ontology_id} 检索 ObjectType/Property，用 t_oag_enum_{ontology_id} 检索 Enum Value，用 t_oag_instance_{ontology_id} 检索 Instance Value。本轮**仅取消 Enum Value 检索索引与 V2 扩展值返回**；Schema 检索和 OMS 枚举本体定义继续保留。

| 对象与能力 | 原方案 | 本次变更 |
|---|---|---|
| t_oag_{ontology_id} | ObjectType / Property Schema 索引 | **保留**，V2 query 的自然语言对象/属性召回不受影响 |
| t_oag_enum_{ontology_id} | Enum Value 向量/全文索引、同义词链接 | **停止新建、重建、增量写入、在线查询和 Enum Value Linking** |
| t_oag_instance_{ontology_id} | Instance Value 向量/关键词检索 | **保留为唯一在线 Value Linking 索引**，继续按 ObjectType/Property 限定与阈值判定 |
| OMS EnumType/values[] | 静态枚举定义 | **保留为唯一权威枚举来源**，属性补全时按 Property → EnumType 绑定查询全部值 |
| V2 值返回 | valueLinks、semanticExtensions 等扩展 | Property.properties.propertyEnumValues / propertyInstanceValues 两种数组，**V2 去除 semanticExtensions** |

**索引构建策略**：

1. 本体 Schema 的 t_oag_{ontology_id} 保留。OAG 构建流程不再生成 t_oag_enum_{ontology_id} 表、Enum 文档、Enum embedding 或相关全文索引。
2. EnumType/values[] 更新时只更新 OMS 权威定义与版本缓存，不再生成 Enum UPSERT/DELETE 索引任务；原 Enum 索引 Verify/Publish、重建及调度分支需跳过，**不应因为枚举表不存在而误判失败**。
3. Instance Value 索引 t_oag_instance_{ontology_id} 继续进行建立、增量更新和查询；ObjectTypeId + PropertyId 归属校验、幂等键、OpenSearch/GaussVector 物理实现沿用原实例值索引设计。
4. **存量表处置**：目标架构不再使用 t_oag_enum_{ontology_id}；现网存量枚举表先停读停写，清理前盘点后台任务、消费者、回退依赖。**物理 DROP 需要迁移/回滚审批，不能在本需求文档中直接安排无保护删除**。

**在线处理流程**：

```text
V2 query / entities → ObjectType/Property 显式或语义锚点
  → 仅 t_oag_instance_{ontology_id} 进行 Instance Value Linking
  → 有效实例值参与 propertyValues-only 的证据裁剪与种子归并
  → 无向最小连通子图 → 最终保留 ObjectType/Property
  → 批量查询 OMS 同版本 Property / EnumType / values[]
     ├─ enum Property：完整填充 propertyEnumValues[]（无 TopK）
     └─ 非 enum Property：propertyEnumValues=[]
  → 实例有效命中填入 propertyInstanceValues[]
  → 返回 nodes/edges/functions/actions 等（不返回 semanticExtensions）
```

**重要行为变化**：取消 Enum Value Linking 后，用户只输入枚举原值时不再产生枚举索引命中的种子，**可能降低原枚举查询的 Recall**。CBS 必须提供对应的 ObjectType/Property 显式锚点；V2 query 可以继续检索 ObjectType/Property Schema，但不得暗中通过 t_oag_enum 找回值。不能把“OMS 中存在枚举定义”等同于“检索出了实例值”。如果需要按值在枚举中选定一项，那属于 CBS 的业务语义选择，而非 OAG 的枚举索引链接。

**OMS 全量值获取与性能**：按 ontologyId、revision、ObjectTypeId、PropertyId 验证关联，批量获取所选 Property 的 EnumType 及全部 values[]，保留 value、isDefault、defaultDataValue、description、synonyms；避免按每个属性单独查询造成 N+1。模型/绑定读取失败不得当作“无枚举”并静默返回空列表。返回体积、枚举项数、OMS 批量加载 P95 和前端列表渲染纳入性能专题；**不能因 TopK 或相似度阈值截断全量枚举**。

**兼容与实施限制**：V2 不再返回 semanticExtensions，CBS、Skill、前端和评测工具必须升级；V1 仍在过渡期保留原 DTO。本说明书的调整相对于原通用 OAG 设计属于**V2 定向覆盖**，不会直接修改其他产品依赖的原始文档或服务代码；真正删除物理索引、修改 OMS 查询与落地版本由相关负责人评审确定。

### A.4 下一步重点：并发性能测试场景

**本节不作为本期新增功能承诺**。重点关注高并发下 OAG 子图检索的 P50/P95/P99、TPS/QPS、错误率、CPU/内存/GC、线程/连接池排队和图库探测放大。第 4 章来自 PPT 的 44 TPS/66 QPS、87 TPS/131 QPS 尚属估算，且 200 万用户档 (38+10)×1.5=72 TPS 与 PPT 87 TPS 不一致；负载定稿前须统一口径。

测试顺序：单用户/单请求阶段基线 → 并发用户与实际到达 TPS 分级 → 不同 Seed/节点度/hopLimit/Value 组合 → 混合长稳态 → 峰值突增 → 索引、图库异常及恢复。客户端并发线程数不等于实际 TPS，应同时记录服务端到达率、成功吞吐及分位耗时。

|---|---|---|---|
