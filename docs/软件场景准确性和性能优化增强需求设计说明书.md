## 1. 软件 CBS 场景本体数据流和新的分工边界

### 1.1 业务背景与目标

CBS 涉及面向运营商人员的问账、集团客户问账，以及面向经营、销售、运营、运维人员的问计、问因与辅助决策。例如：查询预付费账户数量、汇总可用优惠余额、分析套餐月活 TOP3 及原因、回答账单风险和运营建议等。问计智能体侧重 CXO 客户体验、CMO 套餐市场表现、CFO 应收账款风险等决策分析场景，业务IRB成效目标准确率90%，端到端时长5min。

**CBS 软件场景本体模型**：对象类型：144，属性总数：2896，关系总数：370，内部划分11个域，当前业务侧还在优化本体模型。

### 1.3 原有与新增数据流对比

[原始方案和优化方案对比](https://clouddragon.huawei.com/cloudmodeling/myspace/diagram?diagramId=3d573f06653f407ca3c3e0b022f601a0)
![原始方案和优化方案对比](https://cloudmodelingapi.tools.huawei.com/cloudmodelingdrawiosvr/d/a9ab04097ac74d6680bdab1ed2a0e70a?t=1792393267209)

**原有通用链路（概括）**：

    自然语言 Query（结构化）
      → OAG Entity Extraction / Query Understanding
      → ObjectType / Property / Value 混合召回、融合、精排
      → 种子投影、子图构建
      → 候选本体子图
      → 下游 Agent / OAC 再次推理裁剪及查询生成

**软件 CBS 新链路**：

    CBS 用户原问
      → CBS Agent / Skill：意图识别、业务规则补全、问题改写、领域定位
      → OMS：查询分组及组内本体对象/属性定义
      → CBS Agent：结合组内定义做实体提取、规范化切词与对象/属性对齐
      → OAG v2：entities（extractedEntities + propertyValues）
      → OAG：限定对象/属性范围的 Enum / Instance 值混合检索
      → OAG：有效召回判定、冗余候选裁剪、种子并集与属性补全
      → OAG：无向低冗余最小连通子图构建
      → OAG：nodes / edges / functions / actions + 值映射语义扩展
      → CBS Agent：结合业务规则构造、校验并执行 Cypher
      → 数据库 / 业务查询工具 → 聚合、分析、图表或答复

关键变化：**切词与对象、属性对齐前移到业务侧，OAG 软件专项链路不再对这些已对齐的对象/属性重复做语义链接**；平台仍负责真实值链接、图结构的正确性及其输出契约。模型定义、分组和索引完整性由 OMS/OAG 共同保证。

准确性属于**共同交付**：CBS 对业务语义、意图改写和切词正确性负责；OMS 对可见本体定义与分组正确性负责；OAG 对值链接、候选过滤、关系保全和子图结构正确性负责；CBS 对 Cypher 生成与结果解释负责。不得把业务侧切词本身的错误归咎于 OAG 值检索，也不得把 OAG 关系断裂归咎于后置 Cypher 生成。

### 1.5 典型闭环与新增约束

以“查询截至当前所有预付费类型账户总数”为例：CBS 按组获取 Account / paymentType 定义，切词为 extractedEntities 中 Account.paymentType 及 propertyValues 中 Account.paymentType=prepaid；OAG 在归属限定下得到 canonicalValue=Prepaid、defaultDataValue=0，并返回 Account、所需属性及语义映射；CBS 根据真实物理数据绑定生成类似 Account.paymentType='0' 的 Cypher 过滤条件。这里数据值 0 取自真实枚举映射，不应由 LLM 推测。

另一类场景是切词包含大量“预付费”跨对象候选属性。显式锚点（例如 BonusBalanceBook.balanceAmount）不可因某个附加值未命中而删除；仅存在于 propertyValues 的冗余对象，如阈值过滤后无有效候选，才按软件专项规则剔除。

本期**平台子图验收**以“黄金对象/属性/关系标准答案 + 冗余扰动集 + V1 回归 + V2 新链路回归”闭环，覆盖中英文问法、同义词、显式锚点、冗余值、跨对象连接和无向路径；**CBS Cypher 的生成、执行和业务答案验证由 CBS 业务侧独立负责，不纳入平台准入**。时间语义独立处理：配套软件专项设计明确本期 OAG 切词/值链接不实现独立时间实体处理，不能因问句包含“截至当前”就声称平台已完成时间归一。

### 1.6 总体交付与验收边界

- **CBS**：业务问题改写、领域定位、切词结果与 OMS 当前本体定义一致；基于返回子图改进 Cypher，并提供黄金/全量用例。
- **OMS**：支持分组建模、生命周期管理、按组稳定获取可见的对象/属性定义及修订号。
- **OAG**：新增软件结构化入口及可开关流程；值检索、候选裁剪、属性补全、无向图连接可测可回滚；保持存量通用 OAG 请求的行为。
- **平台联合验收**：OMS/CBS 提供权威本体定义和标准切词，OAG 验证值归属、对象/属性/关系召回和精度、V1 兼容与 V2 子图结构；下一阶段另做并发耗时和资源摸底。**CBS Cypher 可执行率由业务侧自行验收**。PPT 中“高 Recall、F1 90%”为目标方向，指标口径、样本范围和正式门槛须先冻结，不作为已达成结论。

## 2. OMS 本体定义和分组查询接口

### 2.1 目标、增量范围与职责

**目标**：业务 Agent 能以领域为单位加载本体定义，而非每轮把全部对象及其数千属性灌入 LLM；同时保持模型分组可管理、可交付、可追溯。解决业务Agent全量定义导致的上下文膨胀与注意力稀释问题，降低切词对不相关对象/属性的误选。

相对原有本体管理能力，本期新增两项能力：
设计文档：《ontology-group-end-to-end-design.md》

1. **分组建模**：通过本体元数据配置与成员记录，定义 ObjectType 的领域归属，并在画布中支持分组管理及独立布局。
2. **分组查询**：OMS 开放分组列表和成员查询接口，供 CBS Agent 按业务域读取真实对象定义，再做精确切词。

这属于 OMS 权威元数据能力，不是由 OAG 临时生成“语义分组”，也不把业务用户实例值划归组。

### 2.2 分组模型概要

V1 采用两个记录类型：ontologyGroup（组定义）和 groupMember（组成员归属），基于配置元数据/图库 Tag 记录承载，App 包中采用 onto-groups/{groupName}.json 组织。沿用现有对象、关系、权限、引用、版本以及 App 安装升级机制。

| 设计项 | 约束 / 新增内容 |
|---|---|
| 分组层级 | V1 平级、单一分组体系，不设置组中组 |
| 成员类型 | 仅 ObjectType；Property、Function、Action 等通过其所属对象获取 |
| 成员归属 | 同一本体一个对象最多属于一个分组；可未分组 |
| 约束范围 | 所属当前本体的有效可见对象，不因配置成员扩大对象访问权限 |
| 身份与迁移 | group 和 groupMember 具有稳定 ID；移组更换成员记录 ID，不变更对象 ID |
| 组与画布 | 组成员归属属于元数据；组框/坐标属于画布布局，2D/3D 独立 |
| 资产生命周期 | 导入导出、App 安装/升级/回滚、并发修改、权限及审计按详细设计执行 |
| 兼容原则 | 分组仅为 OMS 建模元数据及 CBS 领域上下文；OAG V1/V2 均不增加 `groupFilter` 参数或按组召回逻辑；历史 layers 为展示兼容字段，不等价于结构分组 |

特别说明：分组只是**元数据过滤和展示边界**，不是新的业务关系边；不能把 ontologyGroup / groupMember 误作为业务 ObjectType 或用于最小连通路径。

### 2.3 分组查询契约概要

面向 CBS Agent 建议形成两类只读能力（URL 沿用配套 V1 设计中的建议资源契约，实际网关前缀以集成为准）：

| 能力 | 建议接口 | 业务用途 |
|---|---|---|
| 列出当前本体分组 | GET /api/v1/ontologies/{ontologyId}/groups | 获取领域编码、名称、描述、成员数与修订号，辅助选域 |
| 查询组成员 | POST /api/v1/ontologies/{ontologyId}/group/members | 按 groupId 或 groupName 获取对象定义/引用；支持分页、可见性与修订检查 |
| 批量查询归属（支撑能力） | POST /api/v1/ontologies/{ontologyId}/group-members:resolve | 已知对象 ID 时批量查询所属分组，避免逐对象 N+1 |

查询必须绑定 ontologyId、调用方权限与当前元数据 revision；禁止把不同修订版本的分组和成员拼合为一次 LLM 上下文。组内返回对象要进一步获取或包含足够的 ObjectType、Property、description 等权威定义，不能只有组名或对象 ID 就宣称可支撑切词。

**接口评审待收敛项**：配套分组详细设计第 10 章使用 data + cursor + revision 契约；第 11 章的成员接口示例又出现 RestResponse / Page / start-limit 两套分页形式。应在实现联调前统一 OMS 分组列表与成员接口的响应包装、分页方式、修订参数及错误码，不得由调用方猜测。

### 2.4 与 OAG 的分工边界（不按组检索）

**OMS 分组查询的唯一消费者是 CBS Agent/Skill 的领域识别与切词流程**：OMS 按权限、ontologyId 和 revision 返回指定分组的 ObjectType/Property 定义；CBS 利用这些定义生成规范化的 `entities.extractedEntities` 与 `entities.propertyValues`，然后调用 OAG V2。

**OAG 不具备也不新增按组召回/过滤功能**。V2 只根据 `entities` 所携带的对象、属性和值执行语义链接、候选裁剪和真实本体关系图的连接，不接收 `groupFilter`，不查询 OMS 分组成员，不采用 INTERNAL/EXPAND 等分组扩展模式。不同分组的实际本体关系可以构成连接路径，**不能以 CBS 切词时使用的分组边界截断 OAG 图遍历**；本体访问权限与模型有效性仍遵循既有安全和版本约束。

| 模块 | 职责 | 输出及限制 |
|---|---|---|
| OMS | 分组配置、成员归属、列表/成员查询、权限和 revision | 向 CBS 提供领域定义；分组不是 OAG 检索过滤条件 |
| CBS Agent | 使用 OMS 分组定义定位业务领域、选择真实 ObjectType/Property，生成切词结果 | 调用 V2 时只发送已有字段和结构化 `entities`，无需组 ID/名称 |
| OAG V2 | 根据传入切词进行值链接、候选裁剪、属性补全和无向子图构建 | 不依赖组归属；可以跨分组连接本体中的真实节点/关系 |
| OAG V1 | 继续原自然语言输入及历史执行逻辑 | 不受 OMS 新分组能力影响 |

**验收边界**：OMS 按组查询正确、CBS 获取组内定义正确即可满足分组专题；OAG 需验证同一 `entities` 输入在“原对象分组改变但本体关系不变”的情况下检索图结果不被错误裁剪。此前草案中的 OAG `groupFilter` / INTERNAL / EXPAND 不属于本方案接口设计或本期交付范围。

### 2.5 验收标准

| 编号 | 验收场景 | 通过条件 |
|---|---|---|
| OMS-01 | 新增、修改、删除分组及成员 | 本体归属唯一、组编码唯一、成员引用合法；移动对象不改变对象本身 ID |
| OMS-02 | App 导入导出、安装升级与回滚 | 分组配置可重放、跨 App 权属正确、旧包及未分组对象兼容 |
| OMS-03 | 查询按域定义 | CBS 可分页取得指定组全部**有权限**的 ObjectType 及所需 Property 定义；无遗漏和跨组误混 |
| OMS-04 | 权限、引用与修订一致性 | 不泄漏不可见对象，组与成员的 revision 一致；修订改变返回明确错误或重新获取 |
| OMS-05 | 大组与复杂页面 | 无 N+1 查询；游标、索引或批量加载生效；内存、分页、缓存具备上限 |
| OMS-06 | 切词收益 | 同一黄金集对比全量定义与按域定义的输入 Token、实体/属性对齐准确率、漏抽率及歧义错误；输出实测报告，不以未实测百分比替代验收 |
| OMS-07 | 分组与检索职责隔离 | OMS 分组只供 CBS 切词；在对象、属性、关系定义及 V2 `entities` 相同的前提下改变分组归属，不应导致 OAG 子图结果变化；OAG 不接收 `groupFilter` |

详细模型、DDL、元数据包、页面交互、权限、并发和接口字段，统一参见《ontology-group-end-to-end-design.md》。

## 3. OAG 本体子图检索能力增强

### 3.1 总体目标与新增能力分解

**版本决策**：10/30 软件增强参数**预置且默认开启**，内部本体子图 Skill Python 脚本与前端页面适配统一 V2；**10/30 后**增加 DCC 租户级配置并注册原预置参数，支持变更、回滚和 10/30 升级兼容。V1 虽主要供内部 Skill 使用，但当前不能断定所有消费者已清零；只有完成调用方盘点、V2 回归、灰度、监控及正式退役审批后，才可考虑下线。具体方案见 §3.5.2、§3.7、§3.9。

**目标**：在 CBS 已完成对象/属性对齐的前提下，提高有效目标对象及关系召回率，减少冗余对象/属性，确保输出子图既结构连通又可供下游 Cypher 使用；同时减少不必要的 LLM 与索引调用。

本期围绕原有 OAG 原有的检索、值索引及图构建能力，补充三类软件专项能力：

1. **结构化切词接口 v2**：CBS 提供 entities.extractedEntities 和 entities.propertyValues；软件专项可绕过通用对象/属性提取与链接，执行归属限定的值检索。
2. **候选收敛、属性补全与属性类型填充**：基于枚举/实例值有效召回生成种子、裁剪非显式冗余候选，并补齐保留对象的真实属性和 `dataType`。
3. **无向低冗余最小连通子图**：图遍历不区分存储边方向，仅使用真实对象关系白名单，通过成对最短路径和 MST 式归并减少断裂与冗余。

此处“自适应裁剪”指**根据输入锚点和有效值检索证据确定性收敛**，不另设 LLM 消歧/精排阶段；“最小连通”是工程启发式/近似最小连接，并不保证任意图上的全局 Steiner 最优。

**V2 能力覆盖与内部 Skill 迁移原则**：V2 是 V1 的能力超集，不是只提供 CBS entities 的接口。V1 的 query 自然语言提取、ObjectType/Property 语义链接、vector/keyword/hybrid、minimal/khop/component、Function/Action 返回能力均须在 V2 的 **query 模式**保留。V2 还支持 CBS 的 entities 模式，**query / entities 至少一个非空；两者都提供时优先使用 entities**。内部本体 Skill 可迁移到 V2 query 模式，新增增强能力由配置中心的租户级参数控制。

| 接口 | 路径与本体 ID | 输入和能力 | 原文所列默认参数 |
|---|---|---|---|
| V1（内部 Skill 迁移前） | `/v1/onto-retrieval/{ontologyId}/subgraph/semantic-search`；ID 为 Path 参数 | query Body 必填（1～1024 字符），自然语言提取、三种召回模式和三种图策略，返回 ObjectType / Property / Relationship / Function / Action | seedRetrievalMode=vector、similarityThreshold=0.6、topk=1、graphExpansionStrategy=minimal、hopLimit=3、includeFunctions=0、includeActions=0 |
| **V2（统一入口）** | **POST `/v2/onto-retrieval/subgraph/semantic-search`；ontologyId 为 Body 必填**（1～256 字符） | query 或 entities，至少一个非空；两者都有时 entities 优先；完整继承 V1 能力，新增 RelationshipProperty、软件增强与租户级配置 | adaptiveRetrieval=1（ObjectType+Property ≤300 节点默认返回全图，否则按策略）、seedRetrievalMode=vector、similarityThreshold=0.6、topk=3、graphExpansionStrategy=minimal、hopLimit=3、includeFunctions=0、includeActions=0 |

**需联调的契约差异**：文档提供的 V1/V2 参数表均写 `topk`，但仓库现有 `ontology-platform-unified-skill/scripts/semantic_subgraph_search.py` 实际发送 `topK`，并使用 includeFunctions=1、seedRetrievalMode=hybrid 作为其默认值。迁移客户端时须明确转换 `topK → topk`、保留 Skill 所需的行为默认，不得假定 V2 后端已经接受两个拼写。正式 V2 参数表规定 `entities` 为 **JSON String（1～102400 字符）**，现有 CBS 示例却使用 JSON Object；最终线上 DTO 是否同时支持两者须实测确认，接入侧不能省略解析/序列化适配。

**来源和部署边界**：上述 V1/V2 路径、Body/Path 差异、默认值与输入优先级依据本文件此处原有的完整接口说明归纳。V1 给出了后台、网格外、DeepAgent 三种带服务前缀的访问方式；V2 提供的是逻辑 API 路径，具体环境网关前缀遵循实际部署。

### 3.2 V1 能力继承、V2 双输入与租户级配置差异

| 维度 | V1 / 原内部 Skill | V2 query（内部 Skill 迁移） | V2 entities（CBS） |
|---|---|---|---|
| 输入 | query，ontologyId 位于 Path | query，ontologyId 位于 Body | entities，ontologyId 位于 Body；query 同传时 entities 优先 |
| 提取与链接 | 自然语言实体提取、对象/属性链接 | **必须保留原有自然语言提取与对象属性链接能力** | CBS 已对齐对象属性；可以由租户配置关闭重复提取/链接 |
| 值链接 | 原基线索引及链接 | 保留原有值检索能力 | 对候选值做真实归属限定与证据驱动的裁剪 |
| 自适应 | V1 原参数表未声明 adaptiveRetrieval | V2 默认 adaptiveRetrieval=1，可覆盖原 V1 能力 | CBS 可显式 adaptiveRetrieval=0 |
| 子图 | minimal/khop/component | 三策略均保留，最小连通图**无向默认开启** | 同左，可租户级回滚为旧图策略 |
| 返回 | ObjectType、Property、Relationship、Function、Action | **不得丢失任何 V1 元素/功能**；V2 支持 RelationshipProperty | 根据配置增加值语义扩展、属性补全与 dataType |
| 配置 | V1 保持迁移期原契约 | 10/30 query 模式服务端预置，10/30 后 DCC 租户覆盖 | 10/30 entities 增强默认开启，10/30 后注册预置参数到 DCC 并支持修改 |
| 组过滤 | 无 | 无 | OMS 只供 CBS 定义，不增加 OAG groupFilter |

**分阶段配置**：10/30 由 OAG 读取服务端预置参数，按 query/entities 输入模式隔离；不依赖 DCC。10/30 后从 DCC 根据已鉴权 tenantId + 输入模式读取覆盖项，未覆盖项继续采用 10/30 对应预置值。query 模式不能被 CBS entities 模式“关闭二次链接”的参数误伤；DCC 存储、热更新和版本功能待后续实现。

`enableObjectLinking`、`enablePropertyLinking`、`enablePropertyValueLinking`、`includeAllProperties`、`includeKeys`、`subgraph.undirected-filter` 为 **10/30 内置预置，后续按真实 Key 注册 DCC** 的参数，均不新增为请求 Body；Body 的 `adaptiveRetrieval` 等原有 V2 参数保留原语义。软件候选裁剪和 Property 类型输出如果不是独立配置 Key，不应凭空注册。

### 3.3 软件场景语义子图检索输入/输出及 JSON Schema

#### 3.3.1 V2 接口路径、参数与输入模式

**统一 V2**：`POST /v2/onto-retrieval/subgraph/semantic-search`，`application/json`。**ontologyId 位于 Body 且必填**，不再采用 V1 Path 路由。**query 与 entities 至少一个非空；二者同时有值时优先 entities**，跳过 query 的实体提取。CBS 业务侧以 entities 为必备业务输入，但**不能将 entities 定为所有 V2 客户端的通用必填**。

| Body 参数 | 类型 | 必填 | 默认值 | 作用及约束 |
|---|---|---|---|---|
| ontologyId | string | **是** | 无 | 1～256 字符 |
| query | string | 条件必填 | 无 | 1～1024 字符，自然语言模式；与 entities 至少一个非空 |
| entities | **JSON String（正式表）** | 条件必填 | 无 | 1～102400 字符；CBS 业务结构见 3.3.2，和 query 至少一个非空 |
| adaptiveRetrieval | int（0/1） | 否 | **1** | 本体 ObjectType+Property ≤300 默认全量，超过按指定策略；CBS 可传 0 |
| seedRetrievalMode | string | 否 | vector | vector / keyword / hybrid |
| similarityThreshold | double | 否 | 0.6 | vector/hybrid 时生效 |
| topk | int | 否 | **3** | 文档中 V2 的正式拼写为 topk；Skill 现有 topK 需客户端适配 |
| graphExpansionStrategy | string | 否 | minimal | minimal / khop / component |
| hopLimit | int | 否 | 3 | 文档称 khop 时生效，最短路径内部限制另按算法核实 |
| includeFunctions | int（0/1） | 否 | 0 | Function 原能力保留 |
| includeActions | int（0/1） | 否 | 0 | Action 原能力保留 |

**传输格式评审点**：正式 V2 表把 entities 定义为 JSON String，CBS 现有 JSON 示例则是内嵌 Object。请求 Schema 将两种表示列为**待联调确认的候选形态**；静态 Schema 同时接受不等于后端已支持两者。建议客户端基于实际 DTO 明确序列化方式，服务端应在解析后对业务实体结构做相同校验。

**内部 Skill 的 V2 query 调用示例**：

```json
{
  "ontologyId": "<ontology-id>",
  "query": "查询设备故障及关联对象属性",
  "seedRetrievalMode": "hybrid",
  "topk": 3,
  "graphExpansionStrategy": "minimal",
  "includeFunctions": 1
}
```

#### 3.3.2 `entities` 分词结构与校验规则

| 字段 | 类型 | 必填 | 约束与职责 |
|---|---|---|---|
| `entities.extractedEntities[]` | array | 与 propertyValues 二选一有数据 | 显式已对齐的对象锚点，元素 `objectType` 必填；`properties[]` 可以省略，附件大量对象只传 objectType |
| `entities.extractedEntities[].properties[]` | array of string | 否 | 已归属 ObjectType 的本体属性，不能为空名称 |
| `entities.propertyValues[]` | array | 与 extractedEntities 二选一有数据 | 值候选分组，元素含必填 `objectType` 与 `propertyValues[]` |
| `entities.propertyValues[].propertyValues[]` | array of object | 是（分组存在时） | 每项必须有 `property` 和 `value`；`value` 非空 |
| **`property` 为空字符串** | string | 允许 | **附件实测 `"property":""`**，表达该值候选尚未确定所属属性；由值链接决定归属，不能把空串当作真实 Property ID/name |

**entities 模式校验**：解码后 `entities` 不能是空对象或两个数组均空；两输入集合的对象重复时根据归属合并并保护显式锚点。若采用正式 JSON String 传输，还须校验 1～102400 字符长度、JSON 语法及内部结构。**V2 query-only 模式不要求 entities，也不执行软件切词结构校验**。

#### 3.3.4 输出结构与附件兼容性

**V2 响应覆盖 V1 的 ObjectType / Property / Relationship / Function / Action 能力**，并支持 V2 正式定义中的 RelationshipProperty。`resultCode`、`resultMessage`、`result.nodes/edges/functions/actions` 等既有结构保留；根据租户配置与有效输入模式，可额外包含 seedNodes、propertyValuesLinks、semanticExtensions 及 Property 的 dataType。**query-only 模式不强制输出 CBS 专用值映射**；V1 在迁移过渡期仍保持原 DTO。

| 返回路径 | 类型 | 附件中的结构与语义 |
|---|---|---|
| `result.seedNodes[]` | array | `sourceObjectType`、`targetObjectTypes[]`，后者含 `name/id/score/propertyLinks/descriptionZh/descriptionEn/synonyms`；附件有相同对象的重复记录和 `id:""`，Schema 不擅自消重或禁止空 ID |
| `result.propertyValuesLinks[]` | array | `sourceObjectType`、`sourceObjectTypeId`、`valuesLinks[]`，值归属层含 `sourceProperty`、`sourcePropertyId`、`sourceValue`、`valuesMapping[]`（`canonicalValue/defaultDataValue/score`） |
| `result.nodes[]` | array | 容器沿用 V1；**仅 V2 `label=property` 节点允许/填充 `properties.dataType`**（来自 OMS Property 定义）；V1 属性集合不新增此字段。`display`、`description` 等可能是包含 JSON 文本的字符串 |
| `result.edges[]` | array | `sourceId`、`targetId`、`edgeType`、`propertyMap`；保留原始有向关系。`junctionConfig` 可为 JSON 字符串 |
| `result.functions[]` / `actions[]` | array | 附件均为 `[]`；非空元素 DTO 不能从样例证明，输出 Schema 仅对其采用开放对象兼容形态 |
| `result.semanticExtensions.valueMappings[]` | array | **附件实测是扁平字段** `propertyName/objectTypeName/sourceValue/canonicalValue/defaultDataValue/dataType`，不是先前讨论的嵌套对象引用 |

> 输出注意：附件中 `FACEBOOK` 可对应 `Voice`、`Subscriber Group Billing` 等多个候选，`FIFA World Cup` 也可召回多种属性。**这是检索候选的实际回包，不等于这些候选在业务语义上正确**。下游必须依靠置信门槛、归属校验及裁剪后的结果消费，不能将每项 valueMapping 都当作确定性 Cypher 条件。

**V2 Property 节点新增数据类型字段（目标协议示意，不代表附件已经出现相同节点）**：

```json
{"id":"<property-id>","label":"property","properties":{"name":"paymentType","dataType":"string"}}
```

该字段应依据 OMS 同版本属性定义补充；缺失类型要作为数据质量问题处理。**仅 V2 增加此字段；V1 继续返回原始 Property 节点 `properties`，不能因代码复用而新增 `dataType`。**

**完整 JSON Schema（Draft 2020-12）独立维护，不在正文重复展示**：参见 [请求 Schema](./schemas/oag-software-subgraph-request.schema.json) 和 [响应 Schema](./schemas/oag-software-subgraph-response.schema.json)。正文以 3.3.1～3.3.4 的参数/示例为准，Schema 文件用于自动化校验。

#### 3.3.5 `SemanticExtensions` 新增字段说明

`semanticExtensions.valueMappings[]` 属于 V2 可选扩展，示例返回扁平 objectTypeName/propertyName 并带有映射值 dataType，其含义与 Property 定义的 nodes[].properties.dataType 分别核对。内部 Skill 使用 query 模式时不应强制依赖这些 CBS 扩展；V1 退役须待迁移验证。

#### 3.3.6 Schema 使用及回归标准

- **软件输入**：`entities` 必填；支持仅 `objectType`、仅属性值或两者并存；`property:""` 允许表示属性未定。
- **统一 V2 模式校验**：query-only 不需要 entities，entities 优先于 query；V1 过渡期仍用旧路径及返回结构。V2 新功能根据租户 + 输入模式配置生效，原有 Function/Action 和 RelationshipProperty 能力必须回归。
- **输出与边界值**：允许空 ID、重复种子、多项值候选、空描述；`nodes[].properties` / `edges[].propertyMap` 容器及内部 JSON 字符串沿用。
- **质量**：Schema 合法不等于业务准确；属性类型、值归属、子图连通及错误状态按第 3.6～3.8 节验收。

### 3.4 自适应实体裁剪、种子生成、属性补全和属性类型填充

**候选处理规则**：

1. extractedEntities 是 CBS 已对齐的显式语义锚点；即使其某个 value 无命中，也不因“属性值为空”直接删除。
2. propertyValues 可包含同名或跨对象的冗余属性和值。OAG 在指定 objectType/property 范围内检索，排除不属于该对象的错误属性命中。
3. propertyValues-only 的候选对象若所有相关属性值均无**有效**召回，则不形成种子；检索为空或低于阈值必须按最终候选过滤结果判断。
4. 一个对象既出现于 extractedEntities 又出现于 propertyValues 时，合并显式属性和有效值命中的属性，按真实属性 ID 去重。
5. 最终 seedNodes = 显式锚点对象 ∪ 有效属性值链接对象；属性补全阶段按本体当前定义返回入选对象的全量属性，不凭语义相似度删掉主外键或查询必需属性。
6. NO_MATCH、NOT_SEARCHED、ERROR/INDEX_NOT_READY 不可混为一谈：检索失败、超时或未执行不能被当成“对象无关”而直接裁剪。该区分是增强验收约束，错误码和降级流程由详细接口评审定义。

**属性类型填充（仅 V2）**：OAG 在 V2 最终子图的 `label=property` 节点中，依据同一 OMS 本体版本的 Property 定义填充 `properties.dataType`（例如 `string`、`enum`、`long`、`timestamp`）；**V1 走旧 DTO，不增加字段**。必须保证属性 ID/归属与权威本体一致，缺失类型不由 LLM 猜测，应记录数据质量问题。Property 的 `dataType` 是 Schema 元数据，不等同于 `sourceValue → canonicalValue → defaultDataValue` 的值映射。

**属性补全的质量约束**：对象属性必须真实属于返回 ObjectType，冗余跨对象属性不可错挂；若启用 `includeAllProperties`，应完整保留主键及关键关联属性，且 `dataType` 与权威本体定义一致。返回量对 Token 和性能的影响需单独观察。

### 3.5 无向最小连通子图构建算法

名称：**OAG 无向最小连通子图构建算法**（Undirected Minimum Connecting Subgraph，UMCS）。

一句话定义：**基于本体图双向关系遍历与限定边类型，连接多个目标种子对象，通过最短路径探测及低冗余归并构建近似最小的连通子图，同时保留实际关系方向。**

与原有路径探测的新增变化：

| 项 | 历史逻辑 | 无向增强 |
|---|---|---|
| findShortestPath | 单向出边；任意边类型 | Nebula BIDIRECT / Gremlin bothE + otherV，仅 defines_relation / has_property |
| findAllPath | 单向出边；任意边类型 | 双向路径，边类型白名单，严格终点过滤作为质量回归项 |
| getSubgraph | 单向 OUT；仅 defines_relation | BOTH/both，defines_relation + has_property，TinkerPop 显式去重 |
| 归并 | 基于现有 MST 式路径收集 | 最短路径优先、无向端点匹配、并查集判断连通并提前终止 |
| 配置 | V1 过渡期原执行逻辑 | **V2 默认 true（无向白名单）**，按租户配置 false 回退 |

**默认行为**：V2 最小连通图默认开启无向白名单遍历，即 `subgraph.undirected-filter=true`；仅租户显式关闭时执行旧方向逻辑。V1 在 Skill 迁移前保持原路径，不随新默认值变化。

算法流程：

    真实种子 ObjectType / Property
        → 种子对路径探测（Nebula / TinkerPop Repository）
        → 双向、边类型白名单
        → 路径按跳数排序
        → MST 式并查集归并 / 去除不必要连接
        → 补边、去重、保留原始 source / target 方向
        → 结构完整且低冗余的本体子图

**语义与实现限制**：

- “无向”仅用于**连通性判定与遍历**，不改变真实 Relationship 的方向、ID、属性及后续 Cypher 的 source/target 语义。
- 原附件给出的 MST 式贪心归并不是全局 Steiner 最优求解；规范描述为低冗余/近似最小。
- 路径必须真的抵达 dst；Gremlin repeat 通过 until 的 hopLimit 退出时，单用 emit(hasId(dst)) 仍可能把非目标终点带入结果。推荐在 repeat 后执行 hasId(dst).path()，两个分支均需回归。
- Gremlin shortest path 使用 limit(1) 不自动证明得到全局最短，需以最短路径语义一致性测试和实现策略保证。
- 双向搜索会扩大搜索空间；hopLimit、maxPaths、maxNodes、maxEdges、timeoutMs、图库请求量与回退机制必须纳入压测。
- 保留 GraphQueryResult / Path / DataFrame 原有列契约；V2 图算法配置仅在 V2 分流后生效。**即使 V2 `undirected-filter=true`，V1 也必须继续使用历史查询路径和默认配置行为**。

#### 3.5.1 分层调用与最小连接流程

| 模块 | 主要方法及职责 | 约束 |
|---|---|---|
| 编排层 `GraphSearchHelper` | `performGraphSearchOptimized → getPathInfos → computePairwiseShortestPaths` | `minimal` 选定种子对象并计算两两连接路径 |
| 图查询层 `InfinityGraphRepository` | `findShortestPath/findAllPath/getSubgraph`；Nebula、TinkerPop 双实现 | 先由调用版本分流：V1 只使用历史分支；**仅 V2** 根据 `undirectedFilter` 切换路径，DataFrame 列结构不变 |
| 算法层 `GraphSearchUtils` | `buildMstSubgraph/buildAllSubgraph`，并查集和去冗余归并 | 与具体图库解耦；属于近似最小连接，不承诺全局 Steiner 最优 |

实现概要：将种子对路径按跳数升序排序；并查集检测两端是否已连通，已连通跳过，未连通则收集 Path 中节点/边；全部种子进入同一连通分量后提前终止。最后补边、按无向端点规则匹配真实边并校验边 ID，**输出边仍保持实际 source/target 方向**。不同分量时须显式表示无法连通，不应补造关系。

| 图查询 | Nebula 新分支（示意） | TinkerPop 新分支（示意） |
|---|---|---|
| `findShortestPath` | `FIND SHORTEST PATH ... OVER defines_relation,has_property BIDIRECT YIELD path AS p` | `bothE(EDGE_DEFINES_RELATION, EDGE_HAS_PROPERTY).otherV().simplePath()` |
| `findAllPath` | `FIND ALL PATH ... OVER defines_relation,has_property BIDIRECT UPTO N STEPS YIELD path AS p` | `repeat(bothE(...).otherV().simplePath())`，受 `hopLimit` 约束 |
| `getSubgraph` | `GET SUBGRAPH N STEPS ... BOTH defines_relation,has_property` | `both(...)` 扩展，`bothE(...).dedup()` 收边 |

#### 3.5.3 图算法风险与测试

- V2 minimal **无向默认 true**；检查 Nebula BIDIRECT / Gremlin bothE、仅允许 defines_relation/has_property、原始边方向保留及低冗余连通性。
- **10/30** 验证预置 true 和两种输入模式；**后续 DCC 阶段**才验证不同租户 true/false、动态修改及回滚，不得用未来 DCC 能力卡住 10/30 交付。
- V2 Gremlin findAllPath 到达 hopLimit 却未抵达 dst 的路径必须过滤；Gremlin limit(1) 不保证最短，需代码核对和独立用例验证。
- 双向默认可能增大图库探测成本，按种子数/节点度/hopLimit 记录 Probe、P95/P99、CPU/内存并设超限保护。
- 本节为分阶段的方案约束，10/30 不代表已支持 DCC，代码实现和联调验收须分别证明。

### 3.8 子图检索批跑和结果评测工具

## 4. 本体 OAG 性能规格

### 4.1 性能目标与评估边界

本章属于**下一步性能摸底与规格校核专题，非本期新增功能**。以《CBS软件业务和GDE协作方案流程图.pptx》第 12、13 页为初始评估输入，**不是已完成的实测 SLA**。优先验证 CBS 多用户并发下 OAG 接口的 P95/P99、TPS/QPS、错误率及资源饱和点，同时分别统计 Agent/LLM、OMS、值检索、质量处理、图库连接与结果组装耗时，避免以业务端到端总耗时掩盖 OAG 性能瓶颈。

#### 4.1.1 阶段耗时预算

| 阶段 | 预算 | 主责 | 影响因素与边界 |
|---|---:|---|---|
| 意图分析 | 10 s | CBS 业务 | LLM 推理与问题理解 |
| 子图/实体提取 | 10 s | CBS 业务 | GDE 提词开放、业务适配 Prompt |
| 子图向量检索 + 子图数据质量处理 | **共享 30 s** | 检索由平台/星火负责；质量内容由业务保障 | 总耗时仅计一次 |
| 子图语义消歧 | 10 s | CBS 业务 | GDE 提示词适配 |
| 子图最小图算法 | **待评估** | OAG / GDE | PPT 明确未给出耗时，未计入 60 s |

**解释**：和业务侧之前评估，已量化阶段相加为 **10 + 10 + 30 + 10 = 60 s**；**60 s 不包含最小图算法耗时**。不得直接将“完整 OAG 子图检索 ≤60 秒”或“完整业务端到端 ≤60 秒”作为已确认 SLA。需明确阶段串并行关系、百分位口径和最小图算法预算后，才能冻结端到端目标。

建议分别观测 OMS 分组获取、CBS 切词（业务侧计时）、OAG Enum/Instance 检索、融合、候选裁剪、V2 属性类型补全、图库最短路径/连通归并和结果组装。平台报告重点记录 OAG P50/P95/P99、错误率、吞吐、资源与超时；CBS Cypher 生成/执行属业务侧观测及验证范围。

### 4.2 业务并发和检索 QPS 初步估算

容量估算以问账 100 万用户、抽取 5% 用户、每用户 10 轮、8 小时完成为背景，并单列 Agent 问账 10 TPS。原图使用“100w/200w”两档容量，以下依照图中给出的容量数值摘录（不代表已经实测）：

| 估算项目 | 100 万用户 | 200 万用户 | 说明 |
|---|---:|---:|---|
| 问账业务基准请求 | 19 TPS | 38 TPS | 原图：100 万约为 TOC 17 + TOB 2 |
| Agent 入口额外负载 | 10 TPS | 10 TPS（图中文字） | 见下方口径冲突 |
| Agent 到本体检索请求 | 44 TPS | 87 TPS | 原图按“每次请求本体约 1.5 次”列出 |
| 本体到数据库子检索 | 66 QPS | 131 QPS | 原图按“每次本体查询数据库约 1.5 次”列出 |
| OpenSearch 估算基准 | ~100 QPS / 单位容量 | 同左 | 性能假设，不是已测承诺 |
| GaussVector 估算基准 | ~100 QPS / 单位容量 | 同左 | 性能假设，不是已测承诺 |
| 图数据库估算基准 | ~70 QPS / 单位容量 | 同左 | 与具体图复杂度及路径策略相关 |

**必须澄清的原始口径问题**：原有评估写出的“200 万：38 TPS + 10 TPS；每次请求 1.5 次”，应计算为 (38+10)×1.5 = **72 TPS**，与图上标注的 **87 TPS** 不一致；87 TPS 反算等价于入口约 58 TPS。131 QPS 又与 87×1.5 近似一致。因此本设计保留 PPT 中 **87 TPS / 131 QPS 为待验证的高档容量场景**，但实施前必须由 CBS、OAG 双方统一 200 万用户档的额外 Agent 流量、峰值系数和最终 TPS/QPS 口径。

### 4.3 索引容量和初步资源规格

估算假设：CBS 模型约 120+ 对象、3000+ 属性，约 10% 属性涉及用户数据语义索引；Embedding 为 1024 维 FP32，索引开销系数约 1.5。示意中的文本值长度、实例去重率、有效语义属性占比、索引副本数均需以实际数据核对。

| 项目 | 100 万用户 | 200 万用户 | 说明 |
|---|---:|---:|---|
| 用户相关向量索引 | 约 172 GB | 约 344 GB | 原 PPT 估算值，具体 GB/GiB 口径需统一 |
| 用户相关全文索引（2 副本） | 约 11 GB | 约 22 GB | 原 PPT 估算值 |
| 用户无关向量、全文部分 | 约 0.03 GB / 0.008 GB | 同数量级 | 相比用户相关部分较小 |
| 本体检索服务 | 10 U | 18 U | 原图单位 U；资源规格须明确 CPU/内存定义 |
| OpenSearch | 2 U | 4 U | 原图起步配置与容量向上取整 |
| GaussVector | 4 U | 8 U | 原图起步配置与容量向上取整 |
| 图数据库 | 2 U | 4 U | 假定 QPS 与复杂度不突破估算 |
| **本体相关资源合计** | **18 U** | **34 U** | 原初步容量估算 |

原估算给出规划口径：**每增加 100 万用户约增加 16 U + 183 GB 存储**（按上表用户相关向量与全文估算增量之和）。该结果取决于索引行数、去重率、分表策略、复制因子、硬件规格与真实峰值流量，属于容量规划初值，不应直接作为采购或现网交付承诺。

新增无向最小图查询的 CPU、图库 QPS、内存与耗时**未计入 PPT 的 60 s 时延**，且图数据库 QPS 不仅由用户数决定，还受种子个数、平均节点度数、hopLimit、边白名单和路径数影响，必须单独补做专项容量评估。

### 4.4 分阶段性能优化方案概要

| 模块 | 优化措施与新增边界 | 验证指标 |
|---|---|---|
| CBS + OMS | 按领域分组分页加载定义、减少全量上下文；按 revision 缓存有效元数据 | 定义加载 P95、Token/问、领域切词准确率 |
| OAG 值检索 | ObjectType+Property 限定范围，分离 Enum/Instance 检索，关键词+向量混合召回；控制 TopK 和阈值 | 单值查询 P95、检索 QPS、Value Mapping Accuracy、DB CPU/IO |
| 候选裁剪 | 避免对已对齐对象/属性重复调用链接与 LLM；仅对冗余 propertyValues 处理 | 候选缩减率、Seed Precision/Recall、LLM 调用数 |
| 子图构建 | 白名单边、并查集去冗余、最短路径缓存/批量探测（依原有能力评估）、maxPaths 和超时保护 | Pairwise Probe 数、Graph P95、节点/边冗余、路径爆炸率 |
| 结果组装 | 按对象批量补全属性，稳定语义映射，避免 N+1 查询和无效重复属性 | 组装 P95、结果字节数、属性覆盖率 |
| 资源隔离 | 在线查询与批量索引任务错峰/限流，线程池、连接池、队列及背压 | TPS/QPS、P99、错误率、CPU/内存、索引写入影响 |

所有性能优化以**准确性不回退**为前提；削减 Token、TopK 或路径数不能以静默丢失必要对象、属性、关系为代价。

### 4.5 性能验收方式与规格冻结条件

**以下为下一阶段待执行的性能验证计划**：采用冻结的 CBS 黄金集、全量回归集及不同规模本体/实例索引，分别进行单阶段基准、混合并发和链路压测；正式时延门槛需结合并发摸底结果冻结：

| 编号 | 验收主题 | 验证要求 |
|---|---|---|
| PERF-01 | 阶段耗时 | 量测各阶段 P50/P95/P99；核对 10/10/30/10 s 预算与实际串并行关系，补定最小图算法预算 |
| PERF-02 | 入口与后端吞吐 | 复现 100 万 44 TPS / 66 QPS 与 200 万高档 87 TPS / 131 QPS 两档待校核模型；明确是否能稳定承载 |

### A.2 测试策略、数据集与判定口径

**平台验收范围**：OMS 分组配置与按组取定义、OAG V2 检索输入/输出、候选裁剪、属性类型、子图连接与 V1 兼容。**CBS 的 Cypher 生成、执行及业务回答正确性是业务侧验证职责，不纳入本设计的平台验收用例与发布准入。**

采用**模块单测 → V1/V2 契约与配置隔离 → OMS/OAG 集成测试 → CBS 提供的黄金 `entities` 及冗余扰动批跑 → Nebula/Gremlin 图结果对照 → 平台子图报告 → 下一步并发性能专题**。每例记录 Case ID、需求 ID、模型/索引版本、请求、黄金子图、响应、断言、执行状态和归因。

测试数据由五类组成：① OMS 模型（多个领域组、未分组对象、权限差异、revision、同名属性与多种 dataType）；② 小型图拓扑（A→B←C、A→B←C→D、环、平行边、孤立点、has_function 非白名单关系）；③ CBS 黄金用例（标准 extractedEntities、propertyValues、对象/属性/关系 ID、值映射及必需桥接节点）；④ 冗余/异常扰动（空 property、错误对象和值、阈值边缘、无命中、检索服务异常）；⑤ V1 历史请求及响应快照。全部对照需要冻结 ontologyId、OMS revision、索引数据、本体图、配置和图库实现。

度量分别统计 ObjectType、Property、Relationship 的 TP/FP/FN 和 Precision=TP/(TP+FP)、Recall=TP/(TP+FN)、F1=2PR/(P+R)，并单列 Value Mapping Accuracy、Terminal Coverage、Extra Node/Edge Ratio、必要桥接节点覆盖率以及 V2 Property 类型准确率。零分母、等价路径及门槛须在黄金集评审时冻结；**平台不统计 CBS Cypher 执行成功率**。

### A.4 下一步重点：并发性能测试场景

**本节不作为本期新增功能承诺**。重点关注高并发下 OAG 子图检索的 P50/P95/P99、TPS/QPS、错误率、CPU/内存/GC、线程/连接池排队和图库探测放大。第 4 章来自 PPT 的 44 TPS/66 QPS、87 TPS/131 QPS 尚属估算，且 200 万用户档 (38+10)×1.5=72 TPS 与 PPT 87 TPS 不一致；负载定稿前须统一口径。

测试顺序：单用户/单请求阶段基线 → 并发用户与实际到达 TPS 分级 → 不同 Seed/节点度/hopLimit/Value 组合 → 混合长稳态 → 峰值突增 → 索引、图库异常及恢复。客户端并发线程数不等于实际 TPS，应同时记录服务端到达率、成功吞吐及分位耗时。

| 用例 ID | 验收项 | 并发场景 | 必须测量 |
|---|---|---|---|
| PERF-01-T | PERF-01/04 | 单请求 Enum/Instance 基线 | 值检索、裁剪、图构建、组装各段 P50/P95/P99 |
| PERF-02-T | PERF-02 | 逐级增加并发用户和入口 TPS | 实际 TPS、下游 QPS、P95/P99、饱和点、错误率 |
| PERF-03-T | PERF-02/06 | 100 万用户 PPT 44 TPS/66 QPS 档 | 持续承载能力和资源水位，不预判通过 |
| PERF-04-T | PERF-02/06 | 200 万用户 72 TPS 推算及 87 TPS/131 QPS PPT 档 | 两种口径标明来源，联审后冻结测试档位 |
| PERF-05-T | PERF-05 | 种子数、hopLimit、节点度梯度；无向开关开/关 | Pairwise Probe、Graph P95/P99、图查询次数及冗余率 |
