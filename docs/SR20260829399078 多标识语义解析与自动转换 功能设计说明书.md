# SR20260829399078 多标识语义解析与自动转换 功能设计说明书

> 文档名称：SR20260829399078 多标识语义解析与自动转换 功能设计说明书  
> 适用服务：OMS（Ontology Model Service）、OAC（Ontology Access）  
> 需求编号：SR20260829399078  
> 文档版本：V2.2  
> 设计范围：本版本聚焦 `DIMENSION` 数据查询语义下的 ID / NAME 伴生标识，以及 OAC 基于 OQL、对象属性语义和物理 Binding 自动生成**语义等价物理查询计划**。  
> 核心约束：伴生标识仅发生在当前 ObjectType 的两个不同 Property 之间，固定为 1:1 的 `idPropertyId ↔ namePropertyId`。

---

# 0. 方案概述

## 0.1 背景

同一个业务维度通常存在系统标识和业务名称两种表达。例如：

```text
Cell
├── cgi       —— ID
└── cellName  —— NAME
```

用户、Agent 和 OQL 更倾向于使用业务名称：

```text
查询 cellName = "上研小区A" 的 PRB
```

但实际物理模型可能是：

```text
dim_cell
├── cell_id
└── cell_name

Cell_ind
├── cell_id
└── prb
```

此时，OQL 的业务语义需要经过物理规划才能形成可执行查询。OAC 综合分析：

1. OQL 中使用了哪些对象属性；
2. 每个对象属性绑定了哪些物理字段；
3. 这些字段分布在哪些物理模型；
4. 条件属性是否具有 DIMENSION 伴生标识；
5. 当前属性在伴生关系中是 ID 还是 NAME；
6. ID 是否能够在维度解析模型与目标事实模型之间形成桥接；
7. 是否存在一个覆盖更多待查询属性的单一物理模型。

OAC 的目标是基于 OQL 业务语义生成**业务语义等价、物理上可执行**的查询计划。

---

## 0.2 语义等价查询定义

本方案将 OAC 的核心能力定义为：

> **Semantic Equivalent Query Planning：保持 OQL 业务属性语义，基于 OMS 的 DIMENSION 伴生关系与 Property Binding，选择直接查询、同源解析或跨源解析路径，并生成结果等价的物理执行计划。**

语义等价需要同时满足：

| 约束 | 说明 |
|---|---|
| 条件等价 | OQL 对 NAME 或 ID 的过滤，在物理层转换后仍表示同一业务实例 |
| 返回等价 | OQL 要求返回的对象属性语义在物理字段选择后保持一致 |
| 1:1 等价 | DIMENSION 的 ID/NAME 映射固定 1:1，转换结果必须唯一 |
| Binding 有据 | 所有物理字段均来自 OMS Binding 元数据 |
| 路径可执行 | 跨物理模型时必须存在明确的 DIMENSION ID 桥接路径 |
| 单表优先 | 存在覆盖全部查询属性的单一物理模型时优先直接查询 |
| 最优覆盖 | 多个物理模型可执行时，优先选择直接覆盖待查询属性更多的模型 |

## 0.4 四层决策模型

结合本次场景梳理，OAC 采用四层决策模型统一承载各类业务场景：

~~~text
第一层：Binding Topology
        判断对象属性的物理 Binding 是否形成可执行查询路径
        典型：CASE1～CASE7

第二层：Dimension Resolution
        回答“ID / NAME 是否需要转换、转换方向和结果基数”
        NAME → ID
        ID → NAME
        Scalar / Set

第三层：Query Shape
        回答“转换步骤作用于 FILTER / RETURN / GROUP / ORDER 的哪个位置”
        单条件 / 多条件 / IN / LIKE / 无目标维度等值过滤
        GROUP BY / ORDER BY / ID+NAME 同时过滤 / ASSOCIATION_QUERY

第四层：Physical Execution
        回答“逻辑计划最终如何落到数据源执行”
        单表 / 同源 JOIN / 子查询下推 / 跨源 DAG
~~~

统一决策链：

~~~text
OQL
 ↓
Query Shape
 ├─ Filter：ID / NAME / Other
 ├─ Return：ID / NAME / Other
 └─ Query Op：EQ / IN / LIKE / GROUP / ORDER / ...
 ↓
Binding Coverage
 ├─ 同表覆盖
 ├─ 跨表
 └─ 多表 / 多对象
 ↓
Dimension Resolution
 ├─ NONE
 ├─ NAME → ID
 ├─ ID → NAME
 ├─ Scalar
 └─ Set
 ↓
Physical Execution
 ├─ DIRECT_SINGLE_ASSET
 ├─ SAME_SOURCE_JOIN
 ├─ SAME_SOURCE_SUBQUERY
 ├─ CROSS_SOURCE_DAG
 └─ NOT_EXECUTABLE
~~~

CASE1～CASE16 对应四层能力的典型组合，代码实现围绕 QueryShape、DimensionResolutionStep 和 PhysicalPlan 统一展开。

# 第一章 OMS：对象属性 DIMENSION 语义与伴生标识设计

> 原型参考：\`SR20260829399078-companion-identifier-binding-demo-v6.html\`  
> 本章将原型中已经明确的交互原则、配置项、校验规则和 Binding 展示方式固化为 OMS 正式功能设计，聚焦伴生标识与物理 Binding。

## 1.1 OMS 功能职责

OMS 负责向 OAC 提供两类互相独立但可以联合使用的元数据。

### 1.1.1 对象属性 DIMENSION 语义

~~~text
ObjectType
  └── Property
        ├── semanticTypes
        │     └── DIMENSION
        └── dimensionSemantic
              ├── semanticId
              ├── idPropertyId
              └── namePropertyId
~~~

其职责是回答：

> 当前 ObjectType 中，哪两个 Property 构成同一个业务维度的 ID / NAME 伴生关系？

### 1.1.2 物理 Binding

~~~text
Physical Asset.Field
        ↓
ObjectType.Property
~~~

其职责是回答：

> 某个对象属性，在一个或多个物理模型中分别落在哪个字段？

二者职责必须保持分离：

- \`DimensionSemantic\` 定义对象属性之间的业务语义关系；
- Property Binding 定义物理字段到对象属性的映射；
- 物理 Binding 连线表达 Physical Field → Object Property 映射；
- ID / NAME 角色由 DIMENSION 语义元数据确定；
- OAC 运行时联合读取 DIMENSION 语义与 Binding，生成语义等价物理查询。

---

## 1.2 Property.java 领域模型

### 1.2.1 推荐结构

正式 OMS 领域模型采用“一级语义类型 + DIMENSION 专属结构”，为不同语义类型保留独立的数据结构。

~~~java
@EqualsAndHashCode(callSuper = true)
@Data
@Slf4j
public class Property extends AbstractElement {

    private String dataType;

    private String valueType;

    private String defaultValue;

    private List<String> refSharedIds;

    private Boolean primaryKey;

    private Extensions extensions;

    /**
     * 当前 Property 所属的数据查询语义类型。
     * 当前 SR 使用 DIMENSION。
     */
    private List<String> semanticTypes;

    /**
     * DIMENSION 专属语义结构。
     */
    private DimensionSemantic dimensionSemantic;

    ...
}
~~~

### 1.2.2 DimensionSemantic

~~~java
@Data
public class DimensionSemantic {

    /**
     * DIMENSION 伴生关系唯一标识。
     * ID / NAME 两端使用同一个 semanticId。
     */
    private String semanticId;

    /**
     * 当前 ObjectType 中承担 ID 角色的 Property ID。
     */
    private String idPropertyId;

    /**
     * 当前 ObjectType 中承担 NAME 角色的 Property ID。
     */
    private String namePropertyId;
}
~~~

字段定义：

| 字段 | 类型 | 必填 | 说明 |
|---|---|:---:|---|
| \`semanticId\` | String | 是 | 伴生关系唯一标识，由 OMS 生成 |
| \`idPropertyId\` | String | 是 | DIMENSION 的 ID Property |
| \`namePropertyId\` | String | 是 | DIMENSION 的 NAME Property |

固定业务规则：

~~~text
semanticType = DIMENSION
scope        = 当前 ObjectType / SAME_OBJECT
cardinality  = 1:1 / ONE_TO_ONE
role         = ID / NAME
resolverType = Property Field Mapping
~~~

其中 \`scope\`、\`cardinality\`、\`resolverType\` 在本 SR 中作为系统固定规则，由 OMS 自动维护。

## 1.3 Property JSON 示例

ID 属性：

~~~json
{
  "id": "p_cgi",
  "name": "cgi",
  "dataType": "String",
  "semanticTypes": [
    "DIMENSION"
  ],
  "dimensionSemantic": {
    "semanticId": "dim_cell_identity",
    "idPropertyId": "p_cgi",
    "namePropertyId": "p_cell_name"
  }
}
~~~

NAME 属性：

~~~json
{
  "id": "p_cell_name",
  "name": "cellName",
  "dataType": "String",
  "semanticTypes": [
    "DIMENSION"
  ],
  "dimensionSemantic": {
    "semanticId": "dim_cell_identity",
    "idPropertyId": "p_cgi",
    "namePropertyId": "p_cell_name"
  }
}
~~~

OAC 根据 DIMENSION 两个端点直接确定当前 Property 的角色：

~~~text
property.id == idPropertyId   → ID
property.id == namePropertyId → NAME
~~~

## 1.4 原型固化后的 OMS 用户操作流程

原型将对象属性建模过程明确拆成三个步骤：

~~~text
Step 1  定义对象属性
          ↓
Step 2  配置伴生标识
          ↓
Step 3  建立物理字段 Binding
~~~

核心交互原则：

1. 先定义业务对象属性，再配置对象属性之间的 ID / NAME 语义；
2. 伴生标识只存在于右侧 Object Property；
3. 左侧 Physical Model 只展示物理字段；
4. 中间连线只表达 \`Physical Field → Object Property\` Binding；
5. ID / NAME 标签统一展示在对象属性侧；
6. 一个伴生关系可以先于物理 Binding 创建；
7. OAC 真正执行语义转换前，再检查所需物理 Binding 是否完整。

OMS 页面分别提供对象语义配置与物理字段 Binding 两类操作。

---

## 1.5 对象属性列表中的伴生标识展示

对象属性列表直接展示当前 Property 的伴生关系状态。

推荐展示：

| 对象属性 | 数据类型 | DIMENSION 角色 | 伴生标识 | 物理 Binding |
|---|---|---|---|---|
| \`cgi\` | String | ID | \`cellName [NAME]\` | 2 条 |
| \`cellName\` | String | NAME | \`cgi [ID]\` | 1 条 |
| \`prb\` | Number | — | 未配置 | 1 条 |

交互要求：

- 无伴生关系的属性显示“配置伴生”入口；
- 已建立伴生关系的属性显示“伴生标识”入口；
- ID / NAME 以对象属性元数据标签展示；
- 两端 Property 都能够进入同一条伴生关系的查看/编辑界面；
- 从任意一端进入时，当前属性角色和伴生属性角色都按当前视角正确展示。

逻辑上采用一条统一的双端关系：

~~~text
Cell.cgi [ID]
      ↕ 1:1
Cell.cellName [NAME]
~~~

两个 Property 共同引用这一条关系。

## 1.6 数据映射页面设计

### 1.6.1 页面布局

原型明确采用：

~~~text
左侧：Physical Model / Physical Field
                    │
                    │ Binding
                    ▼
右侧：ObjectType / Object Property
~~~

页面顶部可以切换：

- 当前 Physical Model；
- 当前 ObjectType。

### 1.6.2 Binding 连线语义

蓝色连线只表示：

~~~text
Physical Field
      ↓
Object Property
~~~

例如：

~~~text
dim_cell.cell_id    → Cell.cgi
dim_cell.cell_name  → Cell.cellName
Cell_ind.cell_id    → Cell.cgi
Cell_ind.prb        → Cell.prb
~~~

Binding 连线保持单一语义：

~~~text
Physical Field → Object Property
~~~

ID、NAME、1:1 和 NAME → ID 等 DIMENSION 语义统一展示在对象属性侧。

### 1.6.3 右侧对象属性信息

对象属性节点可展示：

~~~text
Property Name
Data Type
ID / NAME Role
伴生标识入口
Binding 状态
~~~

例如：

~~~text
基站标识
siteId
String
[ID]
[伴生标识]
~~~

这样可以同时呈现对象语义与清晰的物理 Binding。

## 1.7 “对象属性 · 伴生标识”抽屉

原型中的伴生标识采用独立抽屉配置。

### 1.7.1 抽屉上下文

顶部固定显示：

~~~text
本体对象
    ↓
当前对象属性
~~~

例如：

~~~text
基站 / BaseStation
        ↓
基站标识 / siteId
~~~

同时明确提示：

> 伴生标识定义右侧对象属性之间的 ID / NAME 语义关系；左侧物理模型与 Binding 连线保持 Physical Field → Object Property 的映射语义。

### 1.7.2 只保留两个业务必填项

配置表单只保留：

| 字段 | 必填 | 候选范围 | 说明 |
|---|:---:|---|---|
| 当前属性标识角色 | 是 | ID / NAME | 当前 Property 在伴生关系中的角色 |
| 伴生属性 | 是 | 当前 ObjectType 内除自身外的 Property | 与当前属性形成 1:1 伴生关系 |

角色文案：

~~~text
ID   · 标识 / 编码
NAME · 名称 / 显示名
~~~

伴生属性角色自动取反：

~~~text
当前属性 = ID
→ 伴生属性 = NAME

当前属性 = NAME
→ 伴生属性 = ID
~~~

UI 根据当前端角色自动生成第二端角色。

### 1.7.3 固定规则与页面呈现

以下规则由 OMS 作为系统固定值维护：

~~~text
scope        = SAME_OBJECT
cardinality  = ONE_TO_ONE
resolverType = FIELD_MAPPING
enabled      = true（关系存在即启用）
~~~

页面仅展示本 SR 支持的 1:1 SAME_OBJECT 伴生关系形态。

## 1.8 伴生标识实时预览

当用户选择角色和伴生属性后，页面实时生成伴生关系预览：

~~~text
当前属性 · ID
BaseStation.siteId
        ↕
伴生属性 · NAME
BaseStation.siteName
~~~

预览必须包含两部分。

### 1.8.1 对象语义预览

明确显示：

- 当前 Property；
- 当前角色；
- 伴生 Property；
- 自动计算出的相反角色；
- 固定 1:1。

### 1.8.2 物理 Binding 覆盖检查

预览区只读展示当前 Property 和伴生 Property 已经绑定的物理字段。

例如：

~~~text
当前属性 siteId
  radio_inventory_a.site_id
  radio_inventory_b.site_code

伴生属性 siteName
  radio_inventory_a.site_name
  dim_site.site_name
~~~

状态判断：

~~~text
两端均存在 Binding
→ 提示：两侧属性均已有物理 Binding，可供 OAC 在执行期进行 ID / NAME 解析。

任一端 Binding 待补充
→ 提示：伴生标识已具备保存条件；执行前补齐参与查询的物理 Binding。
~~~

这里需要明确区分：

> **OMS 负责伴生关系合法性，OAC 负责具体 OQL 的执行可达性。**

OAC Planner 在运行时依据 QueryPropertySet 和 Binding Matrix 判断 Resolver Asset / Target Asset 的可执行路径。

## 1.9 创建与修改校验规则

保存伴生标识时，OMS Service 必须执行以下强校验。

### 1.9.1 必填校验

~~~text
role ∈ {ID, NAME}
companionPropertyId ∈ currentObject.properties
~~~

### 1.9.2 双端属性校验

~~~text
companionPropertyId ∈ currentObject.properties - {currentPropertyId}
~~~

伴生属性选择当前 ObjectType 内的另一个 Property。

### 1.9.3 SAME_OBJECT 校验

~~~text
currentProperty.objectTypeId
==
companionProperty.objectTypeId
~~~

伴生标识的两个 Property 归属同一个 ObjectType。

### 1.9.4 唯一参与关系校验

同一个 Property 在当前 DIMENSION 语义下唯一归属一条有效伴生关系。

例如已经存在：

~~~text
siteId [ID] ↔ siteName [NAME]
~~~

此时 \`siteName\` 的有效伴生关系保持为 \`siteId ↔ siteName\`；关系调整通过编辑当前关系完成。

### 1.9.5 角色互补校验

服务端归一化为：

~~~text
ID ↔ NAME
~~~

服务端始终归一化为一个 ID 端点和一个 NAME 端点。

### 1.9.6 关系基数校验

当前 SR 固定：

~~~text
ONE_TO_ONE
~~~

当前 SR 的伴生关系基数统一采用 ONE_TO_ONE。

### 1.9.7 双端一致性校验

如果 Property API 对两端都输出 \`dimensionSemantic\`，必须保证：

~~~text
semanticId     一致
idPropertyId   一致
namePropertyId 一致
~~~

OMS 通过原子更新保证双端数据一致。

## 1.10 创建、编辑、删除的原子语义

### 1.10.1 新建

从任意一个 Property 发起：

~~~text
currentProperty
+
role
+
companionProperty
~~~

OMS 统一归一化为：

~~~text
semanticId
idPropertyId
namePropertyId
~~~

并原子维护双端视图。

### 1.10.2 编辑

无论从 ID 端还是 NAME 端进入，都编辑同一个 \`semanticId\`。

修改任意以下内容：

- 当前端角色；
- 伴生 Property；

两类修改都更新同一个 semanticId 对应的逻辑关系。

### 1.10.3 删除

删除操作的语义是：

> 解除当前 ObjectType 中这一组 ID / NAME 伴生关系。

删除伴生关系时：

- Property 保持原状态；
- 物理 Binding 保持原状态；
- Physical Model 保持原状态；
- 其他独立语义配置保持原状态。

## 1.11 原型 IdentifierAssociation 与正式领域模型的映射

v6 原型内部使用了一个独立的 \`identifierAssociations\` 状态对象，例如：

~~~json
{
  "id": "ia-base-site",
  "enabled": true,
  "resolverType": "FIELD_MAPPING",
  "propertyId": "p-id",
  "role": "ID",
  "scope": "SAME_OBJECT",
  "companionObjectId": "o-base",
  "companionPropertyId": "p-name",
  "companionRole": "NAME",
  "cardinality": "ONE_TO_ONE",
  "revision": 1
}
~~~

该结构用于表达前端原型状态；正式 OMS 后端采用 DimensionSemantic 作为稳定领域结构。

推荐映射：

| 原型字段 | 正式 OMS 语义 | 处理方式 |
|---|---|---|
| \`id\` | \`semanticId\` | 由 OMS 生成 |
| \`propertyId + role\` | ID 或 NAME 端点 | 保存时归一化 |
| \`companionPropertyId + companionRole\` | 另一端点 | 保存时归一化 |
| \`scope=SAME_OBJECT\` | 同 ObjectType 约束 | 固定规则 + Service 校验 |
| \`cardinality=ONE_TO_ONE\` | 1:1 | 固定规则 + Service 校验 |
| \`resolverType=FIELD_MAPPING\` | 通过 Property Binding 解析 | 系统固定规则 |
| \`enabled\` | 关系是否存在 | 当前需求可由关系存在性表达 |
| \`companionObjectId\` | 当前 ObjectType | 由对象上下文统一确定 |
| \`revision\` | 并发版本 | 可复用 OMS 模型版本 / revision 机制 |

正式领域层仍以：

~~~text
DimensionSemantic
├── semanticId
├── idPropertyId
└── namePropertyId
~~~

作为最小稳定语义结构。

### 1.11.1 UI View Model

为了支撑原型中的抽屉展示，OMS API 可以额外组装一个 View DTO：

~~~java
class DimensionCompanionView {

    String semanticId;

    String objectTypeId;

    String currentPropertyId;
    DimensionRole currentRole;

    String companionPropertyId;
    DimensionRole companionRole;

    List<PropertyBindingSummary> currentBindings;
    List<PropertyBindingSummary> companionBindings;
}
~~~

该 DTO 作为展示模型，与 DimensionSemantic 领域模型配合使用。

### 1.11.2 正式语义确定原则

原型为了方便演示，会根据属性名中的 \`id/code/cgi\` 等字符串预选 ID 角色。

正式 OMS 中：

> Property 的 ID / NAME 角色以用户保存后的 DIMENSION 配置为准，Property Name 和 Physical Field Name 仅用于展示。

## 1.12 页面权限与状态

原型提供设计态、运行态、只读三种体验状态。

本 SR 对伴生标识采用：

| 页面状态 | 查看伴生标识 | 新建 / 修改 / 删除 |
|---|:---:|:---:|
| 设计态 | ✓ | ✓ |
| 运行态 | ✓ | ✗ |
| 只读 | ✓ | ✗ |

伴生标识属于模型设计元数据，应通过设计态变更流程进入模型版本；运行态只消费已经发布的语义。

## 1.13 OMS Service 保存流程

建议服务端统一走一个原子保存流程：

~~~text
收到：
currentPropertyId
role
companionPropertyId
        ↓
加载当前 ObjectType 与两个 Property
        ↓
必填 / 自引用 / SAME_OBJECT 校验
        ↓
检查两个 Property 是否已参加其他伴生关系
        ↓
根据 role 归一化：
ID Property / NAME Property
        ↓
生成或复用 semanticId
        ↓
原子更新 DIMENSION 双端投影
        ↓
递增模型版本 / revision
        ↓
返回标准化 DimensionSemantic
~~~

伪代码：

~~~java
DimensionSemantic saveCompanion(
        String objectTypeId,
        String currentPropertyId,
        DimensionRole currentRole,
        String companionPropertyId) {

    Property current = loadProperty(currentPropertyId);
    Property companion = loadProperty(companionPropertyId);

    validateSameObject(objectTypeId, current, companion);
    validateNotSelf(current, companion);
    validateNoAssociationConflict(current, companion);

    String idPropertyId =
        currentRole == DimensionRole.ID
            ? current.id()
            : companion.id();

    String namePropertyId =
        currentRole == DimensionRole.NAME
            ? current.id()
            : companion.id();

    DimensionSemantic semantic =
        createOrReuseSemantic(
            idPropertyId,
            namePropertyId
        );

    saveBothEndsAtomically(semantic);

    return semantic;
}
~~~

## 1.14 OMS 数据一致性

### 1.14.1 单一逻辑关系

逻辑上只存在一条 DIMENSION 关系：

~~~text
dim_cell_identity
├── idPropertyId   = p_cgi
└── namePropertyId = p_cell_name
~~~

ID Property 和 NAME Property 上保存或输出的是同一关系的双端投影。

### 1.14.2 Property 本地校验

\`Property.validate()\` 负责 Property 本地结构校验：

1. \`semanticTypes\` 包含 DIMENSION 时，\`dimensionSemantic\` 必须存在；
2. \`dimensionSemantic\` 存在时，\`semanticTypes\` 必须包含 DIMENSION；
3. \`semanticId\` 非空；
4. \`idPropertyId\` 非空；
5. \`namePropertyId\` 非空；
6. ID 与 NAME 分别引用两个不同 Property；
7. 当前 Property 必须是两个端点之一。

### 1.14.3 ObjectType / Service 层校验

依赖对象上下文的约束由 Service 层完成：

1. ID Property 存在；
2. NAME Property 存在；
3. 两端属于同一 ObjectType；
4. 一个 Property 只能参与一条当前 DIMENSION 伴生关系；
5. 两端 semanticId 一致；
6. 两端映射内容一致；
7. 删除 Property 前执行引用完整性校验；
8. 修改伴生关系时必须防止与现有关系冲突；
9. 模型并发修改需要使用现有 revision / model version 机制避免覆盖更新。

## 1.15 Binding 完整性与“可配置 / 可执行”边界

这是原型需要固化到正式设计中的重要边界。

### 1.15.1 OMS 配置层

创建伴生关系时，ID 与 NAME 两端的物理 Binding 可以按建模流程逐步补齐。

允许：

~~~text
先定义：
siteId [ID] ↔ siteName [NAME]

后续再建立：
Physical Field → siteId
Physical Field → siteName
~~~

这样保持本体建模和物理映射解耦。

### 1.15.2 OAC 执行层

某一次 OQL 是否能够执行，由 OAC 根据具体 Query Shape 判断。

例如 NAME → ID → Target 必须实际找到：

~~~text
Resolver Asset:
    NAME + ID

Target Asset:
    ID + Target Properties
~~~

所以：

~~~text
OMS 关系合法
≠
当前 OQL 一定可执行
~~~

OMS 页面只做 Binding 覆盖提示；OAC Planner 负责最终执行可达性判断。

OAC 至少需要获得：

以及 Property Binding：

~~~

运行时闭包：

~~~text
OQL Property
+
DimensionSemantic
+
Property Binding
+
Physical Asset Capability
=
Semantic Equivalent Physical Plan
~~~

## 1.17 OMS 功能验收标准

伴生标识功能至少满足：

1. 可以从对象属性列表进入伴生标识配置；
2. 可以从数据映射右侧对象属性进入伴生标识配置；
3. 只提供“当前属性标识角色”和“伴生属性”两个业务必填项；
4. 伴生属性来自当前 ObjectType 内的另一个 Property；
5. ID / NAME 自动互补；
6. 关系基数固定为 1:1；
7. 一个 Property 唯一归属一条有效伴生关系；
8. 从 ID 端和 NAME 端查看时都指向同一个 semanticId；
9. 页面实时展示两端的物理 Binding 覆盖情况；
10. 未完成物理 Binding 时允许保存伴生关系，但给出执行前 Binding 完整性提示；
11. Binding 连线保持 Physical Field → Object Property 的单一映射语义；
12. 删除伴生关系后 Property 和已有 Binding 保持原状态；
13. 伴生关系编辑能力开放在设计态，运行态 / 只读态提供查看能力；
14. 正式语义由 DIMENSION 元数据确定；
15. OAC 能通过 OMS API 获得标准化 \`idPropertyId / namePropertyId\` 以及两端 Binding。

# 第二章 OAC：语义等价查询总体设计

## 2.1 核心职责

OAC 以**完整查询所涉及的 Property 集合**为输入进行规划，并将对象语义映射为物理执行计划。

建议将 OAC 处理拆成四个阶段：

```text
1. Query Property Extraction
2. Binding Matrix Construction
3. Semantic Equivalent Plan Generation
4. Physical Query Translation
```

---

## 2.2 Query Property Extraction

从 OQL 提取本次查询涉及的对象属性集合：

```text
QueryPropertySet =
    Condition Properties
  ∪ Return Properties
  ∪ Group Properties
  ∪ Order Properties
```

例如：

```text
查询 abc = "上研小区A" 的 prb

QueryPropertySet:
- abc     —— 过滤属性
- prb     —— 返回属性
```

同时保留属性用途：

```java
QueryPropertyRef {
    String propertyId;
    QueryPropertyUsage usage;
}
```

```java
public enum QueryPropertyUsage {
    FILTER,
    RETURN,
    GROUP,
    ORDER
}
```

这样 Planner 能区分“用于定位记录的 Property”和“用于返回的 Property”。

---

## 2.3 Binding Matrix

OAC 根据 OMS Binding 构建“对象属性 × 物理模型”矩阵。

示例：

| Property | dim_cell | Cell_ind | Sdr_xxx |
|---|:---:|:---:|:---:|
| cgi | ✓ | ✓ | ✓ |
| abc | ✓ | — | ✓ |
| prb | — | ✓ | ✓ |

矩阵是语义等价查询规划的主要输入。

推荐运行时结构：

```java
Map<String, List<PropertyBinding>> bindingsByProperty;

class PropertyBinding {
    String propertyId;
    String assetId;
    String fieldName;
}
```

同时建立反向索引：

```java
Map<String, Set<String>> propertiesByAsset;
```

用于快速计算一个物理模型覆盖了多少 OQL Property。

---

## 2.4 逻辑规划与物理执行计划

原设计将 DIRECT_SINGLE_ASSET 和 DIMENSION_ID_BRIDGE 直接作为两类物理计划。结合新增场景后，需要拆分“语义 Resolution”和“物理 Execution”两个层次。

### 2.4.1 Dimension Resolution

DIMENSION 统一抽象为 DimensionResolutionStep，覆盖 FILTER / RETURN / GROUP / ORDER 等位置：

~~~java
class DimensionResolutionStep {
    String semanticId;

    String sourcePropertyId;
    String targetPropertyId;

    ResolutionDirection direction;      // NAME_TO_ID / ID_TO_NAME
    ResolutionCardinality cardinality;  // SCALAR / SET

    PredicateOperator operator;         // EQ / IN / LIKE / ...
    QueryPropertyUsage placement;       // FILTER / RETURN / GROUP / ORDER

    String resolverAssetId;
    String sourcePhysicalField;
    String targetPhysicalField;

    boolean uniqueRequired;
}
~~~

典型方向：

~~~text
NAME → ID
    用于 WHERE NAME = ?、IN、LIKE 等过滤解析

ID → NAME
    用于 RETURN NAME、GROUP BY NAME、ORDER BY NAME 等语义恢复
~~~

典型基数：

~~~text
EQ   → Scalar
IN   → 多个 Scalar 合并为 Set
LIKE → Set
~~~

### 2.4.2 Physical Plan

物理执行计划统一分为：

| PlanType | 说明 |
|---|---|
| DIRECT_SINGLE_ASSET | 一个 Asset 完整覆盖 QueryPropertySet |
| SAME_SOURCE_JOIN | Resolver 与 Target 同源，可通过 JOIN 完成 |
| SAME_SOURCE_SUBQUERY | Resolver 与 Target 同源，适合子查询下推 |
| CROSS_SOURCE_DAG | Resolver 与 Target 跨数据源，分 Stage 执行 |
| NOT_EXECUTABLE | 语义等价执行路径缺失时的规划结果 |

DIMENSION_ID_BRIDGE 作为逻辑能力描述，Physical Plan 统一采用上述 PlanType。

## 2.5 计划优先级

完整 Physical Plan 的优先级：

~~~text
P0  DIRECT_SINGLE_ASSET
        ↓
P1  SAME_SOURCE_JOIN / SAME_SOURCE_SUBQUERY
        ↓
P2  CROSS_SOURCE_DAG
        ↓
P3  NOT_EXECUTABLE
~~~

原则：

> 单 Asset 完整覆盖时采用直接查询；跨 Asset 时优先采用同源下推；跨数据源场景采用 CROSS_SOURCE_DAG。

# 第三章 OAC：语义等价规则与 CASE1～CASE16 场景设计

本章将语义等价规则与业务 Case 统一描述。每个 Case 同时给出 Binding 条件、DIMENSION 解析规则、物理计划和典型查询，使规则与场景保持一一对应。

## 3.1 统一 Case Matrix

| Case | 核心场景 | 决策重点 | OAC 计划 / 行为 |

## 3.2 CASE1：同表全覆盖，直接查询

业务：

~~~text
查询 cgi = "460-00-12345-001" 的 PRB
~~~

Binding：

~~~text
Cell_ind
├── msisdn -> cgi
└── prb    -> prb
~~~

判断规则：

~~~text
QueryPropertySet ⊆ propertiesByAsset[Cell_ind]
~~~

计划：

~~~text
DIRECT_SINGLE_ASSET
~~~

SQL：

~~~sql
SELECT prb, msisdn
FROM Cell_ind
WHERE msisdn = ?;
~~~

该规则适用于任何由单一 Asset 完整覆盖 QueryPropertySet 的场景，DIMENSION 伴生关系保持可用状态，由本次查询按需使用。

---

## 3.3 CASE2：跨模型查询的语义桥接路径校验

业务：

~~~text
查询 abc = "上研小区A" 的 PRB
~~~

Binding：

~~~text
abc -> Asset A
prb -> Asset B
~~~

Planner 先计算 Direct Candidate，再计算 DIMENSION Resolution Route。两类候选均为空时输出：

~~~text
SEMANTIC_EQUIVALENT_PLAN_NOT_FOUND
~~~

规则：

~~~text
Direct Candidate = ∅
Dimension Resolution Route = ∅
→ SEMANTIC_EQUIVALENT_PLAN_NOT_FOUND
~~~

所有跨模型关联路径均以 OMS DIMENSION 与 Property Binding 为依据。

---

## 3.4 CASE3：ID 属性直接定位目标模型

业务：

~~~text
查询 cgi = "460-00-12345-001" 的 PRB
~~~

语义：

~~~text
cgi = DIMENSION ID
~~~

Target Asset：

~~~text
Cell_ind
├── cell_id -> cgi
└── prb     -> prb
~~~

Planner 直接把 ID Predicate 下推到 Target Asset：

~~~sql
SELECT prb, cell_id
FROM Cell_ind
WHERE cell_id = ?;
~~~

规则：

~~~text
Filter Role = ID
Target Asset 覆盖 ID + Target Properties
→ DIRECT_SINGLE_ASSET / ID Direct Locate
~~~

---

## 3.5 CASE4：NAME 跨表，通过 ID 建立语义桥接

业务：

~~~text
查询 abc = "上研小区A" 的 PRB
~~~

语义：

~~~text
cgi [ID] ↔ abc [NAME]
~~~

Binding：

~~~text
dim_cell
├── cell_id   -> cgi
└── cell_name -> abc

Cell_ind
├── cell_id -> cgi
└── prb     -> prb
~~~

Planner 生成：

~~~text
DimensionResolutionStep
direction   = NAME_TO_ID
cardinality = SCALAR
placement   = FILTER
~~~

逻辑路径：

~~~text
abc(NAME)
   ↓ dim_cell
cgi(ID)
   ↓ Cell_ind
prb
~~~

同源子查询示例：

~~~sql
SELECT f.prb
FROM Cell_ind f
WHERE f.cell_id = (
    SELECT d.cell_id
    FROM dim_cell d
    WHERE d.cell_name = ?
);
~~~

数据源能力决定最终采用 SAME_SOURCE_JOIN、SAME_SOURCE_SUBQUERY 或 CROSS_SOURCE_DAG。

---

## 3.6 CASE5：NAME 与 Target 同表，直接查询

Binding：

~~~text
Cell_ind
├── name -> abc
├── id   -> cgi
└── prb  -> prb
~~~

QueryPropertySet 中的 NAME 与 Target Properties 由同一 Asset 完整覆盖，因此优先生成：

~~~text
DIRECT_SINGLE_ASSET
~~~

SQL：

~~~sql
SELECT prb, name
FROM Cell_ind
WHERE name = ?;
~~~

该路径保持查询阶段最少、物理资产数量最少。

## 3.7 CASE6：跨表 Bridge 的 ID Binding 完整性

Resolver：

~~~text
dim_cell
├── cell_id   -> cgi
└── cell_name -> abc
~~~

Target：

~~~text
Cell_ind
└── prb -> prb
~~~

跨表 DIMENSION Resolution 需要形成：

~~~text
Resolver Asset：NAME + ID
Target Asset：ID + Target Properties
~~~

当 Target Asset 的 ID Binding 待补齐时，Planner 输出：

~~~text
DIMENSION_TARGET_BINDING_NOT_FOUND
~~~

该错误直接指向需要补齐的伴生 ID Property Binding。

## 3.8 CASE7：多候选 Asset 的稳定选择

示例：

~~~text
dim_cell:
    cgi + abc

Cell_ind:
    cgi + prb

Sdr_perform:
    cgi + abc + prb
~~~

对于：

~~~text
查询 abc = "上研小区A" 的 PRB
~~~

Sdr_perform 完整覆盖 QueryPropertySet，生成 Direct Candidate。

Resolver Candidate 排序采用：

~~~text
1. NAME + ID 同时 Binding
2. 与 Target Asset 同数据源
3. 支持直接 Pushdown
4. Query / Resolution Property 覆盖度
5. Binding Route Priority
6. 稳定 Asset ID
~~~

完整 Physical Plan 排序采用：

~~~text
DIRECT_SINGLE_ASSET
    ↓
SAME_SOURCE_JOIN / SAME_SOURCE_SUBQUERY
    ↓
CROSS_SOURCE_DAG
~~~

同级计划继续比较 stageCount、assetCount、resolutionStepCount、bindingRoutePriority 与 stablePlanKey。

## 3.9 CASE8：多个 DIMENSION、多个单值过滤条件

对象存在：

~~~text
Cell：cgi [ID] ↔ abc [NAME]
Site：sid [ID] ↔ def [NAME]
~~~

OQL：

~~~sql
SELECT prb, abc, def
FROM obj
WHERE abc = "上研小区A"
  AND def = "XX站点"
  AND brand = "5G"
~~~

Planner 独立生成：

~~~text
ResolutionStep1：abc(NAME) → cgi(ID)
ResolutionStep2：def(NAME) → sid(ID)
普通 Predicate：brand = 5G
~~~

两个 semanticId 分别完成解析，再与普通 Predicate 合并为最终物理条件。

---

## 3.10 CASE9：IN 多值查询

OQL：

~~~sql
SELECT prb, abc, def
FROM obj
WHERE abc IN ("上研小区A", "上研小区B", "上研小区C")
  AND def = "XX站点"
  AND brand = "5G"
~~~

解析：

~~~text
abc IN (A, B, C)
→ A / B / C 分别执行 NAME_TO_ID
→ 合并为 ID Set
→ target.id IN (...)
~~~

DimensionResolutionStep：

~~~text
direction   = NAME_TO_ID
cardinality = SET
operator    = IN
placement   = FILTER
~~~

---

## 3.11 CASE10：LIKE 模糊查询

OQL：

~~~sql
SELECT prb, abc, def
FROM obj
WHERE abc LIKE "%上研%"
  AND def = "XX站点"
  AND brand = "5G"
~~~

LIKE 对 NAME 产生集合型解析：

~~~text
NAME LIKE pattern
→ Set<NAME>
→ Set<ID>
~~~

DimensionResolutionStep：

~~~text
direction   = NAME_TO_ID
cardinality = SET
operator    = LIKE
placement   = FILTER
~~~

每个命中的 NAME 按 1:1 语义解析为对应 ID。

---

## 3.12 CASE11：列表查询

场景：

~~~text
查询站点 A 下所有小区名称和 PRB
~~~

事实表保存 cell_id + prb，维度模型保存 cell_id + cell_name 时，Planner 通过 ID 关联恢复 NAME：

~~~sql
SELECT d.cell_name, f.prb
FROM dim_cell d
JOIN Cell_ind f
  ON d.cell_id = f.cell_id
ORDER BY f.prb
LIMIT 10;
~~~

列表查询结合 LIMIT 或聚合控制结果规模。

## 3.13 CASE12：GROUP BY / ORDER BY 使用 NAME

OQL：

~~~sql
SELECT def, SUM(prb)
FROM obj
GROUP BY def
~~~

事实表使用 site_id，维度模型提供 site_id ↔ site_name。

Planner 生成：

~~~text
DimensionResolutionStep
direction = ID_TO_NAME
placement = GROUP
~~~

同源 JOIN：

~~~sql
SELECT d.site_name, SUM(f.prb)
FROM Cell_site_ind f
JOIN dim_site d
  ON f.site_id = d.site_id
GROUP BY d.site_name;
~~~

GROUP BY 与 ORDER BY 都作为 DimensionResolutionStep 的正式 placement。

## 3.14 CASE13：跨数据源 NAME → ID → Target

数据源布局：

~~~text
dim_cell → GaussDB
Cell_ind → Hudi / Hive / API
~~~

Planner 生成 CROSS_SOURCE_DAG：

~~~text
Stage 1：GaussDB
NAME → ID Set
        ↓
Stage 2：Hudi / Hive / API
ID IN (...)
        ↓
Target Result
~~~

PhysicalStage 显式记录数据源、Asset 和依赖关系。

## 3.15 CASE14：ID / NAME 同时作为过滤条件

OQL：

~~~text
cgi = X
AND
abc = Y
~~~

OAC 执行一致性校验：

~~~text
resolve(Y) == X
~~~

结果：

~~~text
Y → X
    条件一致，继续执行

Y → Z 且 Z != X
    两个 Predicate 的交集为空，返回 0 rows
~~~

两个过滤条件都保留在查询语义中。

## 3.16 CASE15：运行时 1:1 数据语义校验

Scalar Resolution：

| Resolver 结果 | OAC 行为 |
|---:|---|
| 0 | DIMENSION_VALUE_NOT_FOUND |
| 1 | 正常进入后续 Stage |
| >1 | DIMENSION_VALUE_NOT_UNIQUE |

其中：

- 0 表示当前输入值没有对应业务实例；
- 1 表示符合 1:1 伴生语义；
- >1 表示数据质量与 OMS 声明的 1:1 语义存在偏差。

LIKE / Set Resolution 支持多个不同 NAME 分别解析到对应 ID。

---

## 3.17 CASE16：关系查询中的伴生标识

业务：

~~~text
查询站点名 A 下名为“上研小区A”的 Cell 的 PRB
~~~

OQL 示意：

~~~text
ASSOCIATION_QUERY Site -> Cell
WHERE Site.def = "A站点"
  AND Cell.abc = "上研小区A"
RETURN Cell.prb
~~~

规划顺序：

~~~text
Relationship Resolution
        ↓
定位 Site / Cell 对象范围
        ↓
Site 内部 def(NAME) → sid(ID)
Cell 内部 abc(NAME) → cgi(ID)
        ↓
Physical Query
~~~

Site 与 Cell 分别在各自 ObjectType 内完成 DIMENSION Resolution，Relationship Resolution 负责对象之间的关系定位。

---

## 3.18 规则归纳

CASE1～CASE16 可以归纳为四类统一规则：

| 规则层 | 统一规则 |
|---|---|
| Binding Topology | 单 Asset 全覆盖优先；跨 Asset 使用显式 DIMENSION 语义路径 |
| Dimension Resolution | FILTER 支持 NAME_TO_ID / ID Direct；RETURN / GROUP / ORDER 支持 ID_TO_NAME |
| Query Shape | EQ 对应 Scalar；IN / LIKE 对应 Set；多个 DIMENSION 独立解析后组合 |
| Physical Execution | 单表优先，其次同源 JOIN / SUBQUERY，再按数据源边界生成 CROSS_SOURCE_DAG |

OAC Planner 基于这四类规则统一生成 Physical Plan。

# 第四章 OAC Planner 详细设计


## 4.0 QueryShape 与 DimensionResolutionStep

从 OQL 提取的 QueryProperty 同时保留属性集合、查询位置和操作符：

~~~text
FILTER
RETURN
GROUP
ORDER
AGGREGATE
RELATIONSHIP_FILTER
~~~

推荐：

~~~java
class QueryPropertyRef {
    String objectTypeId;
    String propertyId;
    QueryPropertyUsage usage;
    PredicateOperator operator;
}
~~~

Dimension Resolution 统一表示为：

~~~java
class DimensionResolutionStep {
    String semanticId;
    String sourcePropertyId;
    String targetPropertyId;

    ResolutionDirection direction;       // NAME_TO_ID / ID_TO_NAME
    ResolutionCardinality cardinality;   // SCALAR / SET

    PredicateOperator operator;
    QueryPropertyUsage placement;

    String resolverAssetId;
    boolean uniqueRequired;
}
~~~

该结构使 OAC 以统一模型承载 FILTER、RETURN、GROUP、ORDER 等 DIMENSION 解析场景。

## 4.1 规划输入

建议定义：

```java

    String objectTypeId;

    List<Predicate> predicates;
    List<String> returnPropertyIds;
}
```

Binding 快照：

```java
class PropertyBindingSnapshot {
    Map<String, List<PropertyBinding>> bindingsByProperty;
    Map<String, Set<String>> propertiesByAsset;
}
```

DIMENSION 快照：

```java

    Map<String, DimensionSemantic> semanticByProperty;
}
```

## 4.2 候选 Asset 计算

### 4.2.1 Direct Candidate

```text
required = QueryPropertySet

for asset in allAssets:
    coverage = required ∩ propertiesByAsset[asset]

    if coverage == required:
        add DIRECT_SINGLE_ASSET candidate
```

### 4.2.2 Bridge Candidate

Direct Candidate 为空时进入 Dimension Resolution Candidate 计算。

对过滤 Property：

```text
filterProperty = predicate.property
```

若：

```text
role(filterProperty) = NAME
```

则：

```text
idProperty = dimension.idPropertyId
nameProperty = dimension.namePropertyId
```

解析模型候选：

```text
resolverAssets =
    assets(nameProperty)
    ∩
    assets(idProperty)
```

目标模型候选：

```text
targetRequired =
    { idProperty }
    ∪
    nonFilterQueryProperties

targetAssets =
    assets that cover targetRequired
```

任意：

```text
resolverAsset × targetAsset
```

组成一个 Dimension Resolution Route 候选。随后由 PhysicalPlanBuilder 根据 resolverAsset 与 targetAsset 的数据源关系生成 SAME_SOURCE_JOIN、SAME_SOURCE_SUBQUERY 或 CROSS_SOURCE_DAG。

任一集合为空时，Planner 返回对应的 Binding 完整性错误。

## 4.3 Candidate Ranking

候选选择分为两级。

### 4.3.1 Resolver Candidate Ranking

当存在多个可完成 ID / NAME 解析的 Asset 时，按以下顺序：

~~~text
1. NAME + ID 是否同时 Binding
2. 是否与 Target Asset 同数据源
3. 是否能够直接 Pushdown
4. 属性覆盖度
5. Binding Route Priority
6. 稳定 Asset ID
~~~

### 4.3.2 Physical Plan Ranking

完整 Plan 的优先级：

~~~text
DIRECT_SINGLE_ASSET
    ↓
SAME_SOURCE_JOIN / SAME_SOURCE_SUBQUERY
    ↓
CROSS_SOURCE_DAG
~~~

同一优先级内：

~~~text
stageCount ASC
assetCount ASC
resolutionStepCount ASC
bindingRoutePriority ASC
stablePlanKey ASC
~~~

## 4.5 Planner 主流程伪代码

~~~text
shape = analyzeQueryShape(oql)

bindingSnapshot = loadBindings(shape.objectTypes)
dimensionSnapshot = loadDimensionSemantics(shape.objectTypes)
sourceCapabilities = loadSourceCapabilities(bindingSnapshot)

directCandidates = findDirectCandidates(
    shape,
    bindingSnapshot
)

if directCandidates.hasAny():
    return rankAndSelect(directCandidates)

resolutionSteps = []

for queryProperty in shape.semanticPositions:
    dimension = dimensionSnapshot.get(queryProperty.propertyId)

    if dimension is null:
        continue

    role = resolveDimensionRole(
        queryProperty.propertyId,
        dimension
    )

    step = buildDimensionResolutionStep(
        queryProperty,
        role,
        dimension,
        bindingSnapshot
    )

    if step != null:
        resolutionSteps.add(step)

validateResolutionRoutes(
    resolutionSteps,
    bindingSnapshot
)

physicalCandidates = buildPhysicalPlans(
    shape,
    resolutionSteps,
    bindingSnapshot,
    sourceCapabilities
)

if physicalCandidates.hasAny():
    return rankAndSelect(physicalCandidates)

throw SEMANTIC_EQUIVALENT_PLAN_NOT_FOUND
~~~

Planner 的统一输出结构为：

~~~text

+

+
PhysicalStage[]
+
ResultSemanticMapping
~~~

# 第五章 Translator 与执行

## 5.1 Direct Plan

Translator 使用一个 targetAsset 组装查询。

```text
OQL Property
  ↓ Binding
Physical Field
```

Direct Plan 直接进入 PhysicalTranslator。

---

## 5.2 DIMENSION Resolution 的基础执行形态

跨 Asset 的 DIMENSION Resolution 可以通过同源下推或分阶段执行。

### 5.2.1 子查询下推

适用条件：

- resolutionAsset 与 targetAsset 可由同一数据源完成；
- 数据源 Translator 支持子查询或 JOIN 下推。

示例：

```sql
SELECT f.prb
FROM Cell_ind f
WHERE f.cell_id = (
    SELECT d.cell_id
    FROM dim_cell d
    WHERE d.cell_name = ?
)
```

### 5.2.2 分阶段执行

适用条件：

- Resolver 与 Target 分别由独立 Stage 访问；
- Stage 间通过中间 ID / ID Set 建立依赖。

```text
Stage 1
NAME -> ID

Stage 2
ID -> Target Query
```

OAC ExecutionContext 保存中间 ID，原始 OQL 在执行链路中保持稳定。

---


## 5.3 同源 JOIN

当：

- Resolver 与 Target 位于同一数据源；
- NAME 还需要参与 RETURN / GROUP / ORDER；
- Translator 支持 JOIN 下推；

可生成：

~~~sql
SELECT f.prb, d.cell_name
FROM Cell_ind f
JOIN dim_cell d
  ON f.cell_id = d.cell_id
WHERE d.cell_name = ?;
~~~

## 5.4 跨源 DAG

当 Resolver 与 Target 位于不同数据源，例如：

~~~text
dim_cell → GaussDB
Cell_ind → Hudi / Hive / API
~~~

执行：

~~~text
Stage 1
GaussDB：NAME → ID / ID Set

Stage 2
Hudi / Hive / API：ID IN (...)

Stage N
必要时执行结果语义恢复
~~~

中间 ID 保存于 OAC ExecutionContext，原始 OQL 在执行链路中保持稳定。

## 5.5 ID → NAME 结果语义恢复

如果事实查询只能得到 ID，而 OQL 要求 RETURN / GROUP / ORDER 使用 NAME，则 Planner 生成 ID_TO_NAME Resolution。

可通过：

1. 同源 JOIN 一次返回 NAME；
2. 主查询后批量 ID → NAME lookup。

NAME 语义通过 ID_TO_NAME Resolution 恢复，字段 alias 与业务语义保持一致。

## 5.6 1:1 结果校验

Stage 1 对单个输入值必须执行唯一性校验：

| 解析结果 | 行为 |
|---:|---|
| 0 | 返回 `DIMENSION_VALUE_NOT_FOUND` |
| 1 | 正常执行 Stage 2 |
| >1 | 返回 `DIMENSION_VALUE_NOT_UNIQUE` |

对于 `IN`，每个输入元素独立满足 1:1，然后合并为 ID 集合。

---

## 5.7 返回语义恢复

如果 OQL 返回 NAME，但目标事实查询只投影 ID，OAC 必须恢复原 Property 语义。

可选方式：

1. 执行计划已包含 resolutionAsset 时直接追加 NAME 投影；
2. 主查询结束后批量执行 ID→NAME lookup。

返回字段名称、alias 和对象属性语义保持 OQL 定义。

# 第六章 错误处理

## 6.1 OMS 错误码

| 错误码 | 场景 |
|---|---|
| `DIMENSION_SEMANTIC_INVALID` | DIMENSION 结构完整性校验失败 |
| `DIMENSION_PROPERTY_NOT_FOUND` | ID / NAME Property 引用缺失 |
| `DIMENSION_PROPERTY_SCOPE_INVALID` | 两端 ObjectType 范围校验失败 |
| `DIMENSION_PROPERTY_CONFLICT` | Property 已参与另一条 DIMENSION 关系 |
| `DIMENSION_SEMANTIC_INCONSISTENT` | 双端 DIMENSION 内容存在差异 |
| `DIMENSION_SEMANTIC_REFERENCE_IN_USE` | 删除 Property 时存在伴生引用 |

## 6.2 OAC 错误码

| 错误码 | 场景 |
|---|---|
| `SEMANTIC_EQUIVALENT_PLAN_NOT_FOUND` | Direct Plan 与 Dimension Resolution Route 均为空 |
| `DIMENSION_TARGET_BINDING_NOT_FOUND` | Target Asset 的伴生 ID Binding 缺失 |
| `DIMENSION_RESOLUTION_BINDING_NOT_FOUND` | Resolver Asset 的 NAME+ID Binding 路径缺失 |
| `DIMENSION_VALUE_NOT_FOUND` | NAME 的 ID 解析结果为空 |
| `DIMENSION_VALUE_NOT_UNIQUE` | NAME 解析到多个 ID |
| `DIMENSION_OPERATOR_NOT_SUPPORTED` | 条件操作符超出当前伴生转换范围 |
| `DIMENSION_CONDITION_INCONSISTENT` | ID / NAME 同时过滤且语义冲突 |
| `CROSS_SOURCE_STAGE_BINDING_FAILED` | 跨源 DAG 中间结果绑定失败 |
| `PHYSICAL_ASSET_SELECTION_AMBIGUOUS` | 候选在当前路由规则下仍保持同级 |

错误信息必须包含：

```json
{
  "objectType": "Cell",
  "queryProperties": [
    "abc",
    "prb"
  ],
  "sourceProperty": "abc",
  "semanticId": "dim_cell_identity",
  "missingBindingProperty": "cgi"
}
```

便于开发和模型配置人员快速定位缺失的 Binding。

| GROUP BY / ORDER BY NAME，事实仅有 ID | ID_TO_NAME + JOIN / Lookup |
| ID + NAME 同时过滤 | Consistency Check |
| ASSOCIATION_QUERY | Relationship Resolution 后执行对象本地 Dimension Resolution |
