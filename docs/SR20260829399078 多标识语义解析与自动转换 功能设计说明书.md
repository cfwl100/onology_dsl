# SR20260829399078 多标识语义解析与自动转换 功能设计说明书

> 文档名称：SR20260829399078 多标识语义解析与自动转换 功能设计说明书  
> 适用服务：OMS（Ontology Model Service）、OAC（Ontology Access）  
> 需求编号：SR20260829399078  
> 文档版本：V2.2  
> 设计范围：本版本聚焦 `DIMENSION` 数据查询语义下的 ID / NAME 伴生标识，以及 OAC 基于 OQL、对象属性语义和物理 Binding 自动生成**语义等价物理查询计划**。  
> 核心约束：伴生标识仅发生在当前 ObjectType 的两个不同 Property 之间，固定为 1:1 的 `idPropertyId ↔ namePropertyId`。

---

# 0. 方案概述

## 0.1 背景

同一个业务维度通常存在系统标识和业务名称两种表达。例如：

```text
Cell
├── cgi       —— ID
└── cellName  —— NAME
```

用户、Agent 和 OQL 更倾向于使用业务名称：

```text
查询 cellName = "上研小区A" 的 PRB
```

但实际物理模型可能是：

```text
dim_cell
├── cell_id
└── cell_name

Cell_ind
├── cell_id
└── prb
```

此时，OQL 的业务语义需要经过物理规划才能形成可执行查询。OAC 综合分析：

1. OQL 中使用了哪些对象属性；
2. 每个对象属性绑定了哪些物理字段；
3. 这些字段分布在哪些物理模型；
4. 条件属性是否具有 DIMENSION 伴生标识；
5. 当前属性在伴生关系中是 ID 还是 NAME；
6. ID 是否能够在维度解析模型与目标事实模型之间形成桥接；
7. 是否存在一个覆盖更多待查询属性的单一物理模型。

OAC 的目标是基于 OQL 业务语义生成**业务语义等价、物理上可执行**的查询计划。

---

## 0.2 语义等价查询定义

本方案将 OAC 的核心能力定义为：

> **Semantic Equivalent Query Planning：保持 OQL 业务属性语义，基于 OMS 的 DIMENSION 伴生关系与 Property Binding，选择直接查询、同源解析或跨源解析路径，并生成结果等价的物理执行计划。**

语义等价需要同时满足：

| 约束 | 说明 |
|---|---|
| 条件等价 | OQL 对 NAME 或 ID 的过滤，在物理层转换后仍表示同一业务实例 |
| 返回等价 | OQL 要求返回的对象属性语义在物理字段选择后保持一致 |
| 1:1 等价 | DIMENSION 的 ID/NAME 映射固定 1:1，转换结果必须唯一 |
| Binding 有据 | 所有物理字段均来自 OMS Binding 元数据 |
| 路径可执行 | 跨物理模型时必须存在明确的 DIMENSION ID 桥接路径 |
| 单表优先 | 存在覆盖全部查询属性的单一物理模型时优先直接查询 |
| 最优覆盖 | 多个物理模型可执行时，优先选择直接覆盖待查询属性更多的模型 |

## 0.4 四层决策模型

结合本次场景梳理，OAC 采用四层决策模型统一承载各类业务场景：

~~~text
第一层：Binding Topology
        判断对象属性的物理 Binding 是否形成可执行查询路径
        典型：CASE1～CASE7

第二层：Dimension Resolution
        回答“ID / NAME 是否需要转换、转换方向和结果基数”
        NAME → ID
        ID → NAME
        Scalar / Set

第三层：Query Shape
        回答“转换步骤作用于 FILTER / RETURN / GROUP / ORDER 的哪个位置”
        单条件 / 多条件 / IN / LIKE / 无目标维度等值过滤
        GROUP BY / ORDER BY / ID+NAME 同时过滤 / ASSOCIATION_QUERY

第四层：Physical Execution
        回答“逻辑计划最终如何落到数据源执行”
        单表 / 同源 JOIN / 子查询下推 / 跨源 DAG
~~~

统一决策链：

~~~text
OQL
 ↓
Query Shape
 ├─ Filter：ID / NAME / Other
 ├─ Return：ID / NAME / Other
 └─ Query Op：EQ / IN / LIKE / GROUP / ORDER / ...
 ↓
Binding Coverage
 ├─ 同表覆盖
 ├─ 跨表
 └─ 多表 / 多对象
 ↓
Dimension Resolution
 ├─ NONE
 ├─ NAME → ID
 ├─ ID → NAME
 ├─ Scalar
 └─ Set
 ↓
Physical Execution
 ├─ DIRECT_SINGLE_ASSET
 ├─ SAME_SOURCE_JOIN
 ├─ SAME_SOURCE_SUBQUERY
 ├─ CROSS_SOURCE_DAG
 └─ NOT_EXECUTABLE
~~~

CASE1～CASE16 对应四层能力的典型组合，代码实现围绕 QueryShape、DimensionResolutionStep 和 PhysicalPlan 统一展开。

# 第一章 OMS：对象属性 DIMENSION 语义与伴生标识设计

> 原型参考：\`SR20260829399078-companion-identifier-binding-demo-v6.html\`  
> 本章将原型中已经明确的交互原则、配置项、校验规则和 Binding 展示方式固化为 OMS 正式功能设计，聚焦伴生标识与物理 Binding。

## 1.1 OMS 功能职责

OMS 负责向 OAC 提供两类互相独立但可以联合使用的元数据。

### 1.1.1 对象属性 DIMENSION 语义

~~~text
ObjectType
  └── Property
        ├── semanticTypes
        │     └── DIMENSION
        └── dimensionSemantic
              ├── semanticId
              ├── idPropertyId
              └── namePropertyId
~~~

其职责是回答：

> 当前 ObjectType 中，哪两个 Property 构成同一个业务维度的 ID / NAME 伴生关系？

### 1.1.2 物理 Binding

~~~text
Physical Asset.Field
        ↓
ObjectType.Property
~~~

其职责是回答：

> 某个对象属性，在一个或多个物理模型中分别落在哪个字段？

二者职责必须保持分离：

- \`DimensionSemantic\` 定义对象属性之间的业务语义关系；
- Property Binding 定义物理字段到对象属性的映射；
- 物理 Binding 连线表达 Physical Field → Object Property 映射；
- ID / NAME 角色由 DIMENSION 语义元数据确定；
- OAC 运行时联合读取 DIMENSION 语义与 Binding，生成语义等价物理查询。

---

## 1.2 Property.java 领域模型

### 1.2.1 推荐结构

正式 OMS 领域模型采用“一级语义类型 + DIMENSION 专属结构”，为不同语义类型保留独立的数据结构。

~~~java
@EqualsAndHashCode(callSuper = true)
@Data
@Slf4j
public class Property extends AbstractElement {

    private String dataType;

    private String valueType;

    private String defaultValue;

    private List<String> refSharedIds;

    private Boolean primaryKey;

    private Extensions extensions;

    /**
     * 当前 Property 所属的数据查询语义类型。
     * 当前 SR 使用 DIMENSION。
     */
    private List<String> semanticTypes;

    /**
     * DIMENSION 专属语义结构。
     */
    private DimensionSemantic dimensionSemantic;

    ...
}
~~~

### 1.2.2 DimensionSemantic

~~~java
@Data
public class DimensionSemantic {

    /**
     * DIMENSION 伴生关系唯一标识。
     * ID / NAME 两端使用同一个 semanticId。
     */
    private String semanticId;

    /**
     * 当前 ObjectType 中承担 ID 角色的 Property ID。
     */
    private String idPropertyId;

    /**
     * 当前 ObjectType 中承担 NAME 角色的 Property ID。
     */
    private String namePropertyId;
}
~~~

字段定义：

| 字段 | 类型 | 必填 | 说明 |
|---|---|:---:|---|
| \`semanticId\` | String | 是 | 伴生关系唯一标识，由 OMS 生成 |
| \`idPropertyId\` | String | 是 | DIMENSION 的 ID Property |
| \`namePropertyId\` | String | 是 | DIMENSION 的 NAME Property |

固定业务规则：

~~~text
semanticType = DIMENSION
scope        = 当前 ObjectType / SAME_OBJECT
cardinality  = 1:1 / ONE_TO_ONE
role         = ID / NAME
resolverType = Property Field Mapping
~~~

其中 \`scope\`、\`cardinality\`、\`resolverType\` 在本 SR 中作为系统固定规则，由 OMS 自动维护。

## 1.3 Property JSON 示例

ID 属性：

~~~json
{
  "id": "p_cgi",
  "name": "cgi",
  "dataType": "String",
  "semanticTypes": [
    "DIMENSION"
  ],
  "dimensionSemantic": {
    "semanticId": "dim_cell_identity",
    "idPropertyId": "p_cgi",
    "namePropertyId": "p_cell_name"
  }
}
~~~

NAME 属性：

~~~json
{
  "id": "p_cell_name",
  "name": "cellName",
  "dataType": "String",
  "semanticTypes": [
    "DIMENSION"
  ],
  "dimensionSemantic": {
    "semanticId": "dim_cell_identity",
    "idPropertyId": "p_cgi",
    "namePropertyId": "p_cell_name"
  }
}
~~~

OAC 根据 DIMENSION 两个端点直接确定当前 Property 的角色：

~~~text
property.id == idPropertyId   → ID
property.id == namePropertyId → NAME
~~~

## 1.4 原型固化后的 OMS 用户操作流程

原型将对象属性建模过程明确拆成三个步骤：

~~~text
Step 1  定义对象属性
          ↓
Step 2  配置伴生标识
          ↓
Step 3  建立物理字段 Binding
~~~

核心交互原则：

1. 先定义业务对象属性，再配置对象属性之间的 ID / NAME 语义；
2. 伴生标识只存在于右侧 Object Property；
3. 左侧 Physical Model 只展示物理字段；
4. 中间连线只表达 \`Physical Field → Object Property\` Binding；
5. ID / NAME 标签统一展示在对象属性侧；
6. 一个伴生关系可以先于物理 Binding 创建；
7. OAC 真正执行语义转换前，再检查所需物理 Binding 是否完整。

OMS 页面分别提供对象语义配置与物理字段 Binding 两类操作。

---

## 1.5 对象属性列表中的伴生标识展示

对象属性列表直接展示当前 Property 的伴生关系状态。

推荐展示：

| 对象属性 | 数据类型 | DIMENSION 角色 | 伴生标识 | 物理 Binding |
|---|---|---|---|---|
| \`cgi\` | String | ID | \`cellName [NAME]\` | 2 条 |
| \`cellName\` | String | NAME | \`cgi [ID]\` | 1 条 |
| \`prb\` | Number | — | 未配置 | 1 条 |

交互要求：

- 无伴生关系的属性显示“配置伴生”入口；
- 已建立伴生关系的属性显示“伴生标识”入口；
- ID / NAME 以对象属性元数据标签展示；
- 两端 Property 都能够进入同一条伴生关系的查看/编辑界面；
- 从任意一端进入时，当前属性角色和伴生属性角色都按当前视角正确展示。

逻辑上采用一条统一的双端关系：

~~~text
Cell.cgi [ID]
      ↕ 1:1
Cell.cellName [NAME]
~~~

两个 Property 共同引用这一条关系。

## 1.6 数据映射页面设计

### 1.6.1 页面布局

原型明确采用：

~~~text
左侧：Physical Model / Physical Field
                    │
                    │ Binding
                    ▼
右侧：ObjectType / Object Property
~~~

页面顶部可以切换：

- 当前 Physical Model；
- 当前 ObjectType。

### 1.6.2 Binding 连线语义

蓝色连线只表示：

~~~text
Physical Field
      ↓
Object Property
~~~

例如：

~~~text
dim_cell.cell_id    → Cell.cgi
dim_cell.cell_name  → Cell.cellName
Cell_ind.cell_id    → Cell.cgi
Cell_ind.prb        → Cell.prb
~~~

Binding 连线保持单一语义：

~~~text
Physical Field → Object Property
~~~

ID、NAME、1:1 和 NAME → ID 等 DIMENSION 语义统一展示在对象属性侧。

### 1.6.3 右侧对象属性信息

对象属性节点可展示：

~~~text
Property Name
Data Type
ID / NAME Role
伴生标识入口
Binding 状态
~~~

例如：

~~~text
基站标识
siteId
String
[ID]
[伴生标识]
~~~

这样可以同时呈现对象语义与清晰的物理 Binding。

## 1.7 “对象属性 · 伴生标识”抽屉

原型中的伴生标识采用独立抽屉配置。

### 1.7.1 抽屉上下文

顶部固定显示：

~~~text
本体对象
    ↓
当前对象属性
~~~

例如：

~~~text
基站 / BaseStation
        ↓
基站标识 / siteId
~~~

同时明确提示：

> 伴生标识定义右侧对象属性之间的 ID / NAME 语义关系；左侧物理模型与 Binding 连线保持 Physical Field → Object Property 的映射语义。

### 1.7.2 只保留两个业务必填项

配置表单只保留：

| 字段 | 必填 | 候选范围 | 说明 |
|---|:---:|---|---|
| 当前属性标识角色 | 是 | ID / NAME | 当前 Property 在伴生关系中的角色 |
| 伴生属性 | 是 | 当前 ObjectType 内除自身外的 Property | 与当前属性形成 1:1 伴生关系 |

角色文案：

~~~text
ID   · 标识 / 编码
NAME · 名称 / 显示名
~~~

伴生属性角色自动取反：

~~~text
当前属性 = ID
→ 伴生属性 = NAME

当前属性 = NAME
→ 伴生属性 = ID
~~~

UI 根据当前端角色自动生成第二端角色。

### 1.7.3 固定规则与页面呈现

以下规则由 OMS 作为系统固定值维护：

~~~text
scope        = SAME_OBJECT
cardinality  = ONE_TO_ONE
resolverType = FIELD_MAPPING
enabled      = true（关系存在即启用）
~~~

页面仅展示本 SR 支持的 1:1 SAME_OBJECT 伴生关系形态。

## 1.8 伴生标识实时预览

当用户选择角色和伴生属性后，页面实时生成伴生关系预览：

~~~text
当前属性 · ID
BaseStation.siteId
        ↕
伴生属性 · NAME
BaseStation.siteName
~~~

预览必须包含两部分。

### 1.8.1 对象语义预览

明确显示：

- 当前 Property；
- 当前角色；
- 伴生 Property；
- 自动计算出的相反角色；
- 固定 1:1。

### 1.8.2 物理 Binding 覆盖检查

预览区只读展示当前 Property 和伴生 Property 已经绑定的物理字段。

例如：

~~~text
当前属性 siteId
  radio_inventory_a.site_id
  radio_inventory_b.site_code

伴生属性 siteName
  radio_inventory_a.site_name
  dim_site.site_name
~~~

状态判断：

~~~text
两端均存在 Binding
→ 提示：两侧属性均已有物理 Binding，可供 OAC 在执行期进行 ID / NAME 解析。

任一端 Binding 待补充
→ 提示：伴生标识已具备保存条件；执行前补齐参与查询的物理 Binding。
~~~

这里需要明确区分：

> **OMS 负责伴生关系合法性，OAC 负责具体 OQL 的执行可达性。**

OAC Planner 在运行时依据 QueryPropertySet 和 Binding Matrix 判断 Resolver Asset / Target Asset 的可执行路径。

## 1.9 创建与修改校验规则

保存伴生标识时，OMS Service 必须执行以下强校验。

### 1.9.1 必填校验

~~~text
role ∈ {ID, NAME}
companionPropertyId ∈ currentObject.properties
~~~

### 1.9.2 双端属性校验

~~~text
companionPropertyId ∈ currentObject.properties - {currentPropertyId}
~~~

伴生属性选择当前 ObjectType 内的另一个 Property。

### 1.9.3 SAME_OBJECT 校验

~~~text
currentProperty.objectTypeId
==
companionProperty.objectTypeId
~~~

伴生标识的两个 Property 归属同一个 ObjectType。

### 1.9.4 唯一参与关系校验

同一个 Property 在当前 DIMENSION 语义下唯一归属一条有效伴生关系。

例如已经存在：

~~~text
siteId [ID] ↔ siteName [NAME]
~~~

此时 \`siteName\` 的有效伴生关系保持为 \`siteId ↔ siteName\`；关系调整通过编辑当前关系完成。

### 1.9.5 角色互补校验

服务端归一化为：

~~~text
ID ↔ NAME
~~~

服务端始终归一化为一个 ID 端点和一个 NAME 端点。

### 1.9.6 关系基数校验

当前 SR 固定：

~~~text
ONE_TO_ONE
~~~

当前 SR 的伴生关系基数统一采用 ONE_TO_ONE。

### 1.9.7 双端一致性校验

如果 Property API 对两端都输出 \`dimensionSemantic\`，必须保证：

~~~text
semanticId     一致
idPropertyId   一致
namePropertyId 一致
~~~

OMS 通过原子更新保证双端数据一致。

## 1.10 创建、编辑、删除的原子语义

### 1.10.1 新建

从任意一个 Property 发起：

~~~text
currentProperty
+
role
+
companionProperty
~~~

OMS 统一归一化为：

~~~text
semanticId
idPropertyId
namePropertyId
~~~

并原子维护双端视图。

### 1.10.2 编辑

无论从 ID 端还是 NAME 端进入，都编辑同一个 \`semanticId\`。

修改任意以下内容：

- 当前端角色；
- 伴生 Property；

两类修改都更新同一个 semanticId 对应的逻辑关系。

### 1.10.3 删除

删除操作的语义是：

> 解除当前 ObjectType 中这一组 ID / NAME 伴生关系。

删除伴生关系时：

- Property 保持原状态；
- 物理 Binding 保持原状态；
- Physical Model 保持原状态；
- 其他独立语义配置保持原状态。

## 1.11 原型 IdentifierAssociation 与正式领域模型的映射

v6 原型内部使用了一个独立的 \`identifierAssociations\` 状态对象，例如：

~~~json
{
  "id": "ia-base-site",
  "enabled": true,
  "resolverType": "FIELD_MAPPING",
  "propertyId": "p-id",
  "role": "ID",
  "scope": "SAME_OBJECT",
  "companionObjectId": "o-base",
  "companionPropertyId": "p-name",
  "companionRole": "NAME",
  "cardinality": "ONE_TO_ONE",
  "revision": 1
}
~~~

该结构用于表达前端原型状态；正式 OMS 后端采用 DimensionSemantic 作为稳定领域结构。

推荐映射：

| 原型字段 | 正式 OMS 语义 | 处理方式 |
|---|---|---|
| \`id\` | \`semanticId\` | 由 OMS 生成 |
| \`propertyId + role\` | ID 或 NAME 端点 | 保存时归一化 |
| \`companionPropertyId + companionRole\` | 另一端点 | 保存时归一化 |
| \`scope=SAME_OBJECT\` | 同 ObjectType 约束 | 固定规则 + Service 校验 |
| \`cardinality=ONE_TO_ONE\` | 1:1 | 固定规则 + Service 校验 |
| \`resolverType=FIELD_MAPPING\` | 通过 Property Binding 解析 | 系统固定规则 |
| \`enabled\` | 关系是否存在 | 当前需求可由关系存在性表达 |
| \`companionObjectId\` | 当前 ObjectType | 由对象上下文统一确定 |
| \`revision\` | 并发版本 | 可复用 OMS 模型版本 / revision 机制 |

正式领域层仍以：

~~~text
DimensionSemantic
├── semanticId
├── idPropertyId
└── namePropertyId
~~~

作为最小稳定语义结构。

### 1.11.1 UI View Model

为了支撑原型中的抽屉展示，OMS API 可以额外组装一个 View DTO：

~~~java
class DimensionCompanionView {

    String semanticId;

    String objectTypeId;

    String currentPropertyId;
    DimensionRole currentRole;

    String companionPropertyId;
    DimensionRole companionRole;

    List<PropertyBindingSummary> currentBindings;
    List<PropertyBindingSummary> companionBindings;
}
~~~

该 DTO 作为展示模型，与 DimensionSemantic 领域模型配合使用。

### 1.11.2 正式语义确定原则

原型为了方便演示，会根据属性名中的 \`id/code/cgi\` 等字符串预选 ID 角色。

正式 OMS 中：

> Property 的 ID / NAME 角色以用户保存后的 DIMENSION 配置为准，Property Name 和 Physical Field Name 仅用于展示。

## 1.12 页面权限与状态

原型提供设计态、运行态、只读三种体验状态。

本 SR 对伴生标识采用：

| 页面状态 | 查看伴生标识 | 新建 / 修改 / 删除 |
|---|:---:|:---:|
| 设计态 | ✓ | ✓ |
| 运行态 | ✓ | ✗ |
| 只读 | ✓ | ✗ |

伴生标识属于模型设计元数据，应通过设计态变更流程进入模型版本；运行态只消费已经发布的语义。

## 1.13 OMS Service 保存流程

建议服务端统一走一个原子保存流程：

~~~text
收到：
currentPropertyId
role
companionPropertyId
        ↓
加载当前 ObjectType 与两个 Property
        ↓
必填 / 自引用 / SAME_OBJECT 校验
        ↓
检查两个 Property 是否已参加其他伴生关系
        ↓
根据 role 归一化：
ID Property / NAME Property
        ↓
生成或复用 semanticId
        ↓
原子更新 DIMENSION 双端投影
        ↓
递增模型版本 / revision
        ↓
返回标准化 DimensionSemantic
~~~

伪代码：

~~~java
DimensionSemantic saveCompanion(
        String objectTypeId,
        String currentPropertyId,
        DimensionRole currentRole,
        String companionPropertyId) {

    Property current = loadProperty(currentPropertyId);
    Property companion = loadProperty(companionPropertyId);

    validateSameObject(objectTypeId, current, companion);
    validateNotSelf(current, companion);
    validateNoAssociationConflict(current, companion);

    String idPropertyId =
        currentRole == DimensionRole.ID
            ? current.id()
            : companion.id();

    String namePropertyId =
        currentRole == DimensionRole.NAME
            ? current.id()
            : companion.id();

    DimensionSemantic semantic =
        createOrReuseSemantic(
            idPropertyId,
            namePropertyId
        );

    saveBothEndsAtomically(semantic);

    return semantic;
}
~~~

## 1.14 OMS 数据一致性

### 1.14.1 单一逻辑关系

逻辑上只存在一条 DIMENSION 关系：

~~~text
dim_cell_identity
├── idPropertyId   = p_cgi
└── namePropertyId = p_cell_name
~~~

ID Property 和 NAME Property 上保存或输出的是同一关系的双端投影。

### 1.14.2 Property 本地校验

\`Property.validate()\` 负责 Property 本地结构校验：

1. \`semanticTypes\` 包含 DIMENSION 时，\`dimensionSemantic\` 必须存在；
2. \`dimensionSemantic\` 存在时，\`semanticTypes\` 必须包含 DIMENSION；
3. \`semanticId\` 非空；
4. \`idPropertyId\` 非空；
5. \`namePropertyId\` 非空；
6. ID 与 NAME 分别引用两个不同 Property；
7. 当前 Property 必须是两个端点之一。

### 1.14.3 ObjectType / Service 层校验

依赖对象上下文的约束由 Service 层完成：

1. ID Property 存在；
2. NAME Property 存在；
3. 两端属于同一 ObjectType；
4. 一个 Property 只能参与一条当前 DIMENSION 伴生关系；
5. 两端 semanticId 一致；
6. 两端映射内容一致；
7. 删除 Property 前执行引用完整性校验；
8. 修改伴生关系时必须防止与现有关系冲突；
9. 模型并发修改需要使用现有 revision / model version 机制避免覆盖更新。

## 1.15 Binding 完整性与“可配置 / 可执行”边界

这是原型需要固化到正式设计中的重要边界。

### 1.15.1 OMS 配置层

创建伴生关系时，ID 与 NAME 两端的物理 Binding 可以按建模流程逐步补齐。

允许：

~~~text
先定义：
siteId [ID] ↔ siteName [NAME]

后续再建立：
Physical Field → siteId
Physical Field → siteName
~~~

这样保持本体建模和物理映射解耦。

### 1.15.2 OAC 执行层

某一次 OQL 是否能够执行，由 OAC 根据具体 Query Shape 判断。

例如 NAME → ID → Target 必须实际找到：

~~~text
Resolver Asset:
    NAME + ID

Target Asset:
    ID + Target Properties
~~~

所以：

~~~text
OMS 关系合法
≠
当前 OQL 一定可执行
~~~

OMS 页面只做 Binding 覆盖提示；OAC Planner 负责最终执行可达性判断。

OAC 至少需要获得：

以及 Property Binding：


运行时闭包：

~~~text
OQL Property
+
DimensionSemantic
+
Property Binding
+
Physical Asset Capability
=
Semantic Equivalent Physical Plan
~~~

## 1.17 OMS 功能验收标准

伴生标识功能至少满足：

1. 可以从对象属性列表进入伴生标识配置；
2. 可以从数据映射右侧对象属性进入伴生标识配置；
3. 只提供“当前属性标识角色”和“伴生属性”两个业务必填项；
4. 伴生属性来自当前 ObjectType 内的另一个 Property；
5. ID / NAME 自动互补；
6. 关系基数固定为 1:1；
7. 一个 Property 唯一归属一条有效伴生关系；
8. 从 ID 端和 NAME 端查看时都指向同一个 semanticId；
9. 页面实时展示两端的物理 Binding 覆盖情况；
10. 未完成物理 Binding 时允许保存伴生关系，但给出执行前 Binding 完整性提示；
11. Binding 连线保持 Physical Field → Object Property 的单一映射语义；
12. 删除伴生关系后 Property 和已有 Binding 保持原状态；
13. 伴生关系编辑能力开放在设计态，运行态 / 只读态提供查看能力；
14. 正式语义由 DIMENSION 元数据确定；
15. OAC 能通过 OMS API 获得标准化 \`idPropertyId / namePropertyId\` 以及两端 Binding。

# 第二章 OAC：语义等价查询总体设计

## 2.1 核心职责

OAC 以**完整查询所涉及的 Property 集合**为输入进行规划，并将对象语义映射为物理执行计划。

建议将 OAC 处理拆成四个阶段：

```text
1. Query Property Extraction
2. Binding Matrix Construction
3. Semantic Equivalent Plan Generation
4. Physical Query Translation
```

---

## 2.2 Query Property Extraction

从 OQL 提取本次查询涉及的对象属性集合：

```text
QueryPropertySet =
    Condition Properties
  ∪ Return Properties
  ∪ Group Properties
  ∪ Order Properties
```

例如：

```text
查询 abc = "上研小区A" 的 prb

QueryPropertySet:
- abc     —— 过滤属性
- prb     —— 返回属性
```

同时保留属性用途：

```java
QueryPropertyRef {
    String propertyId;
    QueryPropertyUsage usage;
}
```

```java
public enum QueryPropertyUsage {
    FILTER,
    RETURN,
    GROUP,
    ORDER
}
```

这样 Planner 能区分“用于定位记录的 Property”和“用于返回的 Property”。

---

## 2.3 Binding Matrix

OAC 根据 OMS Binding 构建“对象属性 × 物理模型”矩阵。

示例：

| Property | dim_cell | Cell_ind | Sdr_xxx |
|---|:---:|:---:|:---:|
| cgi | ✓ | ✓ | ✓ |
| abc | ✓ | — | ✓ |
| prb | — | ✓ | ✓ |

矩阵是语义等价查询规划的主要输入。

推荐运行时结构：

```java
Map<String, List<PropertyBinding>> bindingsByProperty;

class PropertyBinding {
    String propertyId;
    String assetId;
    String fieldName;
}
```

同时建立反向索引：

```java
Map<String, Set<String>> propertiesByAsset;
```

用于快速计算一个物理模型覆盖了多少 OQL Property。

---

## 2.4 逻辑规划与物理执行计划

原设计将 DIRECT_SINGLE_ASSET 和 DIMENSION_ID_BRIDGE 直接作为两类物理计划。结合新增场景后，需要拆分“语义 Resolution”和“物理 Execution”两个层次。

### 2.4.1 Dimension Resolution

DIMENSION 统一抽象为 DimensionResolutionStep，覆盖 FILTER / RETURN / GROUP / ORDER 等位置：

~~~java
class DimensionResolutionStep {
    String semanticId;

    String sourcePropertyId;
    String targetPropertyId;

    ResolutionDirection direction;      // NAME_TO_ID / ID_TO_NAME
    ResolutionCardinality cardinality;  // SCALAR / SET

    PredicateOperator operator;         // EQ / IN / LIKE / ...
    QueryPropertyUsage placement;       // FILTER / RETURN / GROUP / ORDER

    String resolverAssetId;
    String sourcePhysicalField;
    String targetPhysicalField;

    boolean uniqueRequired;
}
~~~

典型方向：

~~~text
NAME → ID
    用于 WHERE NAME = ?、IN、LIKE 等过滤解析

ID → NAME
    用于 RETURN NAME、GROUP BY NAME、ORDER BY NAME 等语义恢复
~~~

典型基数：

~~~text
EQ   → Scalar
IN   → 多个 Scalar 合并为 Set
LIKE → Set
~~~

### 2.4.2 Physical Plan

物理执行计划统一分为：

| PlanType | 说明 |
|---|---|
| DIRECT_SINGLE_ASSET | 一个 Asset 完整覆盖 QueryPropertySet |
| SAME_SOURCE_JOIN | Resolver 与 Target 同源，可通过 JOIN 完成 |
| SAME_SOURCE_SUBQUERY | Resolver 与 Target 同源，适合子查询下推 |
| CROSS_SOURCE_DAG | Resolver 与 Target 跨数据源，分 Stage 执行 |
| NOT_EXECUTABLE | 语义等价执行路径缺失时的规划结果 |

DIMENSION_ID_BRIDGE 作为逻辑能力描述，Physical Plan 统一采用上述 PlanType。

## 2.5 计划优先级

完整 Physical Plan 的优先级：

~~~text
P0  DIRECT_SINGLE_ASSET
        ↓
P1  SAME_SOURCE_JOIN / SAME_SOURCE_SUBQUERY
        ↓
P2  CROSS_SOURCE_DAG
        ↓
P3  NOT_EXECUTABLE
~~~

原则：

> 单 Asset 完整覆盖时采用直接查询；跨 Asset 时优先采用同源下推；跨数据源场景采用 CROSS_SOURCE_DAG。

# 第三章 OAC：语义等价规则与 CASE1～CASE16 场景设计

本章将语义等价规则与业务 Case 统一描述。每个 Case 同时给出 Binding 条件、DIMENSION 解析规则、物理计划和典型查询，使规则与场景保持一一对应。

## 3.1 统一 Case Matrix

| Case | 核心场景 | 决策重点 | OAC 计划 / 行为 |

## 3.2 CASE1：同表全覆盖，直接查询

业务：

~~~text
查询 cgi = "460-00-12345-001" 的 PRB
~~~

Binding：

~~~text
Cell_ind
├── msisdn -> cgi
└── prb    -> prb
~~~

判断规则：

~~~text
QueryPropertySet ⊆ propertiesByAsset[Cell_ind]
~~~

计划：

~~~text
DIRECT_SINGLE_ASSET
~~~

SQL：

~~~sql
SELECT prb, msisdn
FROM Cell_ind
WHERE msisdn = ?;
~~~

该规则适用于任何由单一 Asset 完整覆盖 QueryPropertySet 的场景，DIMENSION 伴生关系保持可用状态，由本次查询按需使用。

---

## 3.3 CASE2：跨模型查询的语义桥接路径校验

业务：

~~~text
查询 abc = "上研小区A" 的 PRB
~~~

Binding：

~~~text
abc -> Asset A
prb -> Asset B
~~~

Planner 先计算 Direct Candidate，再计算 DIMENSION Resolution Route。两类候选均为空时输出：

~~~text
SEMANTIC_EQUIVALENT_PLAN_NOT_FOUND
~~~

规则：

~~~text
Direct Candidate = ∅
Dimension Resolution Route = ∅
→ SEMANTIC_EQUIVALENT_PLAN_NOT_FOUND
~~~

所有跨模型关联路径均以 OMS DIMENSION 与 Property Binding 为依据。

---

## 3.4 CASE3：ID 属性直接定位目标模型

业务：

~~~text
查询 cgi = "460-00-12345-001" 的 PRB
~~~

语义：

~~~text
cgi = DIMENSION ID
~~~

Target Asset：

~~~text
Cell_ind
├── cell_id -> cgi
└── prb     -> prb
~~~

Planner 直接把 ID Predicate 下推到 Target Asset：

~~~sql
SELECT prb, cell_id
FROM Cell_ind
WHERE cell_id = ?;
~~~

规则：

~~~text
Filter Role = ID
Target Asset 覆盖 ID + Target Properties
→ DIRECT_SINGLE_ASSET / ID Direct Locate
~~~

---

## 3.5 CASE4：NAME 跨表，通过 ID 建立语义桥接

业务：

~~~text
查询 abc = "上研小区A" 的 PRB
~~~

语义：

~~~text
cgi [ID] ↔ abc [NAME]
~~~

Binding：

~~~text
dim_cell
├── cell_id   -> cgi
└── cell_name -> abc

Cell_ind
├── cell_id -> cgi
└── prb     -> prb
~~~

Planner 生成：

~~~text
DimensionResolutionStep
direction   = NAME_TO_ID
cardinality = SCALAR
placement   = FILTER
~~~

逻辑路径：

~~~text
abc(NAME)
   ↓ dim_cell
cgi(ID)
   ↓ Cell_ind
prb
~~~

同源子查询示例：

~~~sql
SELECT f.prb
FROM Cell_ind f
WHERE f.cell_id = (
    SELECT d.cell_id
    FROM dim_cell d
    WHERE d.cell_name = ?
);
~~~

数据源能力决定最终采用 SAME_SOURCE_JOIN、SAME_SOURCE_SUBQUERY 或 CROSS_SOURCE_DAG。

---

## 3.6 CASE5：NAME 与 Target 同表，直接查询

Binding：

~~~text
Cell_ind
├── name -> abc
├── id   -> cgi
└── prb  -> prb
~~~

QueryPropertySet 中的 NAME 与 Target Properties 由同一 Asset 完整覆盖，因此优先生成：

~~~text
DIRECT_SINGLE_ASSET
~~~

SQL：

~~~sql
SELECT prb, name
FROM Cell_ind
WHERE name = ?;
~~~

该路径保持查询阶段最少、物理资产数量最少。

## 3.7 CASE6：跨表 Bridge 的 ID Binding 完整性

Resolver：

~~~text
dim_cell
├── cell_id   -> cgi
└── cell_name -> abc
~~~

Target：

~~~text
Cell_ind
└── prb -> prb
~~~

跨表 DIMENSION Resolution 需要形成：

~~~text
Resolver Asset：NAME + ID
Target Asset：ID + Target Properties
~~~

当 Target Asset 的 ID Binding 待补齐时，Planner 输出：

~~~text
DIMENSION_TARGET_BINDING_NOT_FOUND
~~~

该错误直接指向需要补齐的伴生 ID Property Binding。

## 3.8 CASE7：多候选 Asset 的稳定选择

示例：

~~~text
dim_cell:
    cgi + abc

Cell_ind:
    cgi + prb

Sdr_perform:
    cgi + abc + prb
~~~

对于：

~~~text
查询 abc = "上研小区A" 的 PRB
~~~

Sdr_perform 完整覆盖 QueryPropertySet，生成 Direct Candidate。

Resolver Candidate 排序采用：

~~~text
1. NAME + ID 同时 Binding
2. 与 Target Asset 同数据源
3. 支持直接 Pushdown
4. Query / Resolution Property 覆盖度
5. Binding Route Priority
6. 稳定 Asset ID
~~~

完整 Physical Plan 排序采用：

~~~text
DIRECT_SINGLE_ASSET
    ↓
SAME_SOURCE_JOIN / SAME_SOURCE_SUBQUERY
    ↓
CROSS_SOURCE_DAG
~~~

同级计划继续比较 stageCount、assetCount、resolutionStepCount、bindingRoutePriority 与 stablePlanKey。

## 3.9 CASE8：多个 DIMENSION、多个单值过滤条件

对象存在：

~~~text
Cell：cgi [ID] ↔ abc [NAME]
Site：sid [ID] ↔ def [NAME]
~~~

OQL：

~~~sql
SELECT prb, abc, def
FROM obj
WHERE abc = "上研小区A"
  AND def = "XX站点"
  AND brand = "5G"
~~~

Planner 独立生成：

~~~text
ResolutionStep1：abc(NAME) → cgi(ID)
ResolutionStep2：def(NAME) → sid(ID)
普通 Predicate：brand = 5G
~~~

两个 semanticId 分别完成解析，再与普通 Predicate 合并为最终物理条件。

---

## 3.10 CASE9：IN 多值查询

OQL：

~~~sql
SELECT prb, abc, def
FROM obj
WHERE abc IN ("上研小区A", "上研小区B", "上研小区C")
  AND def = "XX站点"
  AND brand = "5G"
~~~

解析：

~~~text
abc IN (A, B, C)
→ A / B / C 分别执行 NAME_TO_ID
→ 合并为 ID Set
→ target.id IN (...)
~~~

DimensionResolutionStep：

~~~text
direction   = NAME_TO_ID
cardinality = SET
operator    = IN
placement   = FILTER
~~~

---

## 3.11 CASE10：LIKE 模糊查询

OQL：

~~~sql
SELECT prb, abc, def
FROM obj
WHERE abc LIKE "%上研%"
  AND def = "XX站点"
  AND brand = "5G"
~~~

LIKE 对 NAME 产生集合型解析：

~~~text
NAME LIKE pattern
→ Set<NAME>
→ Set<ID>
~~~

DimensionResolutionStep：

~~~text
direction   = NAME_TO_ID
cardinality = SET
operator    = LIKE
placement   = FILTER
~~~

每个命中的 NAME 按 1:1 语义解析为对应 ID。

---

## 3.12 CASE11：列表查询

场景：

~~~text
查询站点 A 下所有小区名称和 PRB
~~~

事实表保存 cell_id + prb，维度模型保存 cell_id + cell_name 时，Planner 通过 ID 关联恢复 NAME：

~~~sql
SELECT d.cell_name, f.prb
FROM dim_cell d
JOIN Cell_ind f
  ON d.cell_id = f.cell_id
ORDER BY f.prb
LIMIT 10;
~~~

列表查询结合 LIMIT 或聚合控制结果规模。

## 3.13 CASE12：GROUP BY / ORDER BY 使用 NAME

OQL：

~~~sql
SELECT def, SUM(prb)
FROM obj
GROUP BY def
~~~

事实表使用 site_id，维度模型提供 site_id ↔ site_name。

Planner 生成：

~~~text
DimensionResolutionStep
direction = ID_TO_NAME
placement = GROUP
~~~

同源 JOIN：

~~~sql
SELECT d.site_name, SUM(f.prb)
FROM Cell_site_ind f
JOIN dim_site d
  ON f.site_id = d.site_id
GROUP BY d.site_name;
~~~

GROUP BY 与 ORDER BY 都作为 DimensionResolutionStep 的正式 placement。

## 3.14 CASE13：跨数据源 NAME → ID → Target

数据源布局：

~~~text
dim_cell → GaussDB
Cell_ind → Hudi / Hive / API
~~~

Planner 生成 CROSS_SOURCE_DAG：

~~~text
Stage 1：GaussDB
NAME → ID Set
        ↓
Stage 2：Hudi / Hive / API
ID IN (...)
        ↓
Target Result
~~~

PhysicalStage 显式记录数据源、Asset 和依赖关系。

## 3.15 CASE14：ID / NAME 同时作为过滤条件

OQL：

~~~text
cgi = X
AND
abc = Y
~~~

OAC 执行一致性校验：

~~~text
resolve(Y) == X
~~~

结果：

~~~text
Y → X
    条件一致，继续执行

Y → Z 且 Z != X
    两个 Predicate 的交集为空，返回 0 rows
~~~

两个过滤条件都保留在查询语义中。

## 3.16 CASE15：运行时 1:1 数据语义校验

Scalar Resolution：

| Resolver 结果 | OAC 行为 |
|---:|---|
| 0 | DIMENSION_VALUE_NOT_FOUND |
| 1 | 正常进入后续 Stage |
| >1 | DIMENSION_VALUE_NOT_UNIQUE |

其中：

- 0 表示当前输入值没有对应业务实例；
- 1 表示符合 1:1 伴生语义；
- >1 表示数据质量与 OMS 声明的 1:1 语义存在偏差。

LIKE / Set Resolution 支持多个不同 NAME 分别解析到对应 ID。

## 3.17 CASE16：关系查询中的伴生标识

业务：

~~~text
查询站点名 A 下名为“上研小区A”的 Cell 的 PRB
~~~

OQL 示意：

~~~text
ASSOCIATION_QUERY Site -> Cell
WHERE Site.def = "A站点"
  AND Cell.abc = "上研小区A"
RETURN Cell.prb
~~~

规划顺序：

~~~text
Relationship Resolution
        ↓
定位 Site / Cell 对象范围
        ↓
Site 内部 def(NAME) → sid(ID)
Cell 内部 abc(NAME) → cgi(ID)
        ↓
Physical Query
~~~

Site 与 Cell 分别在各自 ObjectType 内完成 DIMENSION Resolution，Relationship Resolution 负责对象之间的关系定位。

## 3.18 规则归纳

CASE1～CASE16 可以归纳为四类统一规则：

| 规则层 | 统一规则 |
|---|---|
| Binding Topology | 单 Asset 全覆盖优先；跨 Asset 使用显式 DIMENSION 语义路径 |
| Dimension Resolution | FILTER 支持 NAME_TO_ID / ID Direct；RETURN / GROUP / ORDER 支持 ID_TO_NAME |
| Query Shape | EQ 对应 Scalar；IN / LIKE 对应 Set；多个 DIMENSION 独立解析后组合 |
| Physical Execution | 单表优先，其次同源 JOIN / SUBQUERY，再按数据源边界生成 CROSS_SOURCE_DAG |

OAC Planner 基于这四类规则统一生成 Physical Plan。

# 第四章 OAC Planner 详细设计

> 生产链路为：`ObjectRequest → DslServiceImpl.parseXxx → QueryContext（FilterNode 树 + ReturnItem + PropertyMapping）→ DslQuerySupport.generateQuery（按 DBType 路由）→ GeneratedQuery`。
> 注意：`oac-domain` 的 `com.huawei.ryoma.ontoaccess.query` 包是一套**尚未落地的新架构**（拆分策略 SplitStrategy / PhysicalPlan / DAG 引擎），当前生产查询仍走本章描述的旧架构。本章以旧架构为准，伴生标识（DIMENSION）新增能力也落到旧架构上。

## 4.1 规划输入：ObjectRequest

规划器输入为 `ObjectRequest`（`oac-common/model`），是 OQL 请求的入口模型：

~~~java
public class ObjectRequest {
    String version;                        // DSL 版本，如 1.8.0
    String schemaRef;                      // ontologyId / schemaId / ontologyVersionId
    OperationType operation;               // QUERY / AGGREGATE / ASSOCIATION_QUERY / MUTATE ...
    List<ObjectItem> objects;              // 对象引用（alias / objectType / by / byList / byComposite）
    List<RelationshipItem> relationships;  // 关系（relationshipType / from / to）
    Object conditions;                     // 统一条件表达式（扁平化，kind/ref/field/operator/values）
    List<ReturnItem> returns;              // 返回字段（kind/ref/fields/field/function/alias）
    Object having;                         // HAVING（AGGREGATE）
    AggregateFilter aggregateFilter;       // 聚合过滤（version 2.0）
    List<OrderItem> orders;                // 排序
    Object maxResults;                     // 分页（默认 100000）
    List<SourceQueryNode> sourceQuery;     // 子查询定义（version 2.0）
    Mutation mutation;                     // 写操作块
    Map<String, String> fieldPhysicalMap;  // ref:fieldName -> physicalColumnName
}
~~~

`ObjectRequest` 内置 **SQL 注入防护**：`IDENTIFIER_PATTERN`（标识符白名单）、`DANGEROUS_KEYWORDS`（危险关键字）、`DANGEROUS_CHARS`（危险字符）、条件最大递归深度 `MAX_CONDITION_DEPTH = 32`，并通过 `validateAggregateFilter()` 校验聚合过滤安全。

## 4.2 解析流程与 QueryContext（DslServiceImpl）

`DslServiceImpl`（`oac-domain/service`）是解析入口，将 `ObjectRequest` 解析为 `QueryContext`。

### 4.2.1 解析入口 buildQueryContext

~~~text
DslServiceImpl.buildQueryContext(ObjectRequest)
   1. initializeQueryContext(...)        // 解析 schemaRef/operation → datasourceType/schema/dataSourceId
   2. buildMetadataMapForQueryContext    // objectType -> ObjectTypeMetadata
   3. parseObjects(...)                  // objects -> List<ObjectItemInfo>（含 primaryKeys/schema/sourceTable）
   4. buildFieldMappingsContext          // fieldMappings（alias.column -> PropertyMapping）
   5. parseQueryClauses(...)             // 解析 conditions/orderBy/maxResults/relationships/聚合/写操作
~~~

主入口方法：

~~~java
public GeneratedQuery translateGql(ObjectRequest objectRequest) {
    QueryContext context = buildQueryContext(objectRequest);
    dslQuerySupport.generateQuery(context);          // 生成查询（见 4.5）
    GeneratedQuery generated = context.getGeneratedQuery();
    ...
    return generated;
}
~~~

`QueryContext`（`oac-common/pojo`）是规划核心上下文：

~~~java
public class QueryContext {
    String operationType;                  // 操作类型
    String datasourceType;                 // DBType（nebula/mysql/gaussdb/adc/rest/dac_sparksql ...）
    String schemaRef, schema, tableName, dataSourceId;
    com.alibaba.druid.DbType druidDbType;  // SQL 方言
    List<ObjectItemInfo> objects;          // 对象
    List<RelationshipInfo> relationships;  // 关系
    List<FilterNode> filters;              // 过滤树（见 4.2.2）
    List<ReturnItem> returns;              // 返回树（见 4.2.3）
    List<String> fields;                   // 返回字段（alias.field）
    List<OrderBy> orderBy;                 // 排序
    Pagination pagination; Integer maxResults; Boolean distinct;
    Map<String, PropertyMapping> fieldMappings;  // 属性映射（见 4.2.4）
    Map<String, ObjectTypeMetadata> metadataMap; // 对象元数据
    Map<String, RelationTypeMetadata> relationMetadataMap; // 关系元数据
    GeneratedQuery generatedQuery;         // 生成结果
    // 聚合：aggregateFields / groupByFields / having / aggregateFilter
    // 写操作：mutationOperation / mutationProperties / mutationSet ...
}
~~~

### 4.2.2 FilterNode 过滤树

`parseConditions` 将 `conditions` 解析为 `FilterNode` 树：

~~~java
public class FilterNode {
    String kind;                            // PREDICATE / GROUP
    String relation;                        // AND / OR
    FilterOperator operator;                // EQ/NEQ/GT/GTE/LT/LTE/IN/NOT_IN/BETWEEN/CONTAINS/LIKE/...
    String ref;                             // 对象或关系 alias
    String field;                           // 字段名
    Object value; List<Object> values;      // 单值 / 多值
    FilterNode subquery;                    // EXISTS/NOT_EXISTS 或 IN 子查询
    List<FilterNode> children;              // AND/OR 子节点
    FilterFunction function;                // 左侧函数（如 LENGTH(u.NAME)）
}
~~~

`FilterOperator` 枚举覆盖 `EQ / NEQ / GT / GTE / LT / LTE / IN / NOT_IN / BETWEEN / NOT_BETWEEN / CONTAINS / NOT_CONTAINS / LIKE / NOT_LIKE / STARTS_WITH / ENDS_WITH / IS_NULL / IS_EMPTY / AND / OR / NOT / EXISTS / NOT_EXISTS`。DSL 操作符字符串（`= / != / IN / LIKE / AND / OR ...`）通过 `parseOperator` 归一化为枚举。

### 4.2.3 ReturnItem 返回树

`returns` 使用 `ReturnItem`，按 `kind` 区分：

~~~java
public class ReturnItem {
    ReturnKind kind;                        // FIELDS / GROUP_BY / METRIC / FUNCTION / EXPR
    String ref;                             // alias（对象或关系）
    List<String> fields;                    // FIELDS 的字段列表
    String field;                           // GROUP_BY / METRIC 的字段
    ReturnFunction function;                // 聚合函数（SUM/COUNT/AVG/...）
    String name;                            // FUNCTION 名
    List<FunctionArg> args;                 // 函数参数（FIELD/VALUE/EXPR）
    String alias;                           // 别名
    ReturnItem expr;                        // EXPR 嵌套表达式
    Map<String, String> physicalToLogicalFieldMap; // 物理字段 -> 逻辑字段
}
~~~

聚合查询（AGGREGATE）由 `parseAggregateQuery` / `parseAggregateFilter` 解析，`returns` 含 `GROUP_BY` 与 `METRIC` 两类，`aggregateFilter`（语义等价 HAVING）经 `validateAggregateFilter` 安全校验后写入 `QueryContext`。

### 4.2.4 PropertyMapping 属性映射

`fieldMappings` 建立「本体属性 → 物理字段」映射，是语义等价转换的基础：

~~~java
public class PropertyMapping {
    String propertyId;                      // 属性 ID
    String bindingId;                       // 绑定 ID
    String dataSourceId;                    // 数据源 ID
    String dataSourceType;                  // mysql/nebula/postgresql/elasticsearch/carbon ...
    String schema;                          // 库/图空间
    String table;                           // 表名 / Tag
    String column;                          // 物理列/字段名
    boolean primaryKey;                     // 是否主键
    String propertyType;                    // 属性类型
    Map<String, String> nestedMapping;      // ES 嵌套字段
}
~~~

`fieldMappings` 的 key 形如 `alias.column`（如 `cell.cellName`），value 为 `PropertyMapping`，是生成器将逻辑字段转换为物理字段的唯一依据。

## 4.3 元数据解析（MetadataResolver）

`MetadataResolver`（`oac-domain/service`）负责从 OMS 读取对象/关系元数据：

~~~java
public interface MetadataResolver {
    ObjectTypeMetadata resolveObjectType(String objectType, String ontologyId);
    RelationTypeMetadata resolveRelationType(String relationType, String ontologyId,
        String sourceObjectTypeId, String targetObjectTypeId);
    List<SubQueryContext> partition(QueryContext context,
        Map<String, ObjectTypeMetadata> metadataMap,
        Map<String, RelationTypeMetadata> relationMetadataMap);   // 按数据源/表分组
    OntologyRelationship fetchOntologyRelationship(...);
    OntologyDataSource fetchOntologyDataSource(...);

~~~

`ObjectTypeMetadata` 携带 `propertyMappings`（属性 → PropertyMapping）与 `primaryKeys`；`RelationTypeMetadata` 携带 `junctionTableName`、`junctionMappings`（关系两端字段）。这些元数据是 `fieldMappings` 的来源，也是伴生标识识别的元数据入口（见 4.6）。

## 4.4 多数据源分区（SubQueryPartitioner）

跨数据源/多表查询通过 `DslServiceImpl.initMultiQueryContext` 触发分区：

~~~text
initMultiQueryContext(ObjectRequest)
   └─ buildQueryContext(...)
   └─ metadataResolver.partition(context, metadataMap, relationMetadataMap)
        └─ 按 schema+table 分组，生成 List<SubQueryContext>
   └─ 对每个 SubQueryContext 调用 dslQuerySupport.generateQuery
~~~

`SubQueryContext` 继承 `QueryContext`，携带 `joinTables`、`joinMappings`、`tableJoinSort`、`globalOrderBy`、`primaryKeys`、`auxiliaryFiled` 等，供 `AbstractSqlGenerator` 生成同源 JOIN 或跨源多子查询。分区是跨源合并（见 5.5）的前置步骤。

## 4.5 查询生成路由（DslQuerySupport）

`DslQuerySupport.generateQuery`（`oac-domain/generator`）按 `dbType` 路由到对应生成器：

~~~java
public void generateQuery(QueryContext context) {
    String dbType = context.getDatasourceType();
    if (NEBULA_GRAPH.equals(dbType)) {
        // 图数据库 → GQL
        QueryGenerator g = generatorFactory.getGeneratorByName(context.getOperationType());
        context.setGeneratedQuery(g.generateQuery(context));
    } else if (isAdcDatasource(dbType)) {
        // ADC → TQL
        QueryGenerator g = tqlGeneratorFactory.getGeneratorByName(context.getOperationType());
        context.setGeneratedQuery(g.generateQuery(context));
    } else if (REST.equalsIgnoreCase(dbType)) {
        // REST → ExecutionRequest
        QueryGenerator g = thirdPartyQueryGeneratorFactory.getGeneratorByName(context.getOperationType());
        context.setGeneratedQuery(g.generateQuery(context));
    } else {
        // SQL 家族（mysql/gaussdb/pg/carbon/...）→ Druid AST
        context.setDruidDbType(initDbType(dbType));
        QueryGenerator g = sqlQueryGeneratorMap.get(Pair.of(dbType, context.getOperationType()));
        if (g == null) g = sqlQueryGeneratorMap.get(Pair.of(QueryGenerator.DEFAULT_TYPE, context.getOperationType()));
        context.setGeneratedQuery(g.generateQuery(context));
    }
    // 回填 objectsAlias / relationshipsAlias / relationshipEndpoints / primaryKeys / orderBy / originalFields
}
~~~

路由表：

| dbType | 工厂 | 生成器 | 产物 |
|---|---|---|---|
| `NEBULA_GRAPH` | `DslConvertFactory` | NebulaGraphQueryGenerator / AssociationQueryGenerator / AggregateQueryGenerator / MutationGenerator | GQL |
| `ADC` | `TqlGeneratorFactory` | TqlQueryGenerator / TqlAggregateGenerator / TqlAssociationQueryGenerator | TQL |
| `REST` | `ThirdPartyQueryGeneratorFactory` | ThirdPartyQueryGenerator | ExecutionRequest |
| `DAC_SPARKSQL` | `DacJsonBuild`（独立入口 translateDacJson） | — | DAC JSON |
| 其它（mysql/gaussdb/pg/carbon...） | `sqlQueryGeneratorMap` | AbstractSqlGenerator 家族（按 `dbType` + `operationType`） | SQL（Druid AST 防注入） |

`sqlQueryGeneratorMap` 在 `@PostConstruct` 中以 `Pair<supportedType, supportedOperation>` 为键注册所有 `AbstractSqlGenerator` 子类，未命中时回退 `DEFAULT_TYPE`。

## 4.6 伴生标识（DIMENSION）解析设计（新增能力）

本小节给出 ID / NAME 伴生标识能力在**旧架构解析阶段**的代码设计方案。

### 4.6.1 接入点

伴生标识的语义来源是 OMS（第一章）：`Property` 增加 `semanticTypes` + `dimensionSemantic`（`semanticId / idPropertyId / namePropertyId`）。OAC 侧通过 `ObjectTypeMetadata.propertyMappings` 读取，无需新增数据源调用。

### 4.6.2 PropertyMapping 扩展

`PropertyMapping` 增加伴生语义字段：

~~~java
public class PropertyMapping {
    // ... 现有字段 ...
    private List<String> semanticTypes;          // 新增：如 ["DIMENSION"]
    private DimensionSemantic dimensionSemantic; // 新增：伴生语义
}
~~~

`DimensionSemantic` / `DimensionRole`：

~~~java
public class DimensionSemantic {
    private String semanticId;       // 伴生关系唯一标识
    private String idPropertyId;     // ID 端 Property
    private String namePropertyId;   // NAME 端 Property
}
public enum DimensionRole {
    ID, NAME, NONE;
    public static DimensionRole of(String propertyId, DimensionSemantic s) {
        if (s == null) return NONE;
        if (propertyId.equals(s.getIdPropertyId())) return ID;
        if (propertyId.equals(s.getNamePropertyId())) return NAME;
        return NONE;
    }
}
~~~

### 4.6.3 QueryContext 扩展

`QueryContext` 增加解析步骤承载，供生成器消费：

~~~java
public class QueryContext {
    // ... 现有字段 ...
    private List<DimensionResolutionStep> dimensionResolutionSteps;  // 新增
}

class DimensionResolutionStep {
    String semanticId;
    ResolutionDirection direction;     // NAME_TO_ID / ID_TO_NAME
    ResolutionCardinality cardinality; // SCALAR / SET
    String sourcePropertyId;           // 源属性（NAME 或 ID）
    String targetPropertyId;           // 目标属性（ID 或 NAME）
    QueryPropertyUsage placement;      // FILTER / RETURN / GROUP / ORDER
    String resolverTable;              // 解析端物理表（覆盖 NAME + ID）
    String targetTable;                // 目标端物理表（覆盖 ID + Target）
}
~~~

方向 / 基数 / 位置对应关系：

| Query Shape | direction | cardinality | placement |
|---|---|---|---|
| `NAME = X` | NAME_TO_ID | SCALAR | FILTER |
| `NAME IN (...)` | NAME_TO_ID | SET | FILTER |
| `NAME LIKE pattern` | NAME_TO_ID | SET | FILTER |
| `RETURN NAME`（事实仅 ID） | ID_TO_NAME | SCALAR/SET | RETURN |
| `GROUP BY / ORDER BY NAME` | ID_TO_NAME | SET | GROUP / ORDER |

### 4.6.4 解析流程扩展

`DslServiceImpl.parseConditions` / `parseFieldsForQuery` 解析后，追加伴生标识识别步骤：

~~~text
resolveDimensionSteps(QueryContext context)
   1. 遍历 filters / returns / orderBy 中的属性，判定 DimensionRole
   2. role == NAME 且该属性需跨表解析（NAME 与 Target 不在同一物理表）
        → 生成 NAME_TO_ID 解析步骤
   3. 从 metadataMap 的 propertyMappings 定位 resolverTable（NAME+ID）与 targetTable（ID+Target）
   4. 任一缺失 → 抛 DIMENSION_RESOLUTION_BINDING_NOT_FOUND / DIMENSION_TARGET_BINDING_NOT_FOUND
   5. 步骤写入 context.dimensionResolutionSteps
~~~

解析端 / 目标端物理表判定：

~~~text
resolverTable = 同时覆盖 nameProperty + idProperty 的物理表
targetTable   = 覆盖 { idProperty } ∪ 非过滤属性的物理表
~~~

同源（resolverTable == targetTable 或同数据源）时由 `AbstractSqlGenerator` 生成子查询/JOIN（见 5.6.2）；跨源时由 `initMultiQueryContext` 分区为多 `SubQueryContext` 分阶段执行（见 5.6.3）。

### 4.6.5 规划输出

规划器最终输出 `GeneratedQuery`（`QueryContext.generatedQuery`），其中携带伴生解析信息：

~~~text
QueryContext
├── filters / returns / orderBy           // 解析后的业务语义
├── fieldMappings                          // 属性 → 物理字段映射
├── dimensionResolutionSteps[]             // 伴生解析步骤（新增）
└── generatedQuery                         // 生成结果（见 5.2）
~~~

`GeneratedQuery` 的 `relationshipEndpoints`、`objectsAlias`、`columnAliasMapping`、`executeEnvelope` 等字段为执行与结果合并提供元信息。

# 第五章 Translator 与执行

> 本章基于 OAC **生产落地代码**的真实实现刷新。Translator 由查询生成器体系承担（`QueryGenerator` / `AbstractSqlGenerator` 家族 / GQL / TQL / ThirdParty / DAC），产出 `GeneratedQuery`；执行由 `QueryExecutor`（Default 串行 / Parallel 并发）经 `DataSourceConnector` 落到真实数据源，返回 `SourceResult`；跨源结果由 `ResultMergerUtils` 内存合并。
> 注意：`oac-domain` 的 `query` 包（新架构 Translator SPI / ExecutionEngine / DAG 引擎）尚未落地，本章以旧架构为准。

## 5.1 查询生成器体系（QueryGenerator）

生成器接口统一将 `QueryContext` 翻译为 `GeneratedQuery`：

~~~java
public interface QueryGenerator {
    String DEFAULT_TYPE = "default";
    GeneratedQuery generateQuery(QueryContext context);
    default String getSupportedType() { return DEFAULT_TYPE; }
    String getSupportedOperation();
}
~~~

### 5.1.1 生成器抽象基类

~~~text
AbstractQueryGenerator       // GQL 公共基类：buildWhereClause/buildOrderByClause/buildLimitClause/buildGqlFilter
   └─ AbstractCommonGenerator  // SQL 与 GQL 公共逻辑
        └─ AbstractSqlGenerator  // SQL 生成器（Druid AST 防注入）
             ├─ GeneralSqlGenerator / AggregateSqlGenerator / AssociationQuerySqlGenerator
             ├─ CreateSqlGenerator / DeleteSqlGenerator / UpdateSqlGenerator / MutationGenerator
             └─ MultiObjectQueryGenerator / InnerSourceQueryCreateSqlGenerator
~~~

`AbstractQueryGenerator.generateQuery` 统一模板：

~~~text
buildQuery(context)            → StringBuilder 查询语句
buildParameters(filters)       → 收集过滤值作为参数
→ GeneratedQuery { result, type, parameters, dataSourceId, operationType, schema, objectType }
~~~

### 5.1.2 SQL 生成器家族（AbstractSqlGenerator，Druid AST）

`AbstractSqlGenerator`（继承 `AbstractCommonGenerator`）使用 **Druid AST** 拼接 SQL，从源头防注入：

~~~text
generateQuery(context)
   ├─ needJoin ? doGenerateQueryWithJoin : doGenerateQuery
   ├─ doGenerateQuery = buildSelect + buildFromSql + buildWhere + buildGroupBy + buildAggregateFilter + buildOrder + buildPagination
   ├─ buildWhere：FilterNode 树 → SQLExpr（SQLBinaryOpExpr / SQLPropertyExpr / SQLInListExpr / SQLAggregateExpr）
   ├─ buildFunctionSelectItem：FUNCTION/EXPR 类型 → SQLMethodInvokeExpr，字段引用统一 SQLPropertyExpr
   └─ buildColumnAliasMapping：大写列名 → 原始别名（结果还原用）
~~~

关键安全设计：字段引用一律 `SQLPropertyExpr(ref, field)`、常量一律 `createValueExpr(value)`，杜绝字符串拼接注入；时间函数（`DATE_TRUNC / DATE_ADD / DATEDIFF / YEAR...`）按 `dbType`（mysql / gaussdb / postgresql）适配方言；`resolveFilterRefToTableAlias` 将逻辑 alias 解析为物理表别名。

SQL 生成器按 `dbType + operationType` 注册进 `sqlQueryGeneratorMap`（见 4.5）。

### 5.1.3 GQL / TQL / ThirdParty / DAC 生成器

| 数据源 | 工厂 | 生成器 | 产物 |
|---|---|---|---|
| NEBULA_GRAPH | `DslConvertFactory` | NebulaGraphQueryGenerator / AssociationQueryGenerator / AggregateQueryGenerator / MutationGenerator | GQL |
| ADC | `TqlGeneratorFactory` | TqlQueryGenerator / TqlAggregateGenerator / TqlAssociationQueryGenerator | TQL |
| REST | `ThirdPartyQueryGeneratorFactory` | ThirdPartyQueryGenerator | ExecutionRequest |
| DAC_SPARKSQL | `DacJsonBuild` | —（`translateDacJson` 独立入口） | DAC JSON |

图数据库通过 REST 调 graph-proxy，SQL（mysql/pg）通过 yacht 查询（见 5.4 `DataSourceConnector` 注释）。

## 5.2 生成结果（GeneratedQuery）

`GeneratedQuery`（`oac-common/pojo`）是 Translator 产物、Executor 输入：

~~~java
public class GeneratedQuery {

    String schema;                          // schema
~~~

## 5.3 执行器（QueryExecutor）

`QueryExecutor`（`oac-infrastructure/executor`）接口：

~~~java
public interface QueryExecutor {
    QueryResult executeQuery(ExecutionContext executionContext);  // 批量执行
    SourceResult executeQuery(GeneratedQuery query);              // 单条执行
}
~~~

两种实现：

| 实现 | 模式 | 说明 |
|---|---|---|
| `DefaultQueryExecutor` | 串行 | 顺序遍历 `executionContext.getQueries()`，逐条执行 |
| `ParallelQueryExecutor` | 并发 | `CompletableFuture` 并发执行，线程池 `ontology.executor.query.thread`（默认 10），超时 `ontology.executor.query.timeOut`（默认 10s），租户上下文透传 |

两者均通过 `DataSourceConnectorSupport.getConnector(query.getType())` 获取连接器后执行：

~~~text
DefaultQueryExecutor.executeQuery(GeneratedQuery)
   → dataSourceConnectorSupport.getConnector(query.getType())
   → connector.executeQuery(query)
   → SourceResult
~~~

## 5.4 数据源连接器（DataSourceConnector）

`DataSourceConnector`（`oac-infrastructure/connector/datasource`）是真实数据通道的抽象：

~~~java
public interface DataSourceConnector {
    SourceResult executeQuery(GeneratedQuery query);
    DBType dbType();
}
~~~

`DataSourceConnectorSupport` 按 `DBType` 路由到具体连接器：

| 连接器 | DBType |
|---|---|
| `MysqlDataSourceConnector` | mysql |
| `GaussV3DataSourceConnector` | gaussdb100v3r1 |
| `PostgreSQLDataSourceConnector` | postgresql / gaussdb |
| `SparkSqlDataSourceConnector` | spark-sql / carbon |
| `ClickhouseDataSourceConnector` | clickhouse |
| `AdcDataSourceConnector` | adc |
| `AbstractDataSourceConnector` | 公共基类 |

图数据库（nebula）通过 REST 调 graph-proxy，关系库（mysql/pg）通过 yacht 查询。

## 5.5 源结果与跨源合并（SourceResult / ResultMergerUtils）

### 5.5.1 SourceResult

`SourceResult`（`oac-infrastructure/result`）是单数据源查询结果：

~~~java
public class SourceResult {
    List<ResponseRequest.DataItem> data;        // 数据项
    List<ResponseRequest.DataItem> objects;     // 对象
    List<ResponseRequest.DataItem> relationships; // 关系
    boolean success;
    int errorCode; String errorMessage;
    int totalCount;
}
~~~

### 5.5.2 跨源内存合并（ResultMergerUtils）

`ResultMergerUtils.mergeSourceResult`（`oac-interfaces/utils`）合并多子查询结果：

~~~text
mergeSourceResult(List<DslTaskResult> subResults, function)
   1. filterValidResults            // 过滤空结果
   2. 单结果 → 直接返回
   3. shouldRelationshipJoin ?      // GeneratedQuery.supportJoin()
        relationshipJoin(...)       // 关联合并：innerJoin 两端 + 移除 auxiliaryFiled
      : simpleMerge(...)            // 简单合并：按 rid 归并 properties + 补缺失字段 + 全局排序
~~~

`mergeSourceResultForAggregate` 针对聚合结果（无 rid）按 objectType 归并并补全字段。跨源场景下，`DslServiceImpl.initMultiQueryContext` 分区的多个 `SubQueryContext` 各自生成 `GeneratedQuery`，并行执行后由 `ResultMergerUtils` 完成内存合并（关联合并走 `ListMapInnerJoinUtils.innerJoin`）。

## 5.6 伴生标识的翻译与执行设计（新增能力）

本小节给出 ID / NAME 伴生标识能力在**旧架构翻译与执行阶段**的代码设计方案。

### 5.6.1 生成器扩展

`AbstractSqlGenerator` 家族增加伴生解析的语句构建能力。当 `QueryContext.dimensionResolutionSteps` 非空且 `direction = NAME_TO_ID` 时：

NAME→ID 子查询下推（同源单表，SQL）：

~~~sql
SELECT f.prb
FROM cell_ind f
WHERE f.cell_id = (
    SELECT d.cell_id
    FROM dim_cell d
    WHERE d.cell_name = ?
);
~~~

NAME→ID 集合下推（IN 多值）：

~~~sql
SELECT f.prb
FROM cell_ind f
WHERE f.cell_id IN (
    SELECT d.cell_id
    FROM dim_cell d
    WHERE d.cell_name IN (?, ?, ?)
);
~~~

ID→NAME 结果恢复（同源 JOIN）：

~~~sql
SELECT f.prb, d.cell_name AS cellName
FROM cell_ind f
JOIN dim_cell d
  ON f.cell_id = d.cell_id
WHERE ...;
~~~

生成器扩展方法：

~~~java
// AbstractSqlGenerator 新增
protected String buildDimensionSubquery(QueryContext context, DimensionResolutionStep step);
protected String buildDimensionJoin(QueryContext context, DimensionResolutionStep step);
~~~

GQL 侧（`AbstractQueryGenerator`）通过 `buildGqlFilter` 的字段映射支持 ID→NAME 反查，或在 `RETURN` 中挂接维度反查。

### 5.6.2 同源解析

resolverTable 与 targetTable 同数据源时，由单个 `SubQueryContext` 生成单条 SQL/GQL，通过子查询/JOIN 一次完成解析，不拆多子查询。

### 5.6.3 跨源分阶段执行

跨源 NAME→ID→Target 场景复用 `initMultiQueryContext` 分区 + 并行执行 + 结果合并：

~~~text
Stage 1（resolverTable，如 GaussDB dim_cell）
   NAME → ID Set（执行 NAME 过滤，投影 ID）
        ↓
Stage 2（targetTable，如 Hudi cell_ind）
   ID IN (...) 条件，查询 Target 属性
        ↓
ResultMergerUtils 合并（ID 关联）
~~~

`SubQueryContext` 携带的分区信息与 `GeneratedQuery.globalOrderBy` 支持跨源排序；`SourceResult.objects/relationships` 由 `ResultMergerUtils` 按关系端点归并。

### 5.6.4 1:1 运行时校验

Stage 1 对单个 NAME 输入执行唯一性校验：

| 解析结果 | 行为 |
|---:|---|
| 0 | 返回 `DIMENSION_VALUE_NOT_FOUND` |
| 1 | 正常进入 Stage 2 |
| >1 | 返回 `DIMENSION_VALUE_NOT_UNIQUE` |

校验落在 `DataSourceConnector.executeQuery` 返回 `SourceResult` 之后的解析校验钩子，或由生成器在 SQL 中追加 `COUNT` 校验子查询。

### 5.6.5 结果语义恢复

OQL 返回 NAME 而事实查询仅投影 ID 时，通过 ID→NAME 解析恢复：

~~~text
1. 同源：ID→NAME JOIN（buildDimensionJoin）一次返回 NAME
2. 跨源：Stage 2 结果按 ID 批量 lookup NAME（追加恢复子查询，ResultMergerUtils 合并）
~~~

返回字段别名通过 `GeneratedQuery.columnAliasMapping` 与 `ReturnItem.physicalToLogicalFieldMap` 还原业务字段名。

### 5.6.6 新增类清单

| 层 | 新增类 / 扩展点 | 说明 |
|---|---|---|
| 模型 | `DimensionSemantic`、`DimensionRole` | 伴生语义与角色 |
| 模型 | `PropertyMapping.semanticTypes / dimensionSemantic` | 属性映射扩展 |
| 解析 | `QueryContext.dimensionResolutionSteps` | 解析步骤承载 |
| 计划 | `DimensionResolutionStep`、`ResolutionDirection`、`ResolutionCardinality` | 解析步骤模型 |
| 解析 | `DslServiceImpl` 扩展 | 伴生关系识别 |
| 生成 | `AbstractSqlGenerator` / `AbstractQueryGenerator` 扩展 | 子查询/JOIN 构建 |
| 执行 | `DslServiceImpl.initMultiQueryContext` + `ResultMergerUtils` 复用 | 跨源分阶段合并 |

# 第六章 多标识解析与物理查询组装（对接场景设计）

> 本章基于 OAC **生产落地代码**（`DslQuerySupport.generateQuery` 按 `DBType` 路由到五类生成器）设计多标识（ID / NAME 伴生）解析下的物理查询组装方案。
> 五类对接场景：**Yacht 类 MySQL**、**ADC 接口（TQL）**、**三方物理模型接口（REST）**、**图数据库（NEBULA_GRAPH）**、**DAC**。
> 通用前提沿用第四章 4.6 与第五章 5.6：`DimensionSemantic`（semanticId / idPropertyId / namePropertyId）、`DimensionRole`（ID / NAME / NONE）、`DimensionResolutionStep`（direction / cardinality / placement / resolverTable / targetTable）、`PropertyMapping` 扩展（semanticTypes / dimensionSemantic）、`QueryContext.dimensionResolutionSteps`。

## 6.1 通用组装模型

多标识解析在物理查询组装层的统一表达：

~~~text
QueryContext
├── dimensionResolutionSteps[]        // 伴生解析步骤（Planner 产出，见 4.6）
├── fieldMappings                      // 属性 → 物理字段映射（PropertyMapping 携带 dimensionSemantic）
└── datasourceType                     // DBType：决定路由到哪类生成器
        ↓
DslQuerySupport.generateQuery 按 DBType 路由
        ↓
┌───────────────┬────────────────┬───────────────┬────────────────┬──────────────┐
│ Yacht MySQL   │ ADC (TQL)      │ REST (三方)    │ NEBULA_GRAPH   │ DAC          │
│ AbstractSql   │ AbstractTql    │ ThirdParty     │ AbstractGql    │ DacJsonBuild │
│ Generator     │ Generator      │ Generator      │ Generator      │              │
└───────────────┴────────────────┴───────────────┴────────────────┴──────────────┘
        ↓
GeneratedQuery { result / executeEnvelope / ... }
~~~

两类解析形态：

| 形态 | 方向 | 组装方式 |
|---|---|---|
| NAME→ID | NAME 过滤，目标存 ID | 子查询 / JOIN 下推，或分阶段解析 |
| ID→NAME | 返回 NAME，事实存 ID | JOIN 恢复，或维度反查 |

## 6.2 对接 Yacht 类 MySQL（AbstractSqlGenerator）

### 6.2.1 载体与通道

- 载体：SQL（标准 SELECT / JOIN / 子查询）
- 生成器：`AbstractSqlGenerator` 家族（`GeneralSqlGenerator` / `AggregateSqlGenerator` / `AssociationQuerySqlGenerator`），**Druid AST 拼接防注入**
- 执行通道：`MysqlDataSourceConnector` → yacht 查询
- 字段引用：`SQLPropertyExpr(alias, column)`，常量 `createValueExpr`，杜绝字符串拼接

### 6.2.2 NAME→ID 子查询下推（同源单 Stage）

维度表与事实表同库时，单条 SQL 内子查询下推：

~~~sql
SELECT f.prb
FROM cell_ind f
WHERE f.cell_id = (
    SELECT d.cell_id
    FROM dim_cell d
    WHERE d.cell_name = ?
);
~~~

NAME→ID 集合（IN 多值）：

~~~sql
SELECT f.prb
FROM cell_ind f
WHERE f.cell_id IN (
    SELECT d.cell_id
    FROM dim_cell d
    WHERE d.cell_name IN (?, ?, ?)
);
~~~

### 6.2.3 ID→NAME 结果恢复（同源 JOIN）

~~~sql
SELECT f.prb, d.cell_name AS cellName
FROM cell_ind f
JOIN dim_cell d
  ON f.cell_id = d.cell_id
WHERE ...;
~~~

### 6.2.4 跨源分阶段

维度表（GaussDB）与事实表（MySQL）不同源时，由 `initMultiQueryContext` 分区为两个 `SubQueryContext`：

~~~text
Stage 1（GaussDB dim_cell）：SELECT cell_id FROM dim_cell WHERE cell_name = ?
Stage 2（MySQL cell_ind）：SELECT prb FROM cell_ind WHERE cell_id IN (...)
ResultMergerUtils 合并
~~~

生成器扩展点：`AbstractSqlGenerator` 新增 `buildDimensionSubquery` / `buildDimensionJoin`（见 5.6.1），在 `buildWhere` / `buildFrom` 中根据 `dimensionResolutionSteps` 织入子查询/JOIN。

## 6.3 对接 ADC 接口（TQL）

### 6.3.1 载体与通道

- 载体：TQL（类 SQL 方言），由 `AbstractTqlGenerator`（Druid AST）生成
- 生成器：`TqlGeneratorFactory` → `TqlQueryGenerator` / `TqlAggregateGenerator` / `TqlAssociationQueryGenerator`
- TQL 语法特征：表引用 `/schema/table`（`toTqlSchemaTable`）、字段引用 `"字段"`（`toTqlIdentifier`）、分页 `START offset LIMIT n`、字符串匹配 `CONTAINS` / `STARTS` / `ENDS`、时间间隔 `1D` / `1M`（`convertToTqlInterval`）

### 6.3.2 NAME→ID 同源 JOIN（TQL）

ADC 维度模型与指标模型同源时，TQL 内 JOIN 下推：

~~~sql
SELECT f."prb", d."cell_name" AS cellName
FROM "/project/module/cell_ind" f
JOIN "/project/module/dim_cell" d
  ON f."cell_id" = d."cell_id"
WHERE d."cell_name" = ?
~~~

### 6.3.3 跨源 / 维值预解析

ADC 维度模型与指标模型分离时，先解析维值再查指标：

~~~text
Stage 1：TQL 查维度模型 → ID 集合
Stage 2：TQL 查指标模型，WHERE id IN (...) 或过滤维值
~~~

字段引用统一带引号，由 `toTqlIdentifier` 处理，防注入沿用 Druid AST。

## 6.4 对接三方物理模型接口（REST）

### 6.4.1 载体与通道

- 载体：`ExecuteEnvelope`（`ExecutionRequest` + `BindingBundle`）
- 生成器：`ThirdPartyQueryGenerator`（要求 `SubQueryContext` 且 `DBType.REST`）
- 关键动作：`pruneDataSource` 按查询所需属性裁剪 `OntologyDataSource`，只保留 `requiredProperties` 对应的 `PropertyBindings` 与 `CatalogContext`（`fields`/`datasets`/`schemas`/`dataSources` 沿 `parentAssetId` 链裁剪）

~~~java
ExecuteEnvelope envelope = ExecuteEnvelope.builder()
    .request(executionRequest)          // version/operation/objects/conditions/returns/orders/maxResults
    .bindings(bindingBundle)            // request: List<OntologyDataSource>, bindings: []
    .build();
~~~

### 6.4.2 多标识解析策略

三方物理模型接口能力有限，通常只能按对方约定的字段过滤。多标识解析按三方模型的绑定完备性分两种：

~~~text
1. 三方模型同时绑定 ID 与 NAME（可直接按 NAME 过滤目标）
   → 直接下推 NAME 过滤（ExecutionRequest.conditions 携带 NAME 条件），无需解析

2. 三方模型仅绑定 ID，NAME 需经维度服务解析
   → Stage 1：调维度接口（ExecutionRequest）NAME→ID
   → Stage 2：调事实接口（ExecutionRequest）ID IN (...) 过滤
   → 两个 ExecuteEnvelope 分阶段执行
~~~

`pruneDataSource` 在多标识场景下需额外保留伴生两端属性（NAME 端 + ID 端）的绑定，避免裁剪掉解析所需字段。

## 6.5 对接图数据库（NEBULA_GRAPH）

### 6.5.1 载体与通道

- 载体：GQL（MATCH / WHERE / RETURN / ORDER BY / LIMIT）
- 生成器：`DslConvertFactory` → `NebulaGraphQueryGenerator` / `AssociationQueryGenerator` / `AggregateQueryGenerator`（模板方法：`buildMatchPattern` → WHERE → RETURN）
- 字段引用：`alias.ObjectType.field`，返回 `id(alias) AS alias_vid`、`alias.ObjectType.field AS ...`

### 6.5.2 NAME→ID 图内解析

图数据库天然支持属性过滤与多跳关联，伴生解析体现为 MATCH 模式与 WHERE 条件：

~~~text
场景 A：NAME 与 ID 同属一个 Tag（同一 vertex）
   MATCH (v:cell) WHERE v.cell.cell_name == "上研小区A" RETURN id(v) AS v_vid, v.cell.prb
   → 直接按 NAME 过滤，无需解析（ID 即 vid）

场景 B：维度 vertex 与事实 vertex 通过边关联
   MATCH (d:dim_cell)-[:belongs_to]->(f:cell_ind)
   WHERE d.dim_cell.cell_name == "上研小区A"
   RETURN f.cell_ind.prb, id(d) AS d_vid
   → 通过边一次关联完成 NAME→ID→Target
~~~

### 6.5.3 ID→NAME 结果恢复

~~~text
MATCH (f:cell_ind)
RETURN f.cell_ind.prb, f.cell_ind.cell_name AS cellName
（事实 Tag 内已含 NAME 属性时直接返回；否则经边反查维度 Tag 的 NAME）
~~~

图数据库是唯一可"单跳关联完成解析"的通道，天然支撑 CASE16 关联查询中的伴生标识。

## 6.6 对接 DAC

### 6.6.1 载体与通道

- 载体：DAC JSON（`DacJsonContext`），顶层结构 `action/operation + columns + conditions`（聚合场景 `AGGRE_SDR` 无 `cubes`）
- 生成器：`DacJsonBuild`（`translateDacJson` 独立入口）
- 关键：操作符映射 `OPERATOR_MAP`（`GTE→GE`、`LTE→LE`、`IN→CONTAIN`、`NOT_IN→NOTCONTAIN`、`IS_NULL→ISNULL` 等）、不支持操作符 `UNSUPPORTED_OPERATORS`（`CONTAINS/STARTS_WITH/ENDS_WITH/EXISTS/NOT_EXISTS`）

### 6.6.2 DAC 请求结构与 column 类型

真实 DAC 查询请求样例（`AGGRE_SDR`）：

~~~json
{
  "action": "AGGRE_SDR",
  "operation": "AGGRE_SDR",
  "columns": [
    { "id": "900", "alias": "Time", "type": "TIME", "style": "IDENTIFIER" },
    { "id": "29959400523", "alias": "InterfaceID",   "type": "DIMENSION", "style": "IDENTIFIER" },
    { "id": "29959400523", "alias": "InterfaceName", "type": "DIMENSION", "style": "NAME" },
    { "id": "29967098156", "alias": "StatusID",      "type": "DIMENSION", "style": "IDENTIFIER" },
    { "id": "29967098156", "alias": "StatusName",    "type": "DIMENSION", "style": "NAME" },
    { "id": "TEST_DAC04_GRP_IND_USR_USERS_COUNT", "type": "MODEL",
      "function": { "functionName": "CYCLE", "parameters": ["3600"] } }
  ],
  "conditions": {
    "childs": [
      { "id": "900", "operator": "GE", "type": "TIME", "values": ["1597719600"] },
      { "id": "900", "operator": "LT", "type": "TIME", "values": ["1789369676"] }
    ],
    "relation": "AND"
  }
}
~~~

column 类型：

| type | 说明 | 关键字段 |
|---|---|---|
| `TIME` | 时间维度 | `id=900`，`operator GE/LT` 时间范围过滤 |
| `DIMENSION` | 维度 | `id=维度ID`，`style` 区分 ID（IDENTIFIER）/ NAME（NAME） |
| `MODEL` | 指标模型 | `id=指标ID`，`function`（CYCLE/RATE/SUBTRACT） |

### 6.6.3 DIMENSION 多标识伴生机制

DAC 通过**一个维度属性映射为两列、共用同一维度 ID、用 style 区分**来表达 ID / NAME 伴生：

~~~json
// 维度属性 Interface → ID 列 + NAME 列（共用 id=29959400523）
{ "id": "29959400523", "alias": "InterfaceID",   "type": "DIMENSION", "style": "IDENTIFIER" },
{ "id": "29959400523", "alias": "InterfaceName", "type": "DIMENSION", "style": "NAME" }
~~~

- `id`：多维模型中的维度 ID（`attributeId`），ID 列与 NAME 列**共用同一 id**
- `style = IDENTIFIER`：返回 / 过滤维度 ID（InterfaceID）
- `style = NAME`：返回维度显示名（InterfaceName）
- `alias`：业务别名，同一属性拆成 `<属性>ID` 与 `<属性>Name` 两列

### 6.6.4 组装规则

OAC 通过多维模型的维度定义，把一个本体属性拼接为 ID 列 + NAME 列：

~~~text
本体属性 Interface（dimensionSemantic: idPropertyId + namePropertyId）
   ↓ 多维模型维度定义（attributeId + name）
DAC columns（同一个 attributeId，两列）:
   { id=attributeId, alias=InterfaceID,   type=DIMENSION, style=IDENTIFIER }  // ID 列
   { id=attributeId, alias=InterfaceName, type=DIMENSION, style=NAME }        // NAME 列
~~~

一个本体属性可同时映射多维模型的维度 ID 与 NAME：需要返回 ID 时生成 `IDENTIFIER` 列，需要返回 NAME 时生成 `NAME` 列，两列 `id` 相同。

### 6.6.5 过滤组装

condition 使用维度 / 时间列的 id，operator 经 `OPERATOR_MAP` 映射（`GTE→GE`、`LTE→LE` 等），值放 `values`：

~~~json
"conditions": {
  "childs": [
    { "id": "29959400523", "operator": "EQ", "type": "DIMENSION", "values": ["460-00-12345-001"] }
  ],
  "relation": "AND"
}
~~~

按 NAME 过滤时，condition 的 id 同样指向维度 ID（`attributeId`），DAC 侧由维度定义完成 NAME→ID 解析，OAC 无需二次解析。

### 6.6.6 结果恢复

返回 ID 用 `style=IDENTIFIER` 列，返回 NAME 用 `style=NAME` 列，两列 id 相同，DAC 侧按 style 返回对应值。

DAC 是五类通道中伴生标识语义最内聚的一类：ID / NAME 由多维模型的维度定义原生承载，OAC 组装时只需把伴生属性展开为「ID 列（IDENTIFIER）+ NAME 列（NAME）」两列并共用维度 id。

## 6.7 场景汇总对比

| 通道 | 载体 | 生成器 | NAME→ID 组装 | ID→NAME 恢复 | 防注入 |
|---|---|---|---|---|---|
| Yacht 类 MySQL | SQL | `AbstractSqlGenerator` | 子查询下推 / 分阶段 | JOIN | Druid AST |
| ADC 接口 | TQL | `AbstractTqlGenerator` | JOIN / 分阶段（`/schema/table`、`"字段"`） | JOIN | Druid AST |
| 三方物理模型 | `ExecuteEnvelope` | `ThirdPartyQueryGenerator` | 两次 ExecutionRequest 分阶段 / 直接下推 | 维度反查 | 裁剪 + 条件转换 |
| 图数据库 | GQL | `AbstractGqlGenerator` | MATCH 单跳关联 / 同 Tag 直查 | RETURN 反查 | 字段映射 |
| DAC | DAC JSON | `DacJsonBuild` | DIMENSION 列 `attributeId` 过滤 | ID/NAME 双列（`IDENTIFIER`/`NAME` style，共用 id） | 操作符白名单 |

伴生标识在各通道的落地方式虽有差异，但统一由 `DimensionResolutionStep`（Planner 产出）驱动：同源优先下推（子查询/JOIN/MATCH 关联），跨源分阶段（多 `SubQueryContext` + `ResultMergerUtils` 合并），DAC 通道借力其原生 `DIMENSION` 语义实现最简洁的组装。

# 第七章 错误处理

## 7.1 OMS 错误码

| 错误码                                   | 场景                           |
| ------------------------------------- | ---------------------------- |
| `DIMENSION_SEMANTIC_INVALID`          | DIMENSION 结构完整性校验失败          |
| `DIMENSION_PROPERTY_NOT_FOUND`        | ID / NAME Property 引用缺失      |
| `DIMENSION_PROPERTY_SCOPE_INVALID`    | 两端 ObjectType 范围校验失败         |
| `DIMENSION_PROPERTY_CONFLICT`         | Property 已参与另一条 DIMENSION 关系 |
| `DIMENSION_SEMANTIC_INCONSISTENT`     | 双端 DIMENSION 内容存在差异          |
| `DIMENSION_SEMANTIC_REFERENCE_IN_USE` | 删除 Property 时存在伴生引用          |

## 7.2 OAC 错误码

| 错误码 | 场景 |
|---|---|
| `SEMANTIC_EQUIVALENT_PLAN_NOT_FOUND` | Direct Plan 与 Dimension Resolution Route 均为空 |
| `DIMENSION_TARGET_BINDING_NOT_FOUND` | Target Asset 的伴生 ID Binding 缺失 |
| `DIMENSION_RESOLUTION_BINDING_NOT_FOUND` | Resolver Asset 的 NAME+ID Binding 路径缺失 |
| `DIMENSION_VALUE_NOT_FOUND` | NAME 的 ID 解析结果为空 |
| `DIMENSION_VALUE_NOT_UNIQUE` | NAME 解析到多个 ID |
| `DIMENSION_OPERATOR_NOT_SUPPORTED` | 条件操作符超出当前伴生转换范围 |
| `DIMENSION_CONDITION_INCONSISTENT` | ID / NAME 同时过滤且语义冲突 |
| `CROSS_SOURCE_STAGE_BINDING_FAILED` | 跨源 DAG 中间结果绑定失败 |
| `PHYSICAL_ASSET_SELECTION_AMBIGUOUS` | 候选在当前路由规则下仍保持同级 |

错误信息必须包含：

```json
{
  "objectType": "Cell",
  "queryProperties": [
    "abc",
    "prb"
  ],
  "sourceProperty": "abc",
  "semanticId": "dim_cell_identity",
  "missingBindingProperty": "cgi"
}
```

便于开发和模型配置人员快速定位缺失的 Binding。

## 10.3 联调验收

端到端必须验证：

```text
原始问题
  ↓
OQL
  ↓
QueryPropertySet
  ↓
Binding Matrix
  ↓
DIMENSION 语义
  ↓
Physical Plan
  ↓
SQL / GQL / API
  ↓
```

验收标准：

1. 同表场景生成单表查询；
2. NAME 跨表且 ID 桥接完整时生成语义等价查询；
3. NAME 跨表且 Target ID Binding 缺失时返回明确的 Binding 错误；
4. 跨模型查询通过 OMS DIMENSION 与 Binding 元数据确定关联路径；
5. 多模型场景优先选择直接覆盖属性最多的模型；
6. OQL 在不同物理模型布局下保持统一业务表达；
7. NAME→ID 解析满足 1:1；
8. 返回字段保持 OQL 对象属性语义；
9. OMS Binding 或 DIMENSION 关系变更后，新请求使用最新模型版本；
10. 错误日志能够明确指出缺失的 Property Binding 或语义路径。
