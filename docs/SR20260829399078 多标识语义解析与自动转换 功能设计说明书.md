## 2. SR-1设计

### 2.1 基本信息

| SR编号 | SR名称 | SR描述 | IR编号 | IR名称 | IR描述 |
|---|---|---|---|---|---|
| SR20260829399078 | 多标识语义解析与自动转换 | 建立对象属性 ID / NAME 伴生语义，并由 OAC 基于 OQL、DIMENSION 元数据和 Property Binding 自动生成语义等价物理查询 | 待需求侧补充 | 待需求侧补充 | 待需求侧补充 |

### 2.2 设计思路

本 SR 由两个设计用例组成：

1. **UC-OMS-01：伴生标识建模与发布**  
   OMS 定义对象属性 ID / NAME 语义，保证 SAME_OBJECT、ONE_TO_ONE、双端一致性和模型版本一致性，并通过 Property 元数据向 OAC 提供统一语义契约。

2. **UC-OAC-01：语义等价查询规划与执行**  
   OAC 解析 OQL/ObjectRequest，读取 OMS Property Mapping 与 DIMENSION 语义，在现有 OAC 生产查询链路中生成语义等价的查询计划，并由现有生成器、执行器和结果合并机制完成查询。

两个用例之间通过以下契约连接：

~~~text
OMS
  Property
  ├─ semanticTypes = ["DIMENSION"]
  └─ dimensionSemantic
       ├─ semanticId
       ├─ idPropertyId
       └─ namePropertyId
          +
  Property Binding
          ↓
OAC ObjectTypeMetadata / PropertyMapping
          ↓
DimensionResolutionStep
          ↓
GeneratedQuery / Execution
~~~

OAC 采用四层决策模型：

| 决策层 | 职责 |
|---|---|
| Binding Topology | 判断 Query Property 在物理 Asset 上的覆盖关系与语义可达路径 |
| Dimension Resolution | 识别 NAME_TO_ID、ID_TO_NAME，以及 SCALAR / SET 基数 |
| Query Shape | 识别 FILTER / RETURN / GROUP / ORDER / ASSOCIATION_QUERY 中的解析位置 |
| Physical Execution | 选择 DIRECT、同源 JOIN、同源 SUBQUERY、跨源 DAG |

### 2.3 设计用例

#### 2.3.1 设计用例1: UC-OMS-01 对象属性伴生标识建模

##### 2.3.1.1 用例描述

**目标**

在同一个 ObjectType 内，将两个业务 Property 建模为固定 1:1 的 ID / NAME 伴生标识，使 OAC 能通过统一元数据识别两个标识的业务等价关系。

**典型对象**

~~~text
Cell
├── cgi       [ID]
└── cellName  [NAME]
~~~

**前置条件**

- ObjectType 已创建。
- 两个 Property 已定义。
- 用户处于设计态并具备模型编辑权限。
- Property Binding 可以在伴生关系创建前或后逐步完成。

**主流程**

1. 用户在对象属性列表或数据映射右侧对象属性进入“伴生标识”配置。
2. 用户选择“当前属性标识角色”：ID 或 NAME。
3. 用户选择当前 ObjectType 内的另一个 Property 作为伴生属性。
4. OMS 根据当前角色自动确定另一端角色。
5. OMS 执行 SAME_OBJECT、双端属性、唯一关系、角色互补、ONE_TO_ONE 等校验。
6. OMS 生成或复用 \`semanticId\`。
7. OMS 原子维护：
   - \`idPropertyId\`
   - \`namePropertyId\`
   - 两端 Property 的 DIMENSION 投影。
8. 页面展示两个 Property 的物理 Binding 覆盖状态。
9. 模型通过版本/revision 机制进入发布流程。
10. OAC 后续通过 ObjectTypeMetadata / PropertyMapping 消费该语义。

**后置条件**

- 两端 Property 共享同一个 \`semanticId\`。
- \`idPropertyId\` 与 \`namePropertyId\` 唯一确定。
- Property 与已有 Physical Binding 保持独立维护。
- OAC 可以获得 DIMENSION 语义与 Property Binding 的完整闭包。

**业务规则**

~~~text
semanticType = DIMENSION
scope        = SAME_OBJECT
cardinality  = ONE_TO_ONE
role         = ID / NAME
resolverType = FIELD_MAPPING
~~~

#### 2.3.2 设计用例2: UC-OAC-01 语义等价查询规划与执行

##### 2.3.2.1 用例描述

**目标**

OAC 保持 OQL 业务属性语义，结合 OMS DIMENSION 伴生关系、Property Binding、Query Shape 和数据源能力，生成可执行的 SQL / GQL / TQL / REST / DAC 查询，并恢复与 OQL 一致的业务结果。

**生产链路基线**

~~~text
ObjectRequest
  ↓
DslServiceImpl.parseXxx / buildQueryContext
  ↓
QueryContext
  ├─ FilterNode
  ├─ ReturnItem
  ├─ PropertyMapping
  └─ RelationshipInfo
  ↓
DslQuerySupport.generateQuery
  ↓
GeneratedQuery
  ↓
QueryExecutor
  ↓
DataSourceConnector
  ↓
SourceResult
  ↓
ResultMergerUtils
~~~

本 SR 的 DIMENSION 能力扩展到当前生产链路中。\`oac-domain/com.huawei.ryoma.ontoaccess.query\` 包中的 SplitStrategy / PhysicalPlan / DAG 新架构作为后续演进方向，当前实现以既有生产查询链路为准。

**前置条件**

- Agent/调用方已经生成符合 OQL DSL 的 \`ObjectRequest\`。
- OMS 已提供 ObjectTypeMetadata、PropertyMapping 和 DIMENSION 元数据。
- 数据源连接器已经注册到 DataSourceConnectorSupport。
- QueryGenerator 已按 DBType + OperationType 注册。

**主流程**

1. \`DslServiceImpl.buildQueryContext\` 解析 ObjectRequest。
2. MetadataResolver 读取 ObjectType/Relationship 元数据。
3. OAC 构建 \`fieldMappings\` 与 Binding Matrix。
4. OAC 提取 FILTER / RETURN / GROUP / ORDER / RELATIONSHIP 等 Query Shape。
5. OAC 识别 Property 的 DimensionRole。
6. Planner 先计算 Direct Candidate。
7. Direct Candidate 为空时生成 \`DimensionResolutionStep\`。
8. Planner 按 Resolver/Target 数据源关系选择：
   - SAME_SOURCE_JOIN
   - SAME_SOURCE_SUBQUERY
   - CROSS_SOURCE_DAG
9. \`DslQuerySupport.generateQuery\` 按 DBType 路由生成器。
10. QueryExecutor 调用 DataSourceConnector 执行。
11. 跨源结果由 ResultMergerUtils 合并。
12. ID→NAME 场景恢复业务字段语义。
13. 返回 OQL 对应的业务结果。

**后置条件**

- 返回字段语义与 OQL 对象属性保持一致。
- 物理字段来源可通过 Property Binding 追溯。
- NAME/ID 解析路径可通过 \`DimensionResolutionStep\` 追溯。
- 跨源执行阶段可通过 SubQueryContext / GeneratedQuery / 日志追溯。

##### 2.3.2.4 可靠性分析（功能FMEA分析）【可选】

| 失效模式 | 影响 | 检测/保护机制 | 改进措施 |
|---|---|---|---|
| Resolver Asset 缺失 | NAME→ID 路径无法生成 | DIMENSION_RESOLUTION_BINDING_NOT_FOUND | 错误中携带 semanticId/sourceProperty |
| Target ID Binding 缺失 | Resolver 结果无法传递到目标查询 | DIMENSION_TARGET_BINDING_NOT_FOUND | 错误定位 missingBindingProperty |
| Scalar NAME 解析 0 行 | 目标实例不存在 | DIMENSION_VALUE_NOT_FOUND | 终止当前解析并返回语义错误 |
| Scalar NAME 解析 >1 行 | 运行时数据偏离 1:1 | DIMENSION_VALUE_NOT_UNIQUE | 1:1 运行时校验 |
| 多候选计划同级 | 计划选择不稳定 | Candidate Ranking | stablePlanKey/Asset ID 稳定排序 |
| 跨源中间绑定失败 | 后续 Stage 无法构造 | CROSS_SOURCE_STAGE_BINDING_FAILED | 记录 Stage、ID Set、目标 Asset |
| 数据源执行超时 | 查询失败 | ParallelQueryExecutor timeout | 复用现有超时和错误处理机制 |

- 语义规划输出 \`DimensionResolutionStep[]\`。
- GeneratedQuery 保留 objectsAlias、relationshipEndpoints、columnAliasMapping、globalOrderBy 等恢复信息。
- 跨源依赖复用 SubQueryContext 与 ResultMergerUtils。
- Planner 日志输出 QueryShape、ResolutionStep、SelectedPlan、PhysicalStage。

|---|---|---|---|
| AR-OAC-01 语义等价查询规划 | OAC Domain | 业务/可靠性 | 四层决策模型、Candidate Ranking |

##### 2.3.2.5 安全分析【可选】

当前 OAC 查询链路继续使用既有安全机制：

- \`ObjectRequest.IDENTIFIER_PATTERN\` 对标识符执行白名单校验。
- \`DANGEROUS_KEYWORDS\` 与 \`DANGEROUS_CHARS\` 执行危险输入校验。
- 条件最大递归深度 \`MAX_CONDITION_DEPTH = 32\`。
- \`validateAggregateFilter()\` 校验聚合过滤。
- SQL 生成使用 Druid AST：
  - 字段使用 \`SQLPropertyExpr\`
  - 常量使用参数/ValueExpr
  - SQL 方言按 DBType 适配。
- DIMENSION 解析使用 OMS PropertyMapping 和 DimensionSemantic 作为语义来源。

**QueryContext 核心结构**

~~~java
public class QueryContext {
    String operationType;
    String datasourceType;
    List<ObjectItemInfo> objects;
    List<RelationshipInfo> relationships;
    List<FilterNode> filters;
    List<ReturnItem> returns;

~~~

**DIMENSION 解析步骤**

~~~java
class DimensionResolutionStep {
    String semanticId;
    ResolutionDirection direction;      // NAME_TO_ID / ID_TO_NAME
    ResolutionCardinality cardinality;  // SCALAR / SET
    String sourcePropertyId;
    String targetPropertyId;
    QueryPropertyUsage placement;       // FILTER / RETURN / GROUP / ORDER
    String resolverTable;
    String targetTable;
}
~~~

**Query Shape 与 Resolution**

| Query Shape | direction | cardinality | placement |
|---|---|---|---|
| NAME = X | NAME_TO_ID | SCALAR | FILTER |
| NAME IN (...) | NAME_TO_ID | SET | FILTER |
| NAME LIKE pattern | NAME_TO_ID | SET | FILTER |
| RETURN NAME，事实侧使用 ID | ID_TO_NAME | SCALAR/SET | RETURN |
| GROUP BY / ORDER BY NAME，事实侧使用 ID | ID_TO_NAME | SET | GROUP / ORDER |

**Physical Plan**

| PlanType | 说明 |
|---|---|
| DIRECT_SINGLE_ASSET | 单一 Asset 完整覆盖 QueryPropertySet |
| SAME_SOURCE_JOIN | Resolver 与 Target 同源，JOIN 下推 |
| SAME_SOURCE_SUBQUERY | Resolver 与 Target 同源，子查询下推 |
| CROSS_SOURCE_DAG | Resolver 与 Target 跨数据源，分 Stage 执行 |
| NOT_EXECUTABLE | 语义等价执行路径为空时的规划结果 |

**计划优先级**

~~~text
DIRECT_SINGLE_ASSET
    ↓
SAME_SOURCE_JOIN / SAME_SOURCE_SUBQUERY
    ↓
CROSS_SOURCE_DAG
    ↓
NOT_EXECUTABLE
~~~

### 2.4 CASE1～CASE16 设计覆盖

| Case | 核心场景 | 决策重点 | 计划 / 行为 |
|---|---|---|---|
| CASE1 | 待查询属性来源同一物理模型 | Binding 全覆盖 | DIRECT_SINGLE_ASSET |
| CASE2 | 属性跨模型，语义桥接路径为空 | Binding 可达性 | SEMANTIC_EQUIVALENT_PLAN_NOT_FOUND |
| CASE3 | Filter 为 ID，ID + Target 同表 | ID 直接定位 | DIRECT_SINGLE_ASSET |
| CASE4 | Filter 为 NAME，跨表 NAME → ID → Target | NAME_TO_ID | JOIN / SUBQUERY / DAG |
| CASE5 | NAME + Target 同表 | 单表优先 | DIRECT_SINGLE_ASSET |
| CASE6 | Resolver 具备 NAME+ID，Target ID Binding 待补齐 | Bridge 完整性 | DIMENSION_TARGET_BINDING_NOT_FOUND |
| CASE7 | 多个候选 Asset | Candidate Ranking | Stable Best Plan |
| CASE8 | 多个 DIMENSION + 多个单值过滤 | 多 Resolution Step | 组合 Predicate |
| CASE9 | IN 多值查询 | Set Resolution | ID Set |
| CASE10 | LIKE 模糊查询 | Set Resolution | ID Set |
| CASE11 | 列表查询 | NAME 恢复 | JOIN + LIMIT/聚合 |
| CASE12 | GROUP BY / ORDER BY NAME，物理侧使用 ID | ID_TO_NAME | JOIN / Lookup |
| CASE13 | 跨数据源 NAME → ID → Target | Physical Execution | CROSS_SOURCE_DAG |
| CASE14 | ID / NAME 同时过滤 | 一致性校验 | Consistency Check |
| CASE15 | 伴生解析结果为 0 / 1 / >1 | Runtime Semantics | Runtime Validation |
| CASE16 | 关系查询中的伴生标识 | Relationship + Dimension | Relationship → Dimension |

#### 2.4.1 CASE1～CASE7 Binding Topology 规则

- **CASE1**：QueryPropertySet 被一个 Asset 完整覆盖，生成 DIRECT_SINGLE_ASSET。
- **CASE2**：Direct Candidate 与 Dimension Resolution Route 均为空，返回 SEMANTIC_EQUIVALENT_PLAN_NOT_FOUND。
- **CASE3**：Filter Role=ID，Target Asset 覆盖 ID + Target Properties，ID 直接下推。
- **CASE4**：Filter Role=NAME，Resolver Asset 覆盖 NAME + ID，Target Asset 覆盖 ID + Target Properties，生成 NAME_TO_ID。
- **CASE5**：NAME + Target Properties 同表覆盖，生成 DIRECT_SINGLE_ASSET。
- **CASE6**：Target Asset 的伴生 ID Binding 待补齐，返回 DIMENSION_TARGET_BINDING_NOT_FOUND。
- **CASE7**：多候选计划按照稳定 Candidate Ranking 选择。

#### 2.4.2 CASE8～CASE16 Query Shape / Runtime 规则

- **CASE8**：多个 semanticId 分别生成 ResolutionStep，再组合 Predicate。
- **CASE9**：IN 多个 NAME 分别解析并合并为 ID Set。
- **CASE10**：LIKE 生成 Set 型 NAME_TO_ID。
- **CASE11**：列表查询通过 ID 关联恢复 NAME，并结合 LIMIT/聚合控制结果规模。
- **CASE12**：GROUP / ORDER 使用 NAME 时生成 ID_TO_NAME。
- **CASE13**：跨数据源生成 Stage1 Resolver → Stage2 Target 的执行链。
- **CASE14**：ID 与 NAME 同时过滤时执行 \`resolve(NAME) == ID\` 一致性校验。
- **CASE15**：Scalar Resolution 运行时执行 0/1/>1 校验。
- **CASE16**：先完成 Relationship Resolution，再在各 ObjectType 内完成 Dimension Resolution。

#### 2.5.1 CASE 回归

|---|---|

~~~text

  ↓
OQL / ObjectRequest
  ↓

  ↓

  ↓
~~~

验收标准：

1. 同表场景生成单表查询。

6. OQL 在不同物理布局下保持统一业务表达。
7. NAME→ID Scalar 解析满足 1:1。
8. RETURN / GROUP / ORDER 场景保持 NAME 业务语义。
9. OMS 模型版本变化后，新请求读取最新发布元数据。
10. 日志可以还原 QueryShape、ResolutionStep、Physical Stage 与错误上下文。

### 6.7 最终架构关系

~~~mermaid
flowchart TD
    A[Agent / LLM] --> B[Canonical OQL / ObjectRequest]
    B --> C[DslServiceImpl / QueryContext]
    C --> D[MetadataResolver]
    D --> E[OMS DimensionSemantic]
    D --> F[OMS Property Binding]
    C --> G[Dimension Resolution]
    E --> G
    F --> G
    G --> H[QueryGenerator / Translator]
    H --> I[GeneratedQuery]
    I --> J[QueryExecutor]
    J --> K[DataSourceConnector]
    K --> L[SourceResult]
    L --> M[ResultMergerUtils / Semantic Recovery]
    M --> N[业务结果]
~~~

最终职责：

- OMS 定义对象属性、ID/NAME 伴生语义和 Property Binding。
- OQL/ObjectRequest 定义用户查询意图。
- OAC Domain 解析 Query Shape 并生成 DIMENSION Resolution。
- Generator 将 QueryContext 转换为 SQL / GQL / TQL / REST / DAC。
- Executor/Connector 执行真实数据源查询。
- ResultMergerUtils 完成跨源结果合并和业务语义恢复。
