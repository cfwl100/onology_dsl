# SR20260829399078 多标识语义解析与自动转换 功能设计说明书

> 文档名称：SR20260829399078 多标识语义解析与自动转换 功能设计说明书  
> 适用服务：OMS（Ontology Model Service）、OAC（Ontology Access）  
> 需求编号：SR20260829399078  
> 文档版本：V2.1  
> 设计范围：本版本聚焦 `DIMENSION` 数据查询语义下的 ID / NAME 伴生标识，以及 OAC 基于 OQL、对象属性语义和物理 Binding 自动生成**语义等价物理查询计划**。  
> 核心约束：伴生标识仅发生在当前 ObjectType 的两个不同 Property 之间，固定为 1:1 的 `idPropertyId ↔ namePropertyId`。

---

# 0. 方案概述

## 0.1 背景

同一个业务维度通常存在系统标识和业务名称两种表达。例如：

```text
Cell
├── cgi       —— ID
└── cellName  —— NAME
```

用户、Agent 和 OQL 更倾向于使用业务名称：

```text
查询 cellName = "上研小区A" 的 PRB
```

但实际物理模型可能是：

```text
dim_cell
├── cell_id
└── cell_name

Cell_ind
├── cell_id
└── prb
```

此时，OQL 的业务语义并不能直接映射为一条单表物理 SQL。OAC 需要综合：

1. OQL 中使用了哪些对象属性；
2. 每个对象属性绑定了哪些物理字段；
3. 这些字段分布在哪些物理模型；
4. 条件属性是否具有 DIMENSION 伴生标识；
5. 当前属性在伴生关系中是 ID 还是 NAME；
6. ID 是否能够在维度解析模型与目标事实模型之间形成桥接；
7. 是否存在一个覆盖更多待查询属性的单一物理模型。

OAC 的目标不是机械翻译 OQL，而是寻找一个与 OQL **业务语义等价、物理上可执行**的查询计划。

---

## 0.2 语义等价查询定义

本方案将 OAC 的核心能力定义为：

> **Semantic Equivalent Query Planning：在不改变 OQL 业务属性语义的前提下，基于 OMS 的 DIMENSION 伴生关系与 Property Binding，选择直接查询或 ID 桥接查询，并生成结果等价的物理执行计划。**

语义等价需要同时满足：

| 约束 | 说明 |
|---|---|
| 条件等价 | OQL 对 NAME 或 ID 的过滤，在物理层转换后仍表示同一业务实例 |
| 返回等价 | OQL 要求返回的对象属性语义不因物理字段选择而改变 |
| 1:1 等价 | DIMENSION 的 ID/NAME 映射固定 1:1，转换结果必须唯一 |
| Binding 有据 | 所有物理字段必须来自 OMS Binding，不通过字段名推测 |
| 路径可执行 | 跨物理模型时必须存在明确的 DIMENSION ID 桥接路径 |
| 单表优先 | 存在覆盖全部查询属性的单一物理模型时优先直接查询 |
| 最优覆盖 | 多个物理模型可执行时，优先选择直接覆盖待查询属性更多的模型 |


## 0.4 四层决策模型

结合本次场景梳理，OAC 不应继续把所有业务情况实现为平铺的 CASE 分支，而应统一抽象为四层决策模型：

~~~text
第一层：Binding Topology
        回答“对象属性的物理 Binding 能不能支撑查询”
        典型：CASE1～CASE7

第二层：Dimension Resolution
        回答“ID / NAME 是否需要转换、转换方向和结果基数”
        NAME → ID
        ID → NAME
        Scalar / Set

第三层：Query Shape
        回答“转换步骤作用于 FILTER / RETURN / GROUP / ORDER 的哪个位置”
        单条件 / 多条件 / IN / LIKE / 无目标维度等值过滤
        GROUP BY / ORDER BY / ID+NAME 同时过滤 / ASSOCIATION_QUERY

第四层：Physical Execution
        回答“逻辑计划最终如何落到数据源执行”
        单表 / 同源 JOIN / 子查询下推 / 跨源 DAG
~~~

统一决策链：

~~~text
OQL
 ↓
Query Shape
 ├─ Filter：ID / NAME / Other
 ├─ Return：ID / NAME / Other
 └─ Query Op：EQ / IN / LIKE / GROUP / ORDER / ...
 ↓
Binding Coverage
 ├─ 同表覆盖
 ├─ 跨表
 └─ 多表 / 多对象
 ↓
Dimension Resolution
 ├─ NONE
 ├─ NAME → ID
 ├─ ID → NAME
 ├─ Scalar
 └─ Set
 ↓
Physical Execution
 ├─ DIRECT_SINGLE_ASSET
 ├─ SAME_SOURCE_JOIN
 ├─ SAME_SOURCE_SUBQUERY
 ├─ CROSS_SOURCE_DAG
 └─ NOT_EXECUTABLE
~~~

这意味着 CASE1～CASE16 只是四层能力的典型组合，代码实现应围绕 QueryShape、DimensionResolutionStep 和 PhysicalPlan 进行，而不是为每个 CASE 单独增加 if/else。

# 第一章 OMS：对象属性 DIMENSION 语义与伴生标识设计

> 原型参考：\`SR20260829399078-companion-identifier-binding-demo-v6.html\`  
> 本章将原型中已经明确的交互原则、配置项、校验规则和 Binding 展示方式固化为 OMS 正式功能设计。原型同时包含值映射能力，但值映射属于独立需求，本章只保留与“伴生标识”和物理 Binding 边界相关的说明，不展开值映射设计。

## 1.1 OMS 功能职责

OMS 负责向 OAC 提供两类互相独立但可以联合使用的元数据。

### 1.1.1 对象属性 DIMENSION 语义

~~~text
ObjectType
  └── Property
        ├── semanticTypes
        │     └── DIMENSION
        └── dimensionSemantic
              ├── semanticId
              ├── idPropertyId
              └── namePropertyId
~~~

其职责是回答：

> 当前 ObjectType 中，哪两个 Property 构成同一个业务维度的 ID / NAME 伴生关系？

### 1.1.2 物理 Binding

~~~text
Physical Asset.Field
        ↓
ObjectType.Property
~~~

其职责是回答：

> 某个对象属性，在一个或多个物理模型中分别落在哪个字段？

二者职责必须保持分离：

- \`DimensionSemantic\` 定义对象属性之间的业务语义关系；
- Property Binding 定义物理字段到对象属性的映射；
- 物理 Binding 连线不承载 ID / NAME 角色；
- ID / NAME 角色不由物理字段名推断；
- OAC 运行时联合读取 DIMENSION 语义与 Binding，生成语义等价物理查询。

---

## 1.2 Property.java 领域模型

### 1.2.1 推荐结构

正式 OMS 领域模型继续采用“一级语义类型 + DIMENSION 专属结构”，不把所有查询语义统一塞入一个通用 \`querySemantics\`。

~~~java
@EqualsAndHashCode(callSuper = true)
@Data
@Slf4j
public class Property extends AbstractElement {

    private String dataType;

    private String valueType;

    private String defaultValue;

    private List<String> refSharedIds;

    private Boolean primaryKey;

    private Extensions extensions;

    /**
     * 当前 Property 所属的数据查询语义类型。
     * 当前 SR 使用 DIMENSION。
     */
    private List<String> semanticTypes;

    /**
     * DIMENSION 专属语义结构。
     */
    private DimensionSemantic dimensionSemantic;

    ...
}
~~~

### 1.2.2 DimensionSemantic

~~~java
@Data
public class DimensionSemantic {

    /**
     * DIMENSION 伴生关系唯一标识。
     * ID / NAME 两端使用同一个 semanticId。
     */
    private String semanticId;

    /**
     * 当前 ObjectType 中承担 ID 角色的 Property ID。
     */
    private String idPropertyId;

    /**
     * 当前 ObjectType 中承担 NAME 角色的 Property ID。
     */
    private String namePropertyId;
}
~~~

字段定义：

| 字段 | 类型 | 必填 | 说明 |
|---|---|:---:|---|
| \`semanticId\` | String | 是 | 伴生关系唯一标识，由 OMS 生成 |
| \`idPropertyId\` | String | 是 | DIMENSION 的 ID Property |
| \`namePropertyId\` | String | 是 | DIMENSION 的 NAME Property |

固定业务规则：

~~~text
semanticType = DIMENSION
scope        = 当前 ObjectType / SAME_OBJECT
cardinality  = 1:1 / ONE_TO_ONE
role         = ID / NAME
resolverType = Property Field Mapping
~~~

其中 \`scope\`、\`cardinality\`、\`resolverType\` 在本 SR 中都是固定规则，不作为普通用户可编辑参数。

## 1.3 Property JSON 示例

ID 属性：

~~~json
{
  "id": "p_cgi",
  "name": "cgi",
  "dataType": "String",
  "semanticTypes": [
    "DIMENSION"
  ],
  "dimensionSemantic": {
    "semanticId": "dim_cell_identity",
    "idPropertyId": "p_cgi",
    "namePropertyId": "p_cell_name"
  }
}
~~~

NAME 属性：

~~~json
{
  "id": "p_cell_name",
  "name": "cellName",
  "dataType": "String",
  "semanticTypes": [
    "DIMENSION"
  ],
  "dimensionSemantic": {
    "semanticId": "dim_cell_identity",
    "idPropertyId": "p_cgi",
    "namePropertyId": "p_cell_name"
  }
}
~~~

OAC 不需要额外依赖一个永久保存的 \`identifierRole\` 字段，角色可以由端点确定：

~~~text
property.id == idPropertyId   → ID
property.id == namePropertyId → NAME
~~~

## 1.4 原型固化后的 OMS 用户操作流程

原型将对象属性建模过程明确拆成三个步骤：

~~~text
Step 1  定义对象属性
          ↓
Step 2  配置伴生标识
          ↓
Step 3  建立物理字段 Binding
~~~

原型页面中“伴生标识”和“值映射”都位于对象属性侧；本 SR 只固化其中伴生标识部分。

核心交互原则：

1. 先定义业务对象属性，再配置对象属性之间的 ID / NAME 语义；
2. 伴生标识只存在于右侧 Object Property；
3. 左侧 Physical Model 只展示物理字段；
4. 中间连线只表达 \`Physical Field → Object Property\` Binding；
5. 连线上不展示 ID / NAME 标签；
6. 一个伴生关系可以先于物理 Binding 创建；
7. OAC 真正执行语义转换前，再检查所需物理 Binding 是否完整。

因此 OMS 页面不能把“语义关系”和“物理连线”合并为同一个配置动作。

---

## 1.5 对象属性列表中的伴生标识展示

对象属性列表需要直接展示当前 Property 是否参与伴生关系。

推荐展示：

| 对象属性 | 数据类型 | DIMENSION 角色 | 伴生标识 | 物理 Binding |
|---|---|---|---|---|
| \`cgi\` | String | ID | \`cellName [NAME]\` | 2 条 |
| \`cellName\` | String | NAME | \`cgi [ID]\` | 1 条 |
| \`prb\` | Number | — | 未配置 | 1 条 |

交互要求：

- 未配置时显示“配置伴生”入口；
- 已配置时显示“伴生标识”入口；
- ID / NAME 以对象属性元数据标签展示；
- 两端 Property 都能够进入同一条伴生关系的查看/编辑界面；
- 从任意一端进入时，当前属性角色和伴生属性角色都按当前视角正确展示。

逻辑上始终只有一条关系：

~~~text
Cell.cgi [ID]
      ↕ 1:1
Cell.cellName [NAME]
~~~

不是两条相互独立的配置。

## 1.6 数据映射页面设计

### 1.6.1 页面布局

原型明确采用：

~~~text
左侧：Physical Model / Physical Field
                    │
                    │ Binding
                    ▼
右侧：ObjectType / Object Property
~~~

页面顶部可以切换：

- 当前 Physical Model；
- 当前 ObjectType。

### 1.6.2 Binding 连线语义

蓝色连线只表示：

~~~text
Physical Field
      ↓
Object Property
~~~

例如：

~~~text
dim_cell.cell_id    → Cell.cgi
dim_cell.cell_name  → Cell.cellName
Cell_ind.cell_id    → Cell.cgi
Cell_ind.prb        → Cell.prb
~~~

明确禁止在线上表达：

~~~text
ID
NAME
1:1
NAME → ID
值映射
~~~

这些都不是 Binding 连线本身的职责。

### 1.6.3 右侧对象属性信息

对象属性节点可展示：

~~~text
Property Name
Data Type
ID / NAME Role
伴生标识入口
Binding 状态
~~~

例如：

~~~text
基站标识
siteId
String
[ID]
[伴生标识]
~~~

这样既能看到当前对象语义，也不会污染物理连线。

## 1.7 “对象属性 · 伴生标识”抽屉

原型中的伴生标识采用独立抽屉配置。

### 1.7.1 抽屉上下文

顶部固定显示：

~~~text
本体对象
    ↓
当前对象属性
~~~

例如：

~~~text
基站 / BaseStation
        ↓
基站标识 / siteId
~~~

同时明确提示：

> 伴生标识只定义右侧对象属性之间的语义关系；左侧物理模型与 Binding 连线不展示 ID / NAME。

### 1.7.2 只保留两个业务必填项

配置表单只保留：

| 字段 | 必填 | 候选范围 | 说明 |
|---|:---:|---|---|
| 当前属性标识角色 | 是 | ID / NAME | 当前 Property 在伴生关系中的角色 |
| 伴生属性 | 是 | 当前 ObjectType 内除自身外的 Property | 与当前属性形成 1:1 伴生关系 |

角色文案：

~~~text
ID   · 标识 / 编码
NAME · 名称 / 显示名
~~~

伴生属性角色自动取反：

~~~text
当前属性 = ID
→ 伴生属性 = NAME

当前属性 = NAME
→ 伴生属性 = ID
~~~

因此 UI 不再要求用户重复选择第二端角色。

### 1.7.3 固定项不暴露为普通配置

以下规则在原型中是固定值，正式页面也不需要作为普通表单项暴露：

~~~text
scope        = SAME_OBJECT
cardinality  = ONE_TO_ONE
resolverType = FIELD_MAPPING
enabled      = true（关系存在即启用）
~~~

这样能够避免用户配置出本 SR 不支持的关系形态。

## 1.8 伴生标识实时预览

当用户选择角色和伴生属性后，页面实时生成伴生关系预览：

~~~text
当前属性 · ID
BaseStation.siteId
        ↕
伴生属性 · NAME
BaseStation.siteName
~~~

预览必须包含两部分。

### 1.8.1 对象语义预览

明确显示：

- 当前 Property；
- 当前角色；
- 伴生 Property；
- 自动计算出的相反角色；
- 固定 1:1。

### 1.8.2 物理 Binding 覆盖检查

预览区只读展示当前 Property 和伴生 Property 已经绑定的物理字段。

例如：

~~~text
当前属性 siteId
  radio_inventory_a.site_id
  radio_inventory_b.site_code

伴生属性 siteName
  radio_inventory_a.site_name
  dim_site.site_name
~~~

状态判断：

~~~text
两端均存在 Binding
→ 提示：两侧属性均已有物理 Binding，可供 OAC 在执行期进行 ID / NAME 解析。

任一端暂时没有 Binding
→ 提示：伴生标识可以先保存；执行前需确保参与查询的属性具备可用物理 Binding。
~~~

这里需要明确区分：

> **OMS 伴生关系“可保存”不等于某一个具体 OQL 已经“可执行”。**

是否存在满足某次查询的 Resolver Asset / Target Asset，由 OAC Planner 在运行时依据 QueryPropertySet 和 Binding Matrix 判断。

---

## 1.9 创建与修改校验规则

保存伴生标识时，OMS Service 必须执行以下强校验。

### 1.9.1 必填校验

~~~text
role ∈ {ID, NAME}
companionPropertyId != null
~~~

### 1.9.2 自引用校验

~~~text
companionPropertyId != currentPropertyId
~~~

当前 Property 不能与自身构成伴生关系。

### 1.9.3 SAME_OBJECT 校验

~~~text
currentProperty.objectTypeId
==
companionProperty.objectTypeId
~~~

禁止跨 ObjectType 配置伴生标识。

### 1.9.4 唯一参与关系校验

同一个 Property 在当前 DIMENSION 语义下只能参加一条有效伴生关系。

例如已经存在：

~~~text
siteId [ID] ↔ siteName [NAME]
~~~

则 \`siteName\` 不能再与另一个 Property 新建第二条伴生关系，除非先解除原关系。

### 1.9.5 角色互补校验

服务端归一化为：

~~~text
ID ↔ NAME
~~~

不能出现：

~~~text
ID ↔ ID
NAME ↔ NAME
~~~

### 1.9.6 关系基数校验

当前 SR 固定：

~~~text
ONE_TO_ONE
~~~

不接受 1:N、N:1、N:N。

### 1.9.7 双端一致性校验

如果 Property API 对两端都输出 \`dimensionSemantic\`，必须保证：

~~~text
semanticId     一致
idPropertyId   一致
namePropertyId 一致
~~~

禁止出现双端不同步。

---

## 1.10 创建、编辑、删除的原子语义

### 1.10.1 新建

从任意一个 Property 发起：

~~~text
currentProperty
+
role
+
companionProperty
~~~

OMS 统一归一化为：

~~~text
semanticId
idPropertyId
namePropertyId
~~~

并原子维护双端视图。

### 1.10.2 编辑

无论从 ID 端还是 NAME 端进入，都编辑同一个 \`semanticId\`。

修改任意以下内容：

- 当前端角色；
- 伴生 Property；

本质上都是更新同一条逻辑关系，不创建第二条关系。

### 1.10.3 删除

删除操作的语义是：

> 解除当前 ObjectType 中这一组 ID / NAME 伴生关系。

删除伴生关系时：

- 不删除 Property；
- 不删除任何物理 Binding；
- 不修改 Physical Model；
- 不级联删除其他独立语义配置。

## 1.11 原型 IdentifierAssociation 与正式领域模型的映射

v6 原型内部使用了一个独立的 \`identifierAssociations\` 状态对象，例如：

~~~json
{
  "id": "ia-base-site",
  "enabled": true,
  "resolverType": "FIELD_MAPPING",
  "propertyId": "p-id",
  "role": "ID",
  "scope": "SAME_OBJECT",
  "companionObjectId": "o-base",
  "companionPropertyId": "p-name",
  "companionRole": "NAME",
  "cardinality": "ONE_TO_ONE",
  "revision": 1
}
~~~

该结构适合表达前端原型状态，但正式 OMS 后端不要求照搬为唯一持久化结构。

推荐映射：

| 原型字段 | 正式 OMS 语义 | 处理方式 |
|---|---|---|
| \`id\` | \`semanticId\` | 由 OMS 生成 |
| \`propertyId + role\` | ID 或 NAME 端点 | 保存时归一化 |
| \`companionPropertyId + companionRole\` | 另一端点 | 保存时归一化 |
| \`scope=SAME_OBJECT\` | 同 ObjectType 约束 | 固定规则 + Service 校验 |
| \`cardinality=ONE_TO_ONE\` | 1:1 | 固定规则 + Service 校验 |
| \`resolverType=FIELD_MAPPING\` | 通过 Property Binding 解析 | 固定规则，不作为用户输入 |
| \`enabled\` | 关系是否存在 | 当前需求可由关系存在性表达 |
| \`companionObjectId\` | 当前 ObjectType | 上下文校验，不需要重复维护 |
| \`revision\` | 并发版本 | 可复用 OMS 模型版本 / revision 机制 |

正式领域层仍以：

~~~text
DimensionSemantic
├── semanticId
├── idPropertyId
└── namePropertyId
~~~

作为最小稳定语义结构。

### 1.11.1 UI View Model

为了支撑原型中的抽屉展示，OMS API 可以额外组装一个 View DTO：

~~~java
class DimensionCompanionView {

    String semanticId;

    String objectTypeId;

    String currentPropertyId;
    DimensionRole currentRole;

    String companionPropertyId;
    DimensionRole companionRole;

    List<PropertyBindingSummary> currentBindings;
    List<PropertyBindingSummary> companionBindings;
}
~~~

该 DTO 是展示模型，不替代领域模型。

### 1.11.2 不把原型默认猜测作为正式语义

原型为了方便演示，会根据属性名中的 \`id/code/cgi\` 等字符串预选 ID 角色。

正式 OMS 中：

> Property 的 ID / NAME 角色必须以用户保存后的 DIMENSION 配置为准，不能以 Property Name 或 Physical Field Name 进行持久化语义推断。

## 1.12 页面权限与状态

原型提供设计态、运行态、只读三种体验状态。

本 SR 对伴生标识采用：

| 页面状态 | 查看伴生标识 | 新建 / 修改 / 删除 |
|---|:---:|:---:|
| 设计态 | ✓ | ✓ |
| 运行态 | ✓ | ✗ |
| 只读 | ✓ | ✗ |

伴生标识属于模型设计元数据，应通过设计态变更流程进入模型版本；运行态只消费已经发布的语义。

## 1.13 OMS Service 保存流程

建议服务端统一走一个原子保存流程：

~~~text
收到：
currentPropertyId
role
companionPropertyId
        ↓
加载当前 ObjectType 与两个 Property
        ↓
必填 / 自引用 / SAME_OBJECT 校验
        ↓
检查两个 Property 是否已参加其他伴生关系
        ↓
根据 role 归一化：
ID Property / NAME Property
        ↓
生成或复用 semanticId
        ↓
原子更新 DIMENSION 双端投影
        ↓
递增模型版本 / revision
        ↓
返回标准化 DimensionSemantic
~~~

伪代码：

~~~java
DimensionSemantic saveCompanion(
        String objectTypeId,
        String currentPropertyId,
        DimensionRole currentRole,
        String companionPropertyId) {

    Property current = loadProperty(currentPropertyId);
    Property companion = loadProperty(companionPropertyId);

    validateSameObject(objectTypeId, current, companion);
    validateNotSelf(current, companion);
    validateNoAssociationConflict(current, companion);

    String idPropertyId =
        currentRole == DimensionRole.ID
            ? current.id()
            : companion.id();

    String namePropertyId =
        currentRole == DimensionRole.NAME
            ? current.id()
            : companion.id();

    DimensionSemantic semantic =
        createOrReuseSemantic(
            idPropertyId,
            namePropertyId
        );

    saveBothEndsAtomically(semantic);

    return semantic;
}
~~~

## 1.14 OMS 数据一致性

### 1.14.1 单一逻辑关系

逻辑上只存在一条 DIMENSION 关系：

~~~text
dim_cell_identity
├── idPropertyId   = p_cgi
└── namePropertyId = p_cell_name
~~~

ID Property 和 NAME Property 上保存或输出的是同一关系的双端投影。

### 1.14.2 Property 本地校验

\`Property.validate()\` 负责不依赖外部对象上下文的结构校验：

1. \`semanticTypes\` 包含 DIMENSION 时，\`dimensionSemantic\` 必须存在；
2. \`dimensionSemantic\` 存在时，\`semanticTypes\` 必须包含 DIMENSION；
3. \`semanticId\` 非空；
4. \`idPropertyId\` 非空；
5. \`namePropertyId\` 非空；
6. ID 与 NAME 不能是同一个 Property；
7. 当前 Property 必须是两个端点之一。

### 1.14.3 ObjectType / Service 层校验

依赖对象上下文的约束由 Service 层完成：

1. ID Property 存在；
2. NAME Property 存在；
3. 两端属于同一 ObjectType；
4. 一个 Property 只能参与一条当前 DIMENSION 伴生关系；
5. 两端 semanticId 一致；
6. 两端映射内容一致；
7. 删除 Property 前执行引用完整性校验；
8. 修改伴生关系时必须防止与现有关系冲突；
9. 模型并发修改需要使用现有 revision / model version 机制避免覆盖更新。

---

## 1.15 Binding 完整性与“可配置 / 可执行”边界

这是原型需要固化到正式设计中的重要边界。

### 1.15.1 OMS 配置层

创建伴生关系时，不强制要求 ID 与 NAME 两端都已经存在物理 Binding。

允许：

~~~text
先定义：
siteId [ID] ↔ siteName [NAME]

后续再建立：
Physical Field → siteId
Physical Field → siteName
~~~

这样保持本体建模和物理映射解耦。

### 1.15.2 OAC 执行层

某一次 OQL 是否能够执行，由 OAC 根据具体 Query Shape 判断。

例如 NAME → ID → Target 必须实际找到：

~~~text
Resolver Asset:
    NAME + ID

Target Asset:
    ID + Target Properties
~~~

所以：

~~~text
OMS 关系合法
≠
当前 OQL 一定可执行
~~~

OMS 页面只做 Binding 覆盖提示；OAC Planner 负责最终执行可达性判断。

## 1.16 OMS 面向 OAC 的最小契约

OAC 至少需要获得：

~~~json
{
  "propertyId": "p_cell_name",
  "semanticTypes": [
    "DIMENSION"
  ],
  "dimensionSemantic": {
    "semanticId": "dim_cell_identity",
    "idPropertyId": "p_cgi",
    "namePropertyId": "p_cell_name"
  }
}
~~~

以及 Property Binding：

~~~text
PropertyId -> [
    PhysicalAsset.Field,
    PhysicalAsset.Field,
    ...
]
~~~

运行时闭包：

~~~text
OQL Property
+
DimensionSemantic
+
Property Binding
+
Physical Asset Capability
=
Semantic Equivalent Physical Plan
~~~

## 1.17 OMS 功能验收标准

伴生标识功能至少满足：

1. 可以从对象属性列表进入伴生标识配置；
2. 可以从数据映射右侧对象属性进入伴生标识配置；
3. 只提供“当前属性标识角色”和“伴生属性”两个业务必填项；
4. 伴生属性只能来自当前 ObjectType，且不能选择自身；
5. ID / NAME 自动互补；
6. 固定 1:1，不允许配置其他基数；
7. 一个 Property 不能同时参加多条伴生关系；
8. 从 ID 端和 NAME 端查看时都指向同一个 semanticId；
9. 页面实时展示两端的物理 Binding 覆盖情况；
10. 未完成物理 Binding 时允许保存伴生关系，但给出执行前 Binding 完整性提示；
11. Binding 连线不展示 ID / NAME；
12. 删除伴生关系不影响 Property 和已有 Binding；
13. 运行态 / 只读态不能修改伴生关系；
14. 正式语义不依赖属性名或物理字段名猜测；
15. OAC 能通过 OMS API 获得标准化 \`idPropertyId / namePropertyId\` 以及两端 Binding。

# 第二章 OAC：语义等价查询总体设计

## 2.1 核心职责

OAC 不直接把一个 OQL Property 翻译成一个物理字段，而是以**完整查询所涉及的 Property 集合**为输入进行规划。

建议将 OAC 处理拆成四个阶段：

```text
1. Query Property Extraction
2. Binding Matrix Construction
3. Semantic Equivalent Plan Generation
4. Physical Query Translation
```

---

## 2.2 Query Property Extraction

从 OQL 提取本次查询涉及的对象属性集合：

```text
QueryPropertySet =
    Condition Properties
  ∪ Return Properties
  ∪ Group Properties
  ∪ Order Properties
```

例如：

```text
查询 abc = "上研小区A" 的 prb

QueryPropertySet:
- abc     —— 过滤属性
- prb     —— 返回属性
```

同时保留属性用途：

```java
QueryPropertyRef {
    String propertyId;
    QueryPropertyUsage usage;
}
```

```java
public enum QueryPropertyUsage {
    FILTER,
    RETURN,
    GROUP,
    ORDER
}
```

这样 Planner 能区分“用于定位记录的 Property”和“用于返回的 Property”。

---

## 2.3 Binding Matrix

OAC 根据 OMS Binding 构建“对象属性 × 物理模型”矩阵。

示例：

| Property | dim_cell | Cell_ind | Sdr_xxx |
|---|:---:|:---:|:---:|
| cgi | ✓ | ✓ | ✓ |
| abc | ✓ | — | ✓ |
| prb | — | ✓ | ✓ |

矩阵是语义等价查询规划的主要输入。

推荐运行时结构：

```java
Map<String, List<PropertyBinding>> bindingsByProperty;

class PropertyBinding {
    String propertyId;
    String assetId;
    String fieldName;
}
```

同时建立反向索引：

```java
Map<String, Set<String>> propertiesByAsset;
```

用于快速计算一个物理模型覆盖了多少 OQL Property。

---

## 2.4 逻辑规划与物理执行计划

原设计将 DIRECT_SINGLE_ASSET 和 DIMENSION_ID_BRIDGE 直接作为两类物理计划。结合新增场景后，需要拆分“语义 Resolution”和“物理 Execution”两个层次。

### 2.4.1 Dimension Resolution

DIMENSION 不应硬编码为“WHERE NAME → ID”，统一抽象为：

~~~java
class DimensionResolutionStep {
    String semanticId;

    String sourcePropertyId;
    String targetPropertyId;

    ResolutionDirection direction;      // NAME_TO_ID / ID_TO_NAME
    ResolutionCardinality cardinality;  // SCALAR / SET

    PredicateOperator operator;         // EQ / IN / LIKE / ...
    QueryPropertyUsage placement;       // FILTER / RETURN / GROUP / ORDER

    String resolverAssetId;
    String sourcePhysicalField;
    String targetPhysicalField;

    boolean uniqueRequired;
}
~~~

典型方向：

~~~text
NAME → ID
    用于 WHERE NAME = ?、IN、LIKE 等过滤解析

ID → NAME
    用于 RETURN NAME、GROUP BY NAME、ORDER BY NAME 等语义恢复
~~~

典型基数：

~~~text
EQ   → Scalar
IN   → 多个 Scalar 合并为 Set
LIKE → Set
~~~

### 2.4.2 Physical Plan

物理执行计划统一分为：

| PlanType | 说明 |
|---|---|
| DIRECT_SINGLE_ASSET | 一个 Asset 完整覆盖 QueryPropertySet |
| SAME_SOURCE_JOIN | Resolver 与 Target 同源，可通过 JOIN 完成 |
| SAME_SOURCE_SUBQUERY | Resolver 与 Target 同源，适合子查询下推 |
| CROSS_SOURCE_DAG | Resolver 与 Target 跨数据源，分 Stage 执行 |
| NOT_EXECUTABLE | 不存在可证明的语义等价执行路径 |

因此，DIMENSION_ID_BRIDGE 更适合作为逻辑能力描述，而不是唯一的物理 PlanType。

## 2.5 计划优先级

完整 Physical Plan 的优先级：

~~~text
P0  DIRECT_SINGLE_ASSET
        ↓
P1  SAME_SOURCE_JOIN / SAME_SOURCE_SUBQUERY
        ↓
P2  CROSS_SOURCE_DAG
        ↓
P3  NOT_EXECUTABLE
~~~

原则：

> 能在一个 Asset 内完整执行时，不引入无必要的 ID / NAME 转换；必须跨 Asset 时优先同源下推；只有数据源本身无法完成时才拆成跨源 DAG。

# 第三章 OAC：语义等价规则引擎

## 3.1 Rule 1：单一物理模型全覆盖，直接查询

判断条件：

```text
存在 asset A：
QueryPropertySet ⊆ propertiesByAsset[A]
```

执行：

```text
planType = DIRECT_SINGLE_ASSET
targetAsset = A
```

该规则不依赖是否存在伴生标识。

典型场景：

```text
cgi + prb 都绑定 Cell_ind
```

或者：

```text
abc + prb 都绑定 Cell_ind
```

均直接单表执行。

---

## 3.2 Rule 2：跨物理模型且无语义桥接路径，不执行

当不存在单表全覆盖模型时，OAC 检查过滤属性是否能够建立 DIMENSION 语义桥接。

如果不存在可执行的 DIMENSION 路径，则返回规划错误。

判断：

```text
No Direct Full-Coverage Asset
AND
No Executable DIMENSION Bridge
```

输出：

```text
planType = NOT_EXECUTABLE
```

OAC 不为了“把查询执行出来”而自行推测两个物理表的关联字段。

---

## 3.3 Rule 3：过滤属性为 ID 时，ID 直接作为查询键

如果过滤 Property 是 DIMENSION ID：

```text
sourceRole = ID
```

OAC 不需要先做 NAME_TO_ID 转换。

只要存在目标物理模型同时覆盖：

```text
ID Property
+
其余 Query Properties
```

即可直接执行。

例如：

```text
cgi [ID]
prb

Cell_ind:
cell_id -> cgi
prb     -> prb
```

执行：

```sql
SELECT prb, cell_id
FROM Cell_ind
WHERE cell_id = ?
```

伴生关系存在，但不参与本次物理转换。

---

## 3.4 Rule 4：过滤属性为 NAME，跨表时使用 ID 桥接

当：

1. 不存在全覆盖物理模型；
2. 过滤 Property 是 DIMENSION NAME；
3. 存在伴生 ID；
4. 存在同时绑定 NAME + ID 的解析模型；
5. 存在同时绑定 ID + 返回 Property 的目标模型；

生成：

```text
DimensionResolutionStep:
    direction = NAME_TO_ID
    placement = FILTER

PhysicalPlan:
    由数据源关系选择
    SAME_SOURCE_JOIN / SAME_SOURCE_SUBQUERY / CROSS_SOURCE_DAG
```

执行逻辑：

```text
NAME
 ↓
resolutionAsset
 ↓
ID
 ↓
targetAsset
 ↓
Result
```

这是跨物理模型语义等价查询的核心规则。

---

## 3.5 Rule 5：NAME 与查询属性同表时，直接查询

如果过滤 Property 是 NAME，且存在一个物理模型直接绑定：

```text
NAME Property
+
所有其余 Query Properties
```

则直接单表查询。

例如：

```text
Cell_ind
├── name -> abc [NAME]
└── prb  -> prb
```

虽然 abc 具有 cgi 伴生 ID，但本次查询不需要经过 ID。

执行：

```sql
SELECT prb, name
FROM Cell_ind
WHERE name = ?
```

---

## 3.6 Rule 6：跨表桥接时，ID 必须同时覆盖解析模型和目标模型

当采用跨 Asset 的 DIMENSION Resolution 时，ID Property 是语义桥接键，因此必须满足：

```text
resolutionAsset:
    NAME + ID

targetAsset:
    ID + Return Properties
```

如果目标模型只有返回属性，没有绑定伴生 ID，则不能把两个物理模型连接成语义等价路径。

例如：

```text
dim_cell:
    cell_id   -> cgi
    cell_name -> abc

Cell_ind:
    prb       -> prb
    // 无 cgi Binding
```

不存在：

```text
dim_cell.ID -> Cell_ind.ID
```

因此规划失败。

这条规则明确了：

> NAME 可以只存在于解析模型；作为跨模型桥接键的 ID 必须同时在解析模型和目标模型存在 Binding。

---

## 3.7 Rule 7：多候选物理模型时，优先覆盖更多查询属性的模型

同一个 Property 可能绑定多个物理模型。

OAC 对候选 Asset 计算：

```text
directCoverage(asset)
=
| QueryPropertySet ∩ propertiesByAsset[asset] |
```

候选排序：

```text
1. 是否能够直接覆盖全部 QueryPropertySet
2. directCoverage 降序
3. 执行阶段数升序
4. 物理资产数量升序
5. 现有 Binding 路由优先级
6. 稳定的 assetId 顺序
```

因此，如果 `Sdr_perform` 同时绑定：

```text
abc
cgi
prb
```

而其他模型只能绑定其中一部分，则优先：

```text
Sdr_perform
```

直接完成查询。

如果多个候选在业务属性覆盖数和执行代价上完全相同，从语义上任一候选均等价；实现上应使用现有 Binding 路由规则和稳定排序选择唯一结果，保证执行计划可重复。

# 第四章 CASE1～CASE16 的统一归纳

## 4.1 Case Matrix

| Case | 核心场景 | 决策层 | OAC 计划 / 行为 |
|---|---|---|---|
| CASE1 | 待查询属性来源同一物理模型 | Binding Topology | DIRECT_SINGLE_ASSET |
| CASE2 | 属性跨模型且没有伴生语义路径 | Binding Topology | NOT_EXECUTABLE |
| CASE3 | Filter 为 ID，ID + Target 同表 | Binding + Resolution | DIRECT_SINGLE_ASSET |
| CASE4 | Filter 为 NAME，跨表 NAME → ID → Target | Dimension Resolution | JOIN / SUBQUERY / DAG |
| CASE5 | NAME + Target 同表 | Binding Topology | DIRECT_SINGLE_ASSET |
| CASE6 | Resolver 有 NAME+ID，但 Target 缺 ID Binding | Binding Topology | NOT_EXECUTABLE |
| CASE7 | 多个候选 Asset，选择最优覆盖与稳定路由 | Candidate Ranking | Stable Best Plan |
| CASE8 | 多个 DIMENSION + 多个单值过滤条件 | Query Shape | 多 Resolution Step |
| CASE9 | 多个 DIMENSION + IN 多值查询 | Query Shape | Set Resolution |
| CASE10 | 多个 DIMENSION + LIKE 模糊查询 | Query Shape | Set Resolution |
| CASE11 | 列表查询 / 目标维度无等值过滤 | Query Shape | JOIN + LIMIT/聚合 |
| CASE12 | GROUP BY / ORDER BY 使用 NAME，物理数据使用 ID | Query Shape | ID → NAME + JOIN |
| CASE13 | 跨数据源 NAME → ID → Target | Physical Execution | CROSS_SOURCE_DAG |
| CASE14 | ID / NAME 同时作为过滤条件 | Semantic Validation | Consistency Check |
| CASE15 | 伴生值不存在 / 数据不满足 1:1 | Runtime Semantics | Runtime Validation |
| CASE16 | 关系查询中的伴生标识 | Relationship + Resolution | Relationship → Dimension |

## 4.2 CASE1：同表直接查询

业务：

```text
查询 cgi = "460-00-12345-001" 的 PRB
```

Binding：

```text
Cell_ind
├── msisdn -> cgi
└── prb    -> prb
```

规则命中：

```text
Rule 1
```

生成：

```sql
SELECT prb, msisdn
FROM Cell_ind
WHERE msisdn = ?
```

---

## 4.3 CASE2：跨表且无伴生路径

业务：

```text
查询 abc = "上研小区A" 的 PRB
```

Binding：

```text
abc -> Model A
prb -> Model B
```

不存在一个物理模型同时覆盖 abc + prb，也不存在可执行的 DIMENSION ID 桥接路径。

规则命中：

```text
Rule 2
```

OAC 在 Plan 阶段终止，不进入 Translator。

---

## 4.4 CASE3：ID 属性同表直接查询

业务：

```text
查询 cgi = "460-00-12345-001" 的 PRB
```

`cgi` 已配置 DIMENSION 伴生关系，但在本次目标物理模型中 `cgi + prb` 已经全覆盖。

规则命中：

```text
Rule 1 + Rule 3
```

直接：

```sql
SELECT prb, cell_id
FROM Cell_ind
WHERE cell_id = ?
```

---

## 4.5 CASE4：NAME 跨表，通过 ID 桥接

业务：

```text
查询 abc = "上研小区A" 的 PRB
```

语义：

```text
cgi [ID] ↔ abc [NAME]
```

Binding：

```text
dim_cell
├── cell_id   -> cgi
└── cell_name -> abc

Cell_ind
├── cell_id -> cgi
└── prb     -> prb
```

规则命中：

```text
Rule 4 + Rule 6
```

逻辑计划：

```text
abc(NAME)
   ↓ dim_cell
cgi(ID)
   ↓ Cell_ind
prb
```

可生成两段查询：

```sql
SELECT cell_id
FROM dim_cell
WHERE cell_name = ?;
```

```sql
SELECT prb
FROM Cell_ind
WHERE cell_id = ?;
```

在同一数据库并允许下推时，可合并为：

```sql
SELECT f.prb
FROM Cell_ind f
WHERE f.cell_id = (
    SELECT d.cell_id
    FROM dim_cell d
    WHERE d.cell_name = ?
)
```

---

## 4.6 CASE5：NAME 与返回属性同表

业务：

```text
查询 abc = "上研小区A" 的 PRB
```

Binding：

```text
Cell_ind
├── name -> abc
├── id   -> cgi
└── prb  -> prb
```

一个物理模型已直接覆盖 OQL 所需的 `abc + prb`。

规则命中：

```text
Rule 1 + Rule 5
```

生成：

```sql
SELECT prb, name
FROM Cell_ind
WHERE name = ?
```

不执行 NAME_TO_ID。

---

## 4.7 CASE6：缺少事实表 ID Binding

业务仍为：

```text
查询 abc = "上研小区A" 的 PRB
```

Binding：

```text
dim_cell
├── cell_id   -> cgi
└── cell_name -> abc

Cell_ind
└── prb -> prb
```

虽然可在 `dim_cell` 中得到：

```text
abc(NAME) -> cgi(ID)
```

但目标事实模型没有：

```text
Cell_ind.<field> -> cgi
```

因此无法把 ID 继续传递到 PRB 查询。

规则命中：

```text
Rule 6
```

OAC 返回 DIMENSION 目标 Binding 缺失错误。

---

## 4.8 CASE7：覆盖度最高模型优先

当 Binding 存在多个候选模型，例如：

```text
dim_cell:
    cgi + abc

Cell_ind:
    cgi + prb

Sdr_perform:
    cgi + abc + prb
```

对于：

```text
查询 abc = "上研小区A" 的 PRB
```

覆盖度：

```text
dim_cell     = 1 / 2 OQL Property
Cell_ind     = 1 / 2 OQL Property
Sdr_perform  = 2 / 2 OQL Property
```

`Sdr_perform` 可以直接全覆盖。

规则命中：

```text
Rule 7 → Rule 1
```

生成单表查询：

```sql
SELECT prb, cell_name
FROM Sdr_perform
WHERE cell_name = ?
```

---


## 4.9 CASE8：多个 DIMENSION 伴生关系、多个过滤条件组合单值查询

例如对象同时存在：

~~~text
Cell：cgi [ID] ↔ abc [NAME]
Site：sid [ID] ↔ def [NAME]
~~~

OQL：

~~~sql
SELECT prb, abc, def
FROM obj
WHERE abc = "上研小区A"
  AND def = "XX站点"
  AND brand = "5G"
~~~

Planner 为两个 semanticId 独立生成 ResolutionStep：

~~~text
abc(NAME) → cgi(ID)
def(NAME) → sid(ID)
brand = 5G 保持普通 Predicate
~~~

解析完成后再合并为最终物理谓词。不同 DIMENSION 不共享 Resolution 状态。

---

## 4.10 CASE9：多个 DIMENSION + IN 多值查询

OQL：

~~~sql
SELECT prb, abc, def
FROM obj
WHERE abc IN ("上研小区A", "上研小区B", "上研小区C")
  AND def = "XX站点"
  AND brand = "5G"
~~~

IN 需要保留自身谓词语义：

~~~text
abc IN (A, B, C)
→ A/B/C 分别执行 NAME → ID
→ 合并为 ID Set
→ target.id IN (...)
~~~

这不是三个互不相关的 EQ 查询，而是一个 Set Resolution。

---

## 4.11 CASE10：多个 DIMENSION + LIKE 模糊查询

OQL：

~~~sql
SELECT prb, abc, def
FROM obj
WHERE abc LIKE "%上研%"
  AND def = "XX站点"
  AND brand = "5G"
~~~

LIKE 对 NAME 的解析结果天然可能是集合：

~~~text
NAME LIKE "%上研%"
→ Set<NAME>
→ Set<ID>
~~~

因此不能套用 EQ 的“结果必须只有 1 行”规则。1:1 约束仍然要求每个命中的 NAME 不能映射到多个不同 ID。

---

## 4.12 CASE11：列表查询 / 目标维度无等值过滤

场景：

~~~text
查询站点名 A 下所有小区名称和 PRB
~~~

如果事实表只保存 cell_id + prb，而 NAME 在 dim_cell，则需要通过 ID 恢复 NAME：

~~~sql
SELECT d.cell_name, f.prb
FROM dim_cell d
JOIN Cell_ind f
  ON d.cell_id = f.cell_id
ORDER BY f.prb
LIMIT 10;
~~~

此类查询返回数据量可能很大，建议 OQL / 上层业务显式提供 LIMIT 或聚合。

---

## 4.13 CASE12：GROUP BY / ORDER BY 使用 NAME，物理数据使用 ID

OQL：

~~~sql
SELECT def, SUM(prb)
FROM obj
GROUP BY def
~~~

物理事实表只有 site_id 时，不能把 site_id 简单改名为 def。必须执行 ID → NAME 语义恢复：

~~~sql
SELECT d.site_name, SUM(f.prb)
FROM Cell_site_ind f
JOIN dim_site d
  ON f.site_id = d.site_id
GROUP BY d.site_name;
~~~

GROUP BY / ORDER BY 是 DimensionResolutionStep 的正式 placement，而不是 FILTER 的特例。

---

## 4.14 CASE13：跨数据源 NAME → ID → Target

例如：

~~~text
dim_cell → GaussDB
Cell_ind → Hudi / Hive / API
~~~

OAC 生成跨源 DAG：

~~~text
Stage 1：GaussDB
NAME → ID Set
        ↓
Stage 2：Hudi / Hive / API
ID IN (...)
        ↓
Target Result
~~~

禁止生成目标引擎无法执行的“伪跨源 JOIN”。

---

## 4.15 CASE14：ID / NAME 同时作为过滤条件

OQL：

~~~text
cgi = X
AND
abc = Y
~~~

OAC 必须校验：

~~~text
resolve(Y) == X
~~~

如果：

~~~text
Y → X
    正常执行

Y → Z 且 Z != X
    两个条件不能同时成立
    结果为 0 rows
~~~

不能为了减少查询步骤而丢弃 ID 或 NAME 中任意一个条件。

---

## 4.16 CASE15：伴生值不存在 / 数据不满足 1:1

对 Scalar Resolution：

| Resolver 结果 | OAC 行为 |
|---:|---|
| 0 | DIMENSION_VALUE_NOT_FOUND |
| 1 | 正常 |
| >1 | DIMENSION_VALUE_NOT_UNIQUE |

其中 >1 表示运行时数据违反 OMS 声明的 1:1 语义。

对于 LIKE / Set Resolution，允许不同 NAME 对应多个 ID，但同一个 NAME 不能对应多个不同 ID。

---

## 4.17 CASE16：关系查询中的伴生标识

业务：

~~~text
查询站点名 A 下名为“上研小区A”的 Cell 的 PRB
~~~

OQL 示意：

~~~text
ASSOCIATION_QUERY Site -> Cell
WHERE Site.def = "A站点"
  AND Cell.abc = "上研小区A"
RETURN Cell.prb
~~~

规划顺序：

~~~text
Relationship Resolution
        ↓
定位 Site / Cell 对象范围
        ↓
Site 内部 def(NAME) → sid(ID)
Cell 内部 abc(NAME) → cgi(ID)
        ↓
Physical Query
~~~

伴生关系仍然只存在于各自 ObjectType 内，不建立 Site 与 Cell 之间的“跨对象伴生标识”。

# 第五章 OAC Planner 详细设计


## 5.0 QueryShape 与 DimensionResolutionStep

从 OQL 提取的 QueryProperty 不能只保留“有哪些属性”，还必须保留属性所在的查询位置和操作符：

~~~text
FILTER
RETURN
GROUP
ORDER
AGGREGATE
RELATIONSHIP_FILTER
~~~

推荐：

~~~java
class QueryPropertyRef {
    String objectTypeId;
    String propertyId;
    QueryPropertyUsage usage;
    PredicateOperator operator;
}
~~~

Dimension Resolution 统一表示为：

~~~java
class DimensionResolutionStep {
    String semanticId;
    String sourcePropertyId;
    String targetPropertyId;

    ResolutionDirection direction;       // NAME_TO_ID / ID_TO_NAME
    ResolutionCardinality cardinality;   // SCALAR / SET

    PredicateOperator operator;
    QueryPropertyUsage placement;

    String resolverAssetId;
    boolean uniqueRequired;
}
~~~

该结构使 OAC 不再把 DIMENSION 解析硬编码为 WHERE NAME → ID。

## 5.1 规划输入

建议定义：

```java
class SemanticQueryRequest {
    String objectTypeId;
    List<QueryPropertyRef> queryProperties;
    List<Predicate> predicates;
    List<String> returnPropertyIds;
}
```

Binding 快照：

```java
class PropertyBindingSnapshot {
    Map<String, List<PropertyBinding>> bindingsByProperty;
    Map<String, Set<String>> propertiesByAsset;
}
```

DIMENSION 快照：

```java
class DimensionSemanticSnapshot {
    Map<String, DimensionSemantic> semanticByProperty;
}
```

---

## 5.2 候选 Asset 计算

### 5.2.1 Direct Candidate

```text
required = QueryPropertySet

for asset in allAssets:
    coverage = required ∩ propertiesByAsset[asset]

    if coverage == required:
        add DIRECT_SINGLE_ASSET candidate
```

### 5.2.2 Bridge Candidate

仅在没有 Direct Candidate 时计算。

对过滤 Property：

```text
filterProperty = predicate.property
```

若：

```text
role(filterProperty) = NAME
```

则：

```text
idProperty = dimension.idPropertyId
nameProperty = dimension.namePropertyId
```

解析模型候选：

```text
resolverAssets =
    assets(nameProperty)
    ∩
    assets(idProperty)
```

目标模型候选：

```text
targetRequired =
    { idProperty }
    ∪
    nonFilterQueryProperties

targetAssets =
    assets that cover targetRequired
```

任意：

```text
resolverAsset × targetAsset
```

组成一个 Dimension Resolution Route 候选。随后由 PhysicalPlanBuilder 根据 resolverAsset 与 targetAsset 的数据源关系生成 SAME_SOURCE_JOIN、SAME_SOURCE_SUBQUERY 或 CROSS_SOURCE_DAG。

如果任一集合为空，则无可执行 Resolution Route。

---

## 5.3 Candidate Ranking

候选选择分为两级。

### 5.3.1 Resolver Candidate Ranking

当存在多个可完成 ID / NAME 解析的 Asset 时，按以下顺序：

~~~text
1. NAME + ID 是否同时 Binding
2. 是否与 Target Asset 同数据源
3. 是否能够直接 Pushdown
4. 属性覆盖度
5. Binding Route Priority
6. 稳定 Asset ID
~~~

### 5.3.2 Physical Plan Ranking

完整 Plan 的优先级：

~~~text
DIRECT_SINGLE_ASSET
    ↓
SAME_SOURCE_JOIN / SAME_SOURCE_SUBQUERY
    ↓
CROSS_SOURCE_DAG
~~~

同一优先级内：

~~~text
stageCount ASC
assetCount ASC
resolutionStepCount ASC
bindingRoutePriority ASC
stablePlanKey ASC
~~~

## 5.5 Planner 主流程伪代码

~~~text
shape = analyzeQueryShape(oql)

bindingSnapshot = loadBindings(shape.objectTypes)
dimensionSnapshot = loadDimensionSemantics(shape.objectTypes)
sourceCapabilities = loadSourceCapabilities(bindingSnapshot)

directCandidates = findDirectCandidates(
    shape,
    bindingSnapshot
)

if !directCandidates.isEmpty():
    return rankAndSelect(directCandidates)

resolutionSteps = []

for queryProperty in shape.semanticPositions:
    dimension = dimensionSnapshot.get(queryProperty.propertyId)

    if dimension is null:
        continue

    role = resolveDimensionRole(
        queryProperty.propertyId,
        dimension
    )

    step = buildDimensionResolutionStep(
        queryProperty,
        role,
        dimension,
        bindingSnapshot
    )

    if step != null:
        resolutionSteps.add(step)

validateResolutionRoutes(
    resolutionSteps,
    bindingSnapshot
)

physicalCandidates = buildPhysicalPlans(
    shape,
    resolutionSteps,
    bindingSnapshot,
    sourceCapabilities
)

if physicalCandidates.isEmpty():
    throw SEMANTIC_EQUIVALENT_PLAN_NOT_FOUND

return rankAndSelect(physicalCandidates)
~~~

Planner 的关键输出不是“是否命中某一个 Case”，而是：

~~~text
QueryShape
+
DimensionResolutionStep[]
+
PhysicalStage[]
+
ResultSemanticMapping
~~~

# 第六章 Translator 与执行

## 6.1 Direct Plan

Translator 使用一个 targetAsset 组装查询。

```text
OQL Property
  ↓ Binding
Physical Field
```

不进入 DimensionIdentifierResolver。

---

## 6.2 DIMENSION Resolution 的基础执行形态

跨 Asset 的 DIMENSION Resolution 可以通过同源下推或分阶段执行。

### 6.2.1 子查询下推

适用条件：

- resolutionAsset 与 targetAsset 可由同一数据源完成；
- 数据源 Translator 支持子查询或 JOIN 下推。

示例：

```sql
SELECT f.prb
FROM Cell_ind f
WHERE f.cell_id = (
    SELECT d.cell_id
    FROM dim_cell d
    WHERE d.cell_name = ?
)
```

### 6.2.2 分阶段执行

适用条件：

- 无法一次下推；
- 两个 Asset 需要分开访问。

```text
Stage 1
NAME -> ID

Stage 2
ID -> Target Query
```

OAC 执行上下文保存中间 ID，不修改原始 OQL。

---


## 6.3 同源 JOIN

当：

- Resolver 与 Target 位于同一数据源；
- NAME 还需要参与 RETURN / GROUP / ORDER；
- Translator 支持 JOIN 下推；

可生成：

~~~sql
SELECT f.prb, d.cell_name
FROM Cell_ind f
JOIN dim_cell d
  ON f.cell_id = d.cell_id
WHERE d.cell_name = ?;
~~~

## 6.4 跨源 DAG

当 Resolver 与 Target 位于不同数据源，例如：

~~~text
dim_cell → GaussDB
Cell_ind → Hudi / Hive / API
~~~

执行：

~~~text
Stage 1
GaussDB：NAME → ID / ID Set

Stage 2
Hudi / Hive / API：ID IN (...)

Stage N
必要时执行结果语义恢复
~~~

中间 ID 只存在于 OAC ExecutionContext，不修改原始 OQL。

## 6.5 ID → NAME 结果语义恢复

如果事实查询只能得到 ID，而 OQL 要求 RETURN / GROUP / ORDER 使用 NAME，则 Planner 生成 ID_TO_NAME Resolution。

可通过：

1. 同源 JOIN 一次返回 NAME；
2. 主查询后批量 ID → NAME lookup。

禁止仅把物理 ID 字段 alias 成 NAME，因为字段名相同不代表业务语义等价。

## 6.6 1:1 结果校验

Stage 1 对单个输入值必须执行唯一性校验：

| 解析结果 | 行为 |
|---:|---|
| 0 | 返回 `DIMENSION_VALUE_NOT_FOUND` |
| 1 | 正常执行 Stage 2 |
| >1 | 返回 `DIMENSION_VALUE_NOT_UNIQUE` |

对于 `IN`，每个输入元素独立满足 1:1，然后合并为 ID 集合。

---

## 6.7 返回语义恢复

如果 OQL 返回 NAME，但目标事实查询只投影 ID，OAC 必须恢复原 Property 语义。

可选方式：

1. 执行计划已包含 resolutionAsset 时直接追加 NAME 投影；
2. 主查询结束后批量执行 ID→NAME lookup。

返回字段名称、alias 和对象属性语义保持 OQL 定义。

---

# 第七章 错误处理

## 7.1 OMS 错误码

| 错误码 | 场景 |
|---|---|
| `DIMENSION_SEMANTIC_INVALID` | DIMENSION 结构不完整 |
| `DIMENSION_PROPERTY_NOT_FOUND` | ID / NAME Property 不存在 |
| `DIMENSION_PROPERTY_SCOPE_INVALID` | 两端不属于同一 ObjectType |
| `DIMENSION_PROPERTY_CONFLICT` | Property 已参与另一条 DIMENSION 关系 |
| `DIMENSION_SEMANTIC_INCONSISTENT` | 双端 DIMENSION 内容不一致 |
| `DIMENSION_SEMANTIC_REFERENCE_IN_USE` | 删除 Property 时存在伴生引用 |

## 7.2 OAC 错误码

| 错误码 | 场景 |
|---|---|
| `SEMANTIC_EQUIVALENT_PLAN_NOT_FOUND` | 无 Direct Plan 且无可执行 Bridge Plan |
| `DIMENSION_TARGET_BINDING_NOT_FOUND` | 目标事实模型未绑定伴生 ID |
| `DIMENSION_RESOLUTION_BINDING_NOT_FOUND` | 找不到同时绑定 NAME+ID 的解析模型 |
| `DIMENSION_VALUE_NOT_FOUND` | NAME 未解析到 ID |
| `DIMENSION_VALUE_NOT_UNIQUE` | NAME 解析到多个 ID |
| `DIMENSION_OPERATOR_NOT_SUPPORTED` | 条件操作符不支持伴生转换 |
| `DIMENSION_CONDITION_INCONSISTENT` | ID / NAME 同时过滤且语义冲突 |
| `CROSS_SOURCE_STAGE_BINDING_FAILED` | 跨源 DAG 中间结果绑定失败 |
| `PHYSICAL_ASSET_SELECTION_AMBIGUOUS` | 候选无法通过路由规则稳定选择 |

错误信息必须包含：

```json
{
  "objectType": "Cell",
  "queryProperties": [
    "abc",
    "prb"
  ],
  "sourceProperty": "abc",
  "semanticId": "dim_cell_identity",
  "missingBindingProperty": "cgi"
}
```

便于开发和模型配置人员快速定位缺失的 Binding。

11. 多 DIMENSION 独立解析；
12. 多候选按 Resolver Candidate Ranking 稳定选择；
13. 同源时生成 JOIN / SUBQUERY 候选；
14. 跨源时生成 DAG；
15. Translator 不重新执行语义规划；
16. Scalar Resolution 执行 1:1 唯一性校验。

## 10.3 联调验收

端到端必须验证：

```text
原始问题
  ↓
OQL
  ↓
QueryPropertySet
  ↓
Binding Matrix
  ↓
DIMENSION 语义
  ↓
Physical Plan
  ↓
SQL / GQL / API
  ↓
结果
```

验收标准：

1. 同表场景生成单表查询；
2. NAME 跨表且 ID 桥接完整时生成语义等价查询；
3. NAME 跨表但目标事实表缺 ID Binding 时明确失败；
4. 无伴生路径的跨模型查询不进行字段猜测；
5. 多模型场景优先选择直接覆盖属性最多的模型；
6. OQL 不因物理模型布局而改变；
7. NAME→ID 解析满足 1:1；
8. 返回字段保持 OQL 对象属性语义；
9. OMS Binding 或 DIMENSION 关系变更后，新请求使用最新模型版本；
10. 错误日志能够明确指出缺失的 Property Binding 或语义路径。

## 10.4 CASE8～CASE16 扩展验收

新增必须覆盖：

1. CASE8：两个及以上 DIMENSION 伴生关系独立解析并合并 Predicate；
2. CASE9：IN 生成 ID Set；
3. CASE10：LIKE 生成 Set Resolution；
4. CASE11：列表查询通过 JOIN 恢复 NAME，并支持 LIMIT / 聚合控制；
5. CASE12：GROUP BY / ORDER BY NAME 时保持业务语义；
6. CASE13：跨数据源生成 CROSS_SOURCE_DAG；
7. CASE14：ID / NAME 同时过滤时执行一致性校验；
8. CASE15：0 / 1 / >1 的运行时语义处理正确；
9. CASE16：先执行 Relationship Resolution，再执行对象本地 DIMENSION Resolution；
10. RETURN / GROUP / ORDER 场景能够生成 ID_TO_NAME Resolution；
11. Translator 不自行重复实现 ID / NAME 语义规则；
12. 计划日志能够还原 QueryShape、ResolutionStep 和 PhysicalStage。

最终职责：
