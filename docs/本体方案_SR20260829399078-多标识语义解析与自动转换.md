## 问题概述
本体对象的属性对于类似维值、枚举这一类的信息，会有ID和Name两个信息，用户原始问题输入、OQL的输入（过滤条件、返回字段）、数据库实际存储的值，在这三个阶段交互中需要根据输入的字段实际表示的内容进行转换。
例如：
原始问题是某个小区名称指标，数据库中存储的是小区ID，这就需要小区属性本身就定义ID和name两个字段，从界面输入转OQL时标识查询小区名称，OAC根据OMS的属性定义（ID和name的对应）以及关联物理模型信息，分析需要转换为ID才能拼接物理SQL查询，然后返回时又要求转换为name进行小区名称的返回。

请对以上单个问题进行描述逻辑和处理的整理，并再给出几个相似的案例说明，之后总结输出如下章节内容：
1. 章节1：业务问题场景
2. 章节2：业务问题实例化举例，含业务问题期望的处理过程与结果
3. 章节3：针对业务问题做系统性的归类整理，给出该类问题的系统性处理思路
4. 章节4: 以"原始问题输入"->"意图理解"->“schema对齐”->"ID/Name标识识别"->"处理过程中根据标识进行正确的ID、Name的互转"





这个问题建议不要只定义成“ID/Name转换”，其本质是**业务实体的多标识表达与物理存储标识之间的语义对齐问题**：

> 同一个业务实体，在自然语言、OQL语义查询和底层物理数据中可能使用不同标识表达。平台需要在本体中显式描述这些标识之间的伴生/等价关系，并在查询链路中根据“输入语义、查询语义、物理存储语义、输出语义”自动完成标识解析与转换。

下面按你要求的四个章节整理。

# 1. 业务问题场景

## 1.1 问题背景

本体对象通常存在多个能够描述或标识同一业务实体的属性，最典型的是 **ID + Name**。

例如“小区”对象：

| 属性              | 示例                            | 作用                  |
| --------------- | ----------------------------- | ------------------- |
| `Cell.ID / CGI` | `460-00-12345-001`            | 唯一标识小区，适合系统存储、关联和查询 |
| `Cell.Name`     | `MTUTK_001_TaiKooMTR_A_SUB6G` | 业务可读名称，适合用户输入和结果展示  |

两者描述的是**同一个Cell实例**，只是承担不同的标识角色：

```text
Cell
├── CGI       → Identifier / Key
└── CellName  → Name / Label
```

实际业务链路中，三个阶段使用的标识可能并不一致：

```text
自然语言 / OQL           物理数据库              最终展示
     │                       │                      │
 小区名称                  CGI                  小区名称
     │                       │                      │
     └────── Name → ID ──────┴──── ID → Name ──────┘
```

因此不能简单按照“用户输入哪个属性，就使用哪个物理字段查询”。

---

## 1.2 核心问题

以用户问题：

> “查询 MTUTK_001_TaiKooMTR_A_SUB6G 小区的PRB利用率。”

为例。

用户输入的是：

```text
Cell.Name =
MTUTK_001_TaiKooMTR_A_SUB6G
```

但性能表实际可能只保存：

```text
CGI
PRB_USAGE
TIME
```

并不存在 `CELL_NAME`。

如果OAC直接生成：

```sql
WHERE CELL_NAME = 'MTUTK_001_TaiKooMTR_A_SUB6G'
```

查询就无法执行。

因此平台需要知道：

```text
Cell.Name
    ↕
Cell.CGI
```

是同一个Cell对象实例的**伴生标识属性**，并进一步知道：

```text
自然语言输入：Name
        ↓
OQL语义：Cell.Name
        ↓
物理查询要求：Cell.CGI
        ↓
Name → CGI解析
        ↓
物理SQL：WHERE CGI = ...
        ↓
查询结果
        ↓
CGI → Name
        ↓
按照用户要求返回Cell.Name
```

---

## 1.3 问题本质

因此，该问题建议统一定义为：

### **对象多标识语义对齐与转换**

英文可定义为：

### **Entity Identifier Resolution & Translation**

解决的是：

> **同一业务对象在自然语言、OQL、本体Schema和物理数据之间使用不同标识方式时，基于本体定义自动识别标识语义，并完成不同标识之间的解析、转换和结果还原。**

---

# 2. 业务问题实例化举例

## 2.1 案例一：小区 Name → CGI → Name

### 用户问题

> 查询“MTUTK_001_TaiKooMTR_A_SUB6G”小区的PRB利用率。

### 本体定义

```text
Cell
├── CGI
│   └── identifierRole = ID
│
├── CellName
│   └── identifierRole = NAME
│
└── PRBUsage
```

并定义：

```text
CGI ←→ CellName
```

属于同一对象实例的标识映射。

### OQL

意图理解后生成：

```text
SELECT
    Cell.CellName,
    Cell.PRBUsage

WHERE
    Cell.CellName =
    'MTUTK_001_TaiKooMTR_A_SUB6G'
```

这里非常重要：

> **OQL应该保持业务语义，不建议提前把Name强制改写成CGI。**

### OAC物理转换

OMS告诉OAC：

```text
CellName → Name标识
CGI      → ID标识

Performance表：
Cell.CGI → CELL_CGI
Cell.PRBUsage → PRB_USAGE
```

OAC发现性能表只有CGI，因此首先解析：

```text
MTUTK_001_TaiKooMTR_A_SUB6G
       ↓
CellName → CGI
       ↓
460-00-12345-001
```

再生成物理SQL：

```sql
SELECT
    CELL_CGI,
    PRB_USAGE
FROM CELL_PERFORMANCE
WHERE CELL_CGI = '460-00-12345-001';
```

查询得到：

```text
460-00-12345-001 | 87.5
```

再根据OQL要求：

```text
CGI → CellName
```

最终返回：

```text
小区名称：MTUTK_001_TaiKooMTR_A_SUB6G
PRB利用率：87.5%
```

形成完整闭环：

> **Name输入 → ID查询 → Name输出**

# 2.2 案例二：终端型号 Name → TAC → Name

用户问：

> “iPhone 16 Pro用户的平均下行速率是多少？”

本体：

```text
Terminal
├── TAC
│   └── ID
│
└── ModelName
    └── NAME
```

实际用户性能数据只保存：

```text
TAC
DL_THROUGHPUT
```

因此：

```text
iPhone 16 Pro
      ↓
Terminal.ModelName
      ↓
TAC映射
      ↓
TAC IN ('12345678', ...)
      ↓
查询用户性能数据
      ↓
聚合DL_THROUGHPUT
```

最终仍按照用户语义返回：

```text
终端型号：iPhone 16 Pro
平均下行速率：XX Mbps
```

这里还说明一个问题：

> **Name → ID不一定是一对一，也可能是一对多。**

一个终端型号可能对应多个TAC，因此转换能力必须支持：

```text
1:1
1:N
N:1
```

而不能简单做字符串替换。

# 2.3 案例三：套餐名称 → Package ID

用户问：

> “分析5G家庭融合套餐用户的年龄分布。”

本体：

```text
Package
├── PackageID
└── PackageName
```

用户表实际存：

```text
USER_ID
PACKAGE_ID
AGE
```

处理：

```text
“5G家庭融合套餐”
        ↓
识别为Package.PackageName
        ↓
PackageName → PackageID
        ↓
PACKAGE_ID = 'P10086'
        ↓
查询User
        ↓
GROUP BY Age
```

这里又与前面讨论的**维值实体链接**结合起来：

如果用户实际说的是：

> “5G家庭套餐”

还需要先：

```text
5G家庭套餐
   ↓ 语义/向量/全文检索
5G家庭融合套餐
   ↓
Package.PackageName
   ↓
PackageID
```

所以存在两级解析：

> **非标准业务表达 → 标准Name → 物理ID**

# 2.4 案例四：区域名称 → Region Code

用户问：

> “分析Jakarta区域WhatsApp体验情况。”

业务语义：

```text
Region.Name = Jakarta
```

底层网络性能数据可能只存：

```text
REGION_CODE = 'JKT'
```

因此：

```text
Jakarta
 ↓
Region.Name
 ↓
Region.Code = JKT
```

返回时：

```text
JKT → Jakarta
```

# 2.5 案例五：枚举Label → Code

这类问题甚至不一定是独立对象。

例如：

```text
Alarm.Severity
```

本体定义值域：

```text
Critical → 1
Major    → 2
Minor    → 3
Warning  → 4
```

用户问：

> “查询Major及以上级别告警。”

OQL表达业务语义：

```text
Alarm.Severity = Major+
```

而物理SQL可能需要：

```sql
WHERE SEVERITY_CODE IN (1, 2)
```

返回：

```text
1 → Critical
2 → Major
```

因此这个问题已经从简单的：

> ID ↔ Name

扩展成更普遍的：

> **业务语义值 ↔ 物理编码值**

# 3. 该类问题的系统性归类与处理思路

建议不要针对“小区ID/名称”“终端TAC/型号”“套餐ID/名称”分别做特殊逻辑，而抽象成统一的 **Semantic Value Resolution** 能力。

## 3.1 第一类：对象标识伴生属性

典型：

```text
Cell.CGI        ↔ Cell.Name
Terminal.TAC    ↔ Terminal.ModelName
User.MSISDN     ↔ User.Name
Site.SiteID     ↔ Site.Name
```

特点：

> 多个属性共同标识/描述同一个对象实例。

建议本体增加类似：

```text
identifierRole:
  PRIMARY_ID
  BUSINESS_ID
  CODE
  NAME
  LABEL
  ALIAS
```

同时定义同一：

```text
identifierGroup
```

例如：

```text
Cell

identifierGroup = CellIdentity
├── CGI      : PRIMARY_ID
├── CellName : NAME
└── CellCode : CODE
```

---

## 3.2 第二类：维度值 ID/Name

例如：

```text
PackageID ↔ PackageName
RegionCode ↔ RegionName
VendorID ↔ VendorName
```

通常来源于维表。

这种情况下本体Schema不需要存储所有实例，而是定义：

```text
Property: User.Package

valueSource:
    DimensionTable

keyProperty:
    PackageID

labelProperty:
    PackageName
```

运行时从维表/维值服务解析。

---

## 3.3 第三类：枚举 Code/Label

例如：

```text
1 ↔ Critical
2 ↔ Major
3 ↔ Minor
```

特点是：

* 小基数；
* 稳定；
* 受控值域。

可以直接作为本体属性的Value Domain管理：

```text
Alarm.Severity
    ↓
EnumValue
├── code=1 / label=Critical
├── code=2 / label=Major
└── code=3 / label=Minor
```

---

## 3.4 第四类：非标准名称 → 标准名称 → ID

这是Agent场景尤其重要的一类：

```text
用户表达
“5G家庭套餐”
      ↓
实体链接
      ↓
标准名称
“5G家庭融合套餐”
      ↓
标识转换
      ↓
PackageID=P001
```

这里不能把两个步骤混为一谈：

**第一步是Semantic Entity Linking：**

> 用户说的是什么？

**第二步是Identifier Translation：**

> 这个业务实体在目标数据源中用什么值查询？

二者职责应明确分离。

---

# 3.5 建议建立统一的“规范标识—展示标识—物理标识”模型

这是我最推荐的抽象。

对于每个对象/维度实例，不要只考虑ID和Name，而是区分三种角色：

```text
              Entity
                 │
      ┌──────────┼──────────┐
      ↓          ↓          ↓
Canonical     Display     Physical
Identifier   Identifier   Identifier
规范标识       展示标识       物理标识
```

例如Cell：

```text
Canonical：CGI
Display：CellName
Physical：CELL_CGI
```

终端：

```text
Canonical：TAC
Display：ModelName
Physical：TAC_CODE
```

套餐：

```text
Canonical：PackageID
Display：PackageName
Physical：PACKAGE_ID
```

注意：

> **Physical Identifier不一定固定。**

同一个本体对象映射不同数据源：

```text
                 Cell
                  │
              CGI / Name
                  │
       ┌──────────┼──────────┐
       ↓          ↓          ↓
无线性能表      告警系统       API
CGI            CELL_ID      CellName
```

因此：

* **哪个属性是ID/Name** → 本体概念语义层；
* **当前物理数据源实际使用哪个标识** → 数据模型/绑定映射层。

这样正好与你现有三层模型保持一致。

# 4. 完整处理流程设计

建议把整个链路设计成：

> **原始问题输入 → 意图理解 → Schema对齐 → ID/Name标识识别 → 标准实体解析 → 物理标识转换 → 查询执行 → 结果标识还原**

可以进一步展开为下面8步。

### Step 1：原始问题输入

例如：

> 查询“MTUTK_001_TaiKooMTR_A_SUB6G”小区的PRB利用率。

此时只知道用户输入的是一个字符串：

```text
MTUTK_001_TaiKooMTR_A_SUB6G
```

---

### Step 2：意图理解

Agent/OAG识别：

```text
查询对象：Cell
查询指标：PRBUsage

过滤条件：
“MTUTK_001_TaiKooMTR_A_SUB6G”
```

并判断该Mention很可能是：

```text
Cell实例
```

---

### Step 3：Schema对齐

通过本体实体链接，将其对齐到：

```text
Cell.CellName
```

而不是：

```text
Cell.CGI
```

形成明确语义：

```text
Cell.CellName =
"MTUTK_001_TaiKooMTR_A_SUB6G"
```

---

### Step 4：ID/Name标识识别

读取OMS本体定义：

```text
Cell
├── CGI
│   identifierRole = PRIMARY_ID
│
└── CellName
    identifierRole = NAME

identifierGroup = CellIdentity
```

因此平台知道：

```text
CellName ↔ CGI
```

是同一对象实例的两个标识。

---

### Step 5：保持业务语义生成OQL

建议OQL仍然表达：

```text
SELECT
    Cell.CellName,
    Cell.PRBUsage
WHERE
    Cell.CellName =
    "MTUTK_001_TaiKooMTR_A_SUB6G"
```

**不要让Agent负责Name→ID的物理转换。**

这是很关键的架构边界：

> Agent负责“我要查哪个小区”；OAC负责“这个数据源应该用什么标识查询”。

---

### Step 6：OAC进行物理标识解析

OAC读取Binding：

```text
Cell.PRBUsage
    ↓
CELL_PERFORMANCE.PRB_USAGE

Cell实例关联键
    ↓
CELL_PERFORMANCE.CGI
```

发现目标事实表要求CGI，因此生成转换需求：

```text
Required Identifier = CGI
Current Identifier = CellName
```

执行：

```text
CellName
   ↓ Identifier Resolver
CGI
```

得到：

```text
460-00-12345-001
```

---

### Step 7：生成物理SQL并执行

```sql
SELECT
    CGI,
    PRB_USAGE
FROM CELL_PERFORMANCE
WHERE CGI = '460-00-12345-001';
```

底层返回：

```text
460-00-12345-001 | 87.5
```

---

### Step 8：按照OQL语义恢复结果

原始OQL要求返回：

```text
Cell.CellName
Cell.PRBUsage
```

因此OAC执行：

```text
460-00-12345-001
      ↓
CGI → CellName
      ↓
MTUTK_001_TaiKooMTR_A_SUB6G
```

最终向Agent返回：

```text
CellName                         PRBUsage
------------------------------------------------
MTUTK_001_TaiKooMTR_A_SUB6G      87.5%
```

---

## 最终建议形成的平台机制

整条链路可以收敛成下面这个架构：

```text
原始问题
   │
   ▼
意图理解 / Mention提取
   │
   │ "MTUTK..."
   ▼
本体Schema对齐
   │
   │ Cell.CellName
   ▼
标准业务语义 OQL
   │
   │ WHERE Cell.CellName = xxx
   ▼
┌──────────── OAC ─────────────┐
│                              │
│  查询Binding                  │
│       ↓                      │
│  识别目标物理标识             │
│       ↓                      │
│  Name → ID                   │
│       ↓                      │
│  生成物理SQL                  │
│       ↓                      │
│  数据查询                     │
│       ↓                      │
│  ID → Name                   │
│                              │
└──────────────┬───────────────┘
               ▼
        业务语义结果
```

这里建议坚持一个非常重要的设计原则：

> **OQL保持业务语义，ID/Name等物理标识转换尽量下沉到OAC。**

否则如果Agent/OAG提前把：

```text
CellName → CGI
```

再生成OQL，就会让上层开始感知底层数据源到底使用CGI、CellID还是Name，破坏本体数据访问层最重要的**语义与物理解耦**。

最终可以把这个能力定义为：

### **多标识语义解析与自动转换**

**Multi-Identifier Semantic Resolution & Translation**

其核心价值是：

> **允许用户、Agent和OQL始终使用自然的业务语义表达，由本体定义对象不同标识之间的语义关系，OAC根据目标数据源的实际存储方式自动完成ID/Name/Code/Label等标识转换，实现“业务怎么说”与“数据怎么存”的解耦。**
