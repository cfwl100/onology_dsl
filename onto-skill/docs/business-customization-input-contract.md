# 业务定制 Skill 输入契约

## 1. 目标

业务定制 Skill 位于 `scenario-skill/`，负责把用户问题和业务知识注入给 `Ontology-based-planning-skill`。

该契约的核心原则是：**自然语言优先，结构化字段可选，对外只暴露一个公共本体ID，并把业务定制拆成流程级定制和步骤级定制两部分**。

上层业务 Skill 不需要为了适配 planning 层而强行填写复杂字段表，也不需要同时区分本体子图检索的 `ontologyId` 和本体访问的 `schemaRef`。对外本体是一个整体，业务 Skill 只需提供一个 `本体ID`。

---

## 2. 两类业务定制内容

### 2.1 流程级定制

流程级定制说明：planning 大流程要执行全部步骤还是部分步骤，是否调整顺序，是否跳过或追加步骤。

默认流程为：

```text
S1 读取业务注入与整理上下文
  -> S2 子图检索
  -> S3 基于本体子图的任务规划
  -> S4 OAC 查询
  -> S5 Function 发现
  -> S6 Function 执行
  -> S7 汇总
```

业务 Skill 可以自然语言说明：

- 只检索子图并解释模型。
- 只执行子图检索和 OAC 查询。
- 需要子图检索、任务规划、OAC 查询和 Function 调用全流程。
- 某方向或某对象需要重复执行 S2/S3/S4。
- Function 先于 OAC，或 Function 作为 OAC 的补充。

### 2.2 步骤级定制

步骤级定制说明：每个具体步骤的输入、输出、执行规则和失败策略。

业务 Skill 可以自然语言说明：

- S2 子图检索规则：query 模板、扩展策略、返回函数候选、返回哪些子图字段。
- S3 任务规划规则：从哪个起点对象查到哪个终点对象、如何选择路径、如何拆分任务。
- S4 OAC 查询规则：操作类型、查询对象、过滤条件、返回字段、排序分组、空结果策略。
- S5/S6 Function 规则：函数选择依据、参数规格获取、参数来源、缺参策略。
- S7 汇总规则：分方向输出、保留依据、结果为空如何说明。

---

## 3. 推荐自然语言定制输入

业务定制 Skill 推荐向 planning 层传递一段自然语言定制说明：

```text
本体ID：<对外公共本体ID，如已知>
业务意图：<用户改写后的详细自然语言问题，包含业务目标、实体、条件、范围、方向、返回要求和期望动作>
已读取业务定制文件：<knowledge / rules / templates 文件路径，可多个>
业务知识与规则：<从业务文件原文抽取或直接引用的场景知识、规则、SOP、模板、禁止项、返回要求>
流程级定制：<执行全部默认步骤还是部分步骤；是否调整步骤顺序；是否追加或跳过步骤>
步骤级定制：<分别说明子图检索、基于子图规划、OAC 查询、Function 调用和汇总的输入、输出、执行规则>
缺失信息：<无法从用户输入或业务知识获得的信息；没有则写无>
```

其中强烈建议保留三类信息：

1. `业务意图`：必须是业务 Skill 改写后的详细自然语言问题，而不是短标签。
2. 实际读取的业务定制文件路径。
3. 原始知识中的硬约束、固定模板、禁止项、返回字段和失败处理规则。

`本体ID` 如果业务 Skill 已知，应直接写入；如果未知，交给 planning 层返回缺失项。

---

## 4. 业务注入文件内容建议

业务定制文件可以保持自然语言 Markdown 写法，不要求 JSON 化。建议按如下内容组织：

```text
# <场景或规则名称>

## 场景知识
<行业规则、业务含义、对象解释>

## 子图检索规则
<如何改写 OAG query，是否需要函数候选，扩展方向，返回哪些子图字段>

## 基于子图的任务规划规则
<从哪个对象出发，查到哪个对象；单步还是多步；先 OAC 还是先 Function；步骤顺序和跳过规则>

## OAC 查询规则
<操作类型、查询对象、过滤条件、返回字段、排序、maxResults、空结果策略>

## Function 调用规则
<函数选择依据、参数来源、缺参策略、是否必须调用>

## 汇总规则
<输出结构、分方向或分对象汇总、空结果说明>
```

Planning 层会结合这些文件和 OAG 子图结果生成执行任务。

---

## 5. 结构化字段只是可选增强

如果某些业务 Skill 已经方便地产生结构化字段，可以继续使用：

| 字段 | 是否必填 | 说明 |
|---|---|---|
| `intent` | 可选 | 建议填写为改写后的详细自然语言问题，而不是短标签。 |
| `ontologyId` | 可选 | 兼容字段，等价于对外公共 `本体ID`。 |
| `schemaRef` | 可选 | 兼容字段。若与 `本体ID` 冲突，planning 层必须报告冲突。 |
| `knowledge` | 可选 | 业务知识。可以是自然语言段落，不要求拆成 facts/rules/constraints。 |
| `flowCustomization` | 可选 | 流程级定制。 |
| `stepCustomization` | 可选 | 步骤级定制。 |
| `entities` | 可选 | 实体值。可自然语言描述。 |
| `variables` | 可选 | 时间范围、方向列表等变量。可自然语言描述。 |
| `constraints` | 可选 | 执行约束。可自然语言描述。 |
| `steps` | 可选 | 仅当外部系统已经有完整显式步骤时使用。 |

不要为了填字段而把原始知识强行拆碎。字段存在的目的只是方便 planning 层读取，不是业务 Skill 的强制接口。

---

## 6. Planning 层如何消费自然语言定制内容

`Ontology-based-planning-skill` 收到自然语言定制说明后，应在 S1 阶段完成轻量整理：

1. 提取 `业务意图`，作为 OAG、OAC、Function 的详细自然语言问题。
2. 识别公共 `本体ID`。
3. 读取并保留业务定制文件内容。
4. 识别流程级定制：哪些步骤执行、步骤顺序、追加/跳过规则。
5. 识别步骤级定制：S2/S3/S4/S5/S6/S7 的输入输出要求。
6. 不提前确定对象、字段、关系或函数；这些仍以本体子图和平台返回结果为准。

---

## 7. 无损注入原则

1. 可以直接引用业务文件原文，不要求拆成结构化字段。
2. 不要只传一句摘要，例如“当前意图对应的业务知识摘要”。
3. 必须保留知识来源，例如 `knowledge/nealarm.md`、`knowledge/propagation.md`、`knowledge/evidence.md`。
4. 硬约束、固定模板、禁止项、返回字段、方向顺序、不可重试规则必须完整保留。
5. 流程级定制和步骤级定制必须区分表达。
6. 用户显式输入与业务知识冲突时，以用户输入优先，并说明冲突。
7. 业务知识只能作为规划依据；对象、字段、关系、函数最终仍以本体子图和平台返回结果为准。

---

## 8. 与三种输入模式的关系

| 模式 | 上层业务 Skill 推荐做法 |
|---|---|
| 默认规划模式 | 传业务意图以及必要本体ID。 |
| 业务定制模式 | 传自然语言定制说明，包含本体ID、业务意图、业务文件、流程级定制和步骤级定制。 |
| 显式步骤执行模式 | 直接传完整 steps；如果没有完整 steps，不要强行构造。 |

---

## 9. alarm-propagation 推荐注入方式

`alarm-propagation` 可以保留原始 `evidence.md`、`nealarm.md`、`propagation.md` 的自然语言写法。

注入给 planning 层时建议这样表达：

```text
本体ID：network@1.0
业务意图：<基于用户问题改写后的详细自然语言任务，例如“验证网元A在同站点和对端网元方向上的告警传播证据，并分别返回每个方向的证据结果或空结果说明”>
已读取业务定制文件：knowledge/<xxx>.md
业务知识与规则：完整保留该 knowledge 文件中的目标、核心经验知识、OAG 调用规则、OAC 调用规则、执行建议、必须遵循的禁止项和返回要求。
流程级定制：<例如“每个方向串行执行 S2/S3/S4；不调用 Function；每个方向独立汇总”>
步骤级定制：<例如“S2 使用 knowledge 原文固定检索模板；S4 只查询子图确认过的对象、字段、关系；空结果不重试”>
缺失信息：没有则写无。
```

这样上层业务 Skill 的编写方式仍然接近原始自然语言 Skill，不需要维护复杂字段表。
